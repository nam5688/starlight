# 궁합 3종 고객용 서술 개편 + 결과 위치 수정 (2026-10-19)

간단 궁합(무료) · 사주 궁합 · 리포트 궁합(심층)이 **개인 심층 리포트처럼 생활 말로 읽히게** 고쳤고, 간단 궁합 제출 뒤 결과가 중간부터 보이던 문제를 고쳤다.
**AI 호출 0회 · 승인 6/6 · 누적 4,314.89원 불변 · 실결제 0 · 운영 DB 0 · 판매 스위치 그대로(사주 궁합 · 리포트 궁합 꺼짐).** 엔진(`compat.ts`) · 점수 · 커플 유형 · 근거 ID · fact · cue는 한 글자도 바꾸지 않았다.

> **두 가지 검증을 구분한다.** ① **모의 편집 검증**(이 문서): 지시문을 고친 뒤 AI 하위 작업자(대리 작성기)가 쓴 글을 제품 검사와 사람이 근거와 대조한 것 — 실제 서비스 AI의 글이 아니다. ② **실제 AI 출력 품질 검증**: 하지 않았다(승인 전). 이 문서의 어떤 줄도 "실제 AI가 이렇게 쓴다"는 증거가 아니다.

## 3. 사주 궁합 — 모의 전문 · 근거 대조

- **지시문 변경**: `docs/samples/prompts/compat-v1-prompt-0.5.txt` → `0.6`(개편 직후, 기록으로 보관) → **`0.7`(현재, 아래 3-1 검수 보정 반영 — 시험이 보관본과 글자 하나까지 같음을 확인)**.
- **수정 전의 글(참고)**: 같은 지시문 계열의 예전 대리 작성기 글 `docs/samples/compat-v1-proxy/prompt-0.3/C1-first-response.json` — 같은 입력의 글이 아니고 구성도 이전(영역 다섯)이라 *말투 비교용*일 뿐이다. 예: "이렇게 읽는 바탕에는 일간(태어난 날의 하늘 글자)이 있어요. A님은 나무 기운, B님은 물 기운에 해당하는데, 이런 짝은 한쪽이 다른 쪽을 받쳐 주고 키워 주는 모양으로 읽는 경우가 많아요." — 용어 설명이 문단을 끌고 간다.
- **수정 후의 모의 전문**: `docs/samples/compat-voice-v1/saju-after.json`(연인 · 가상 쌍 · 제품 검사 **통과: BLOCK 0 · WARN 0**) · 근거와 한 장씩 대조한 표 `saju-after-evidence-check.md`.
  예: "두 분은 한 사람이 더 챙기고 한 사람이 더 기대는 모양이 되기 쉬운 사이예요. … 챙기는 쪽이 지치지 않도록 오늘은 누가 더 챙겼는지 가볍게 돌아보면 좋아요." (근거 `compat.day-stem` 상생 + `compat.role`)

**근거 대조에서 찾아 고친 오류 2건(모의 글 자체의 결함이며 검사는 이를 통과시켰다 — 제품 검사의 한계)**

1. **A→B / B→A 방향이 근거와 거꾸로**였다. 근거(`compat.role`): A 기준 B는 인성(A를 돌봐 주는 쪽), B 기준 A는 식상(B에게 베푸는 쪽). 처음 글은 A→B에 "챙겨 주고 싶은 마음이 앞설 때"를 줬다 → A→B "챙김을 받았다고 느낄 때" / B→A "챙겨 주고 싶은 마음이 앞설 때"로 바꿈. **형식 검사로는 이 방향을 못 잡는다 — 사람이 읽어 확인해야 한다**(실제 AI 글에서도 같은 점검이 필요하다).
2. 개운 문단에 "**이미 가진** 흰색 소품"이 있었다 — 가진 물건을 추정한 말이다. 처음에는 "집에 있는 흰색 소품"으로 바꿨으나 이것도 **있다고 가정하는 같은 뜻**이라, 검수 지적(2026-10-19)에 따라 **"흰색 소품이 있다면 곁에 두는 정도로 활용해 보세요"라는 가정형**으로 고쳤다. 지시문의 "이미 가진 것으로 가볍게 먼저 해 볼 수 있다고 전하고"가 이 문장의 출처라 지시문에서도 "물건은 '있다면 활용해 보세요'처럼 가정형으로"로 바꿨다.

나머지 장(오행 개수 · 합 3곳 · 충/형 2곳 · 속도 · 시기 두 사람의 대운 · 세운 연도)은 근거의 fact와 숫자 · 방향이 일치함을 한 줄씩 확인했다(`saju-after-evidence-check.md`).

- **근거 대조에서 찾아 고친 것**: ① B→A 행동이 거꾸로였다(`pair.sensitivity`: 반응에 마음이 크게 쓰이는 쪽은 A인데 처음 글은 A에게 "가볍게 물어보세요"를 줬다 → "B님이 A님에게: 답이 늦어질 것 같으면 바쁘다고 한 줄 먼저"로 고침). ② A→B는 "A는 거리가 필요하고 B는 가까워지는 쪽이 편하다"(`pair.avoidance`)에 맞춰 "혼자 있고 싶은 날에는 다시 연락할 때를 한마디"로 고침. ③ 근거 밖의 감정 서술("서로를 고마워하기 쉬운 사이")과 6곳의 충 · 형을 "큰 문제라기보다"로 줄이던 문장을 고침. ④ "한 분 · 다른 분"이던 응답 비교 문장을 `A님 · B님`으로 바꿔 누가 어느 쪽인지 화면에서 "본인 · 상대"로 읽히게 했다.
- **지어내지 않은 것**: 두 사람이 답하지 않은 영역은 비교하지 않았고(근거 `compared` 5개 · 건너뜀 5개), 속마음 · 지난 사건 · 가족 · 성 역할은 쓰지 않았다. 친구 사이에 연애 · 결혼 말이 없다(검사가 막음).
- **개인정보**: 이 글(저장 형태)에는 실명 · 생년월일 · 응답 원문이 없다. 화면의 "본인 · 상대"는 저장 글을 바꾸지 않고 보여 주기 직전에만 바꾼다.

## 5. 결과가 중간부터 보이던 문제(간단 궁합)

- **원인(재현)**: 제출 직후 `requestAnimationFrame`에서 `scrollIntoView`를 불렀는데, 입력 칸이 사라지고 결과로 바뀌며 문서 길이가 달라져 **렌더 전에 실행되면 이전 스크롤 위치(결과 중간)가 그대로 남았다**. 수정 전 빌드로 재현: 390×844 · 390×650 · 320×568 · 844×390 모두 제목이 화면 위로 지나감(스냅샷 "두 사주에서 읽힌 점"이 맨 위).
- **수정**: 결과 컴포넌트가 붙은 **뒤** 한 번만 `scrollIntoView({block:"start"})`(고정 머리글은 `html { scroll-padding-top: 5rem }`가 비켜 줌) + 제목으로 초점 이동(`preventScroll`). 전체 스크롤 초기화 없음. "다시 보기"는 입력 화면이 그려진 뒤 입력 맨 위로.
- **수정 뒤 확인(새 빌드, 4개 화면 크기)**: 결과 제목이 모두 화면 안(`h2` 상단 248px · 256px)에서 시작하고 1.6초 동안 움직이지 않는다. 추가 시나리오: Enter 제출 ✔ · 키보드로 줄어든 화면(420px)에서 제출 후 844px 복원 ✔ · 결과 → 다시 보기(입력이 비워지고 입력 맨 위) → 다시 입력해 재제출 ✔ · 결과 → 다른 화면 → 뒤로 가기(탭 임시 보관 입력이 복원되고 억지 이동 없음) ✔.
- 하지 못한 것: 실제 iPhone · Android 기기의 소프트 키보드와 주소창 높이 변화(창 크기 모의만 했다).

## 6. 하지 못한 것 · 알려진 한계

- **실제 AI로 이 지시문(0.7 / 0.5)의 글을 한 번도 읽지 못했다.** 모의 글이 검사를 통과해도 실제 AI가 같은 서술을 하는지는 모른다. 실제 AI 검증은 별도 승인을 받는다.
- 제품 검사는 낱말 · 표지를 센 어림이라 A→B/B→A 방향 · 근거 밖의 감정 서술 · 추상 풀이는 못 잡는다(위 오류 2건이 그 예). 실제 글에서는 `real-ai-evaluation-rubric.md`의 사람이 읽는 평가를 써야 한다.
- 사이별 장면 문장(60개)은 설계한 고정 문구라 **같은 신호 · 같은 사이는 같은 문장**이다(결정론). "같은 사이라고 늘 같은 글"을 피하는 범위는 신호 조합이 다른 쌍 사이까지다.
- 지시문 최악 비용: 사주 656.04원(상한 656.30) · 리포트 693.04원(상한 701.40) — 여유가 0.26 · 8.36원뿐이라 지시문을 더 늘리려면 재승인이 필요하다.
- 판매 게이트(사주 궁합 · 리포트 궁합)는 열지 않았다.
