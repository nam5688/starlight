# 결제 새 진단 증거 정리 — 결제 화면 빈 화면 vs 가맹점 조회 오류, 키 구성 점검(읽기 전용) (2026-10-20)

> 이 문서는 **근거와 점검 방법만 정리한 것이다.** 원인을 확정하지 않았고, 키를 교체하지 않았고, 판매 게이트를 바꾸지 않았고, 토스 · 외부 결제 API를 호출하지 않았다(이 개발 환경에서). 키 값은 어디에도 적지 않는다.
> 운영자 보고(2026-10-20, 이 세션이 직접 본 값이 아니다): miutest `/admin`에서 배포 `6b913f2` 확인 · 새 주문 `MEU-20261020-49KY6VJJVB`의 `checkout.widget` 알림은 `render · CLIENT_TIMEOUT`(10:07:30) · 이전 주문 `…7B94PJTNMS`는 `reconcile.error NOT_FOUND_MERCHANT`가 10/19부터 반복되고 오늘 10:06:01에도 발생 · 승인 0 · 환불 0 · 오늘 AI 0.

## 1. 두 증상은 서로 다른 곳에서 난다 — 먼저 구분한다

| | ① 결제 화면(카드 UI)이 비어 있다 | ② 가맹점 조회 오류 |
| --- | --- | --- |
| 알림 이름 | `checkout.widget` (단계 `render` · 코드 `CLIENT_TIMEOUT`) | `reconcile.error` (코드 `NOT_FOUND_MERCHANT`) |
| 어디서 | **브라우저**(고객 화면) | **서버**(정기 점검 · 결제 재확인) |
| 쓰는 키 | 클라이언트 키(`NEXT_PUBLIC_TOSS_CLIENT_KEY`, `*_gck_`) + 토스 SDK + 토스가 그리는 iframe | **시크릿 키**(`TOSS_SECRET_KEY`, `*_gsk_`)로 토스 결제 조회 API |
| 대상 주문 | 새 주문 `49KY6VJJVB` (결제 시작 전) | 이전 주문 `7B94PJTNMS` (결제 대기 상태로 남음) |
| 코드의 주인 | `CLIENT_TIMEOUT`은 **토스의 오류 코드가 아니라 우리 코드**(`lib/commerce/widget-session.ts`, 30초 안에 준비되지 않으면 우리가 멈추는 시계) | `NOT_FOUND_MERCHANT`는 **토스 API가 돌려준 코드**(404) |
| 결제와의 관계 | 화면이 안 열려 결제를 시작하지 못했다(승인 0) | 결제는 없었고, 우리 서버가 "이 주문의 결제가 있나" 물을 때 결제사가 가맹점 단위로 못 찾겠다고 답한다 |

두 증상은 **키 세트의 문제로 한꺼번에 설명될 수도 있지만**, 같은 원인이라는 증거는 아직 없다. 하나를 고쳐도 다른 하나가 남을 수 있어 따로 확인한다.

## 2. 확인된 사실 (코드 · 토스 공식 문서에서 읽은 것)

**① 결제 화면 — 우리 코드에서 읽은 것**
- 준비 순서는 `sdk`(토스 스크립트 불러오기) → `init`(`widgets({customerKey})`) → `amount`(`setAmount`) → `render`(결제수단 · 약관 화면 그리기)다. `render · CLIENT_TIMEOUT`은 **앞의 세 단계가 오류 없이 끝났고**, 결제수단 · 약관 iframe이 30초 안에 준비되지 않았다는 뜻이다(`startWidgetSession`).
  - 그래서 "스크립트를 아예 못 불러왔다"(단계 `sdk` · `SDK_LOAD_FAILED`)는 아니다. 다만 **클라이언트 키가 올바르다는 증거도 아니다** — `widgets()`는 키를 그 자리에서 검증하지 않을 수 있고(이 세션은 토스 서버와 통신하지 않아 확인하지 못했다), 토스 화면 설정은 `render` 때 가져오는 것으로 보인다.
  - 토스의 자체 오류(`INVALID_CLIENT_KEY` · `INVALID_VARIANT_KEY` 등)가 아니라 **우리 30초 시계**가 먼저 울렸다 = 토스 쪽에서 구분된 오류가 오지 않았다.
- 응답 헤더에 CSP가 없고 `Permissions-Policy`는 카메라 · 마이크 · 위치만 막는다(`next.config.ts`) — **우리 헤더가 토스 iframe을 막는 구조는 아니다.**
- 키 모양 검사: 서버는 테스트 모드에서 `test_gck_` / `test_gsk_`만 받는다(`server/env.ts`). 운영자 PC의 키는 이 모양이고 LIVE false였다(운영자 보고).
- 알림 하나에 남는 값: 단계 · 코드 · 걸린 시간 · 시도 횟수 · 브라우저 종류 · 보안 연결 · 저장소/쿠키 사용 가능 여부 · 결제 칸 개수 · 화면 보임 여부(`visible`/`hidden`) · 최상위 창 여부. **알림 본문의 이 값들로 "자동 브라우저 문제 vs 실제 환경 문제"를 가를 수 있다**(5장).

**② 가맹점 조회 오류 — 우리 코드 · 토스 문서에서 읽은 것**
- 결제 대기 주문의 재확인은 `GET /v1/payments/orders/{주문번호}`를 **현재 서버의 시크릿 키**로 호출한다(`lib/integrations/tosspayments/gateway.ts` · `reconcile-service.ts`). 결제사가 `NOT_FOUND_PAYMENT`(결제 없음)이면 일정 시간 뒤 "결제 미완료"로 정리하지만 **그 밖의 코드는 오류로만 알리고 주문을 그대로 둔다**(`reconcile-service.ts`) — 그래서 이 주문은 정리되지 않고 정기 점검마다 같은 오류가 반복된다(운영 알림은 같은 주문 · 같은 종류를 6시간에 한 번만 보낸다 — `lib/ops/alerts.ts`의 `ALERT_DEDUPE_MS` — 그래서 알림은 6시간 간격으로 다시 온다, `server/reconcile.ts`). 이것은 의도한 안전한 동작이다(알 수 없는 오류로 주문을 닫지 않는다).
- 토스 공식 오류 목록(`docs.tosspayments.com/reference/error-codes`, 2026-10-20 읽음): `NOT_FOUND_MERCHANT` = 404 "존재하지 않는 상점 정보 입니다." — 이 코드는 **"전체 에러 목록"과 계좌 프로모션 조회에만 나열돼 있고, 결제 조회 · 승인 · 취소 문서에는 `NOT_FOUND_PAYMENT`("존재하지 않는 결제 정보 입니다.")만 나열돼 있다.** 즉 이번 조회는 문서가 말하는 "결제가 없다"가 아니라 **가맹점(상점) 단위로 찾지 못했다**는 응답이다.
- 같은 문서의 다른 키 오류: `UNAUTHORIZED_KEY`(401, 인증되지 않은 시크릿 키 · 클라이언트 키) · `INVALID_API_KEY`(400, 잘못된 시크릿키 연동 정보) · `INVALID_CLIENT_KEY`(400) · `API_KEY_ACCESS_DENIED`(403, 허용 IP 정책). **지금 보인 것은 이 중 `NOT_FOUND_MERCHANT`뿐**이다 — 키 모양이 틀렸을 때의 `UNAUTHORIZED_KEY` · `INVALID_API_KEY`가 아니다. (`NOT_FOUND_MERCHANT`가 어떤 조건에서 결제 조회에 돌아오는지는 공식 문서에 없어 이 세션은 모른다.)
- 키 짝 규칙(토스 API 키 안내, 같은 날 읽음): "클라이언트 키와 시크릿 키는 항상 '세트'로 묶여 있고, 한 세트로 써야 돼요." 테스트 키와 라이브 키를 섞으면 `INVALID_API_KEY`, 다른 MID(상점아이디)의 키를 짝으로 써도 맞지 않는다. 결제위젯 연동 키(`gck`/`gsk`)와 API 개별 연동 키(`ck`/`sk`)는 별개 세트다. 문서의 예제 테스트 키는 로그인하면 "내 개발 연동 체험 상점 키"로 바뀐다고 안내한다(신청 전에는 체험 상점의 일부 테스트 키만 보인다).
- 우리 앱이 이미 구분해 두는 것: 토스 문서 예제용 공용 키(`test_gck_docs_…` · `test_gsk_docs_…`)를 쓰면 주문의 결제 환경이 `test-docs`("테스트 결제 · 공용 예제 키")로 저장되고 주문 상세에 안내가 뜬다(`server/env.ts`의 `paymentEnvOf` · `server/setup-checks.ts`의 `isTossDocsKey`). 이 값은 **주문을 만들던 순간의 키 구성**이다.

## 3. 가능한 원인 후보 — 모두 미확인, 각 후보가 맞다면 보일 모습

| 후보 | ① 결제 화면 | ② 가맹점 조회 | 가르는 방법(읽기 전용) |
| --- | --- | --- | --- |
| A. 클라이언트 키와 시크릿 키가 **서로 다른 세트(다른 상점)** | 토스 화면 설정을 못 가져와 render가 끝나지 않을 수 있음 | 시크릿 키의 상점에서 이 주문을 못 찾음 | 4장 ① · ③ (두 키의 같은 세트 확인) |
| B. 시크릿 키가 **실제 상점에 묶이지 않은 키**(체험 · 공용 · 만료/삭제된 상점 등) | (클라이언트 키 쪽은 별개일 수 있음) | `NOT_FOUND_MERCHANT`(상점 정보 없음)와 가장 잘 맞는 후보 | 4장 ① · ③ |
| C. 주문을 만든 때와 **지금의 키 구성이 다르다**(키를 바꾼 뒤 이전 주문을 조회) | 새 주문은 무관 | 이전 주문 `7B94PJTNMS`만 반복되는 것과 맞음(새 주문 `49KY…`에서도 같은 오류가 나는지가 갈림) | 4장 ② (두 주문의 결제 환경 비교) |
| D. 결제위젯 상점 설정(결제 UI `variantKey` · 결제수단 · 위젯 사용 상태)이 비어 있음 | `render`가 끝나지 않거나 토스가 `INVALID_VARIANT_KEY` | 무관(별개) | 4장 ③ · 토스 개발자센터의 결제위젯 설정 화면 |
| E. 브라우저/자동화 환경(응답을 붙잡는 자동 브라우저 · 앱 안 브라우저 · 광고 차단 · 회사망) | iframe이 `about:blank`로 남다 우리 시계가 울림 — 운영자가 본 모습과 같다 | 무관 | 5장(알림 본문의 환경 값 · 실제 휴대폰 비교) |
| F. 허용 IP 정책(`API_KEY_ACCESS_DENIED`) | 무관 | 코드가 다르다(403) | 지금 증상과 맞지 않는다 — 후보에서 낮게 본다 |

**두 증상이 모두 키 세트에서 나온다면 후보 A 또는 B가 하나로 설명하지만**, ①이 E(환경)에서 난 것일 수도 있어 ②와 분리해서 본다. 후보 순위는 정하지 않는다(증거가 부족하다).

## 4. 읽기 전용 점검 순서 (운영자 · root가 직접, 키 값은 어디에도 출력하지 않는다)

1. **앱 안에서(비용 · 변경 없음) — 두 주문의 결제 환경을 비교한다.** MY → 결제내역 → 각 주문 상세, 또는 `/admin`의 최근 주문 목록에서 `7B94PJTNMS`와 `49KY6VJJVB`의 **결제 환경 표시**("테스트 결제" vs "테스트 결제 · 공용 예제 키")를 본다.
   - 둘이 **다르면** 그 사이에 키 구성이 바뀐 것이다(후보 C 강화) — 이전 주문은 이전 키로 만든 주문이라 지금 시크릿 키로 조회되지 않을 수 있다.
   - 둘 다 "공용 예제 키"이면 공용 예제 키를 쓰고 있다(후보 B와 맞음 — 공용 키는 내 상점 관리자에 결제내역이 보이지 않는다고 앱도 안내한다).
2. **Vercel 환경변수(읽기만).** Project → Settings → Environment Variables에서 **값을 펼치지 않고** 확인한다.
   - 이름 두 개(`NEXT_PUBLIC_TOSS_CLIENT_KEY` · `TOSS_SECRET_KEY`)가 **Production 환경(miutest의 Production 브랜치)** 에 둘 다 있는지, 각각의 **마지막 수정 시각**이 같은 때인지(둘 중 하나만 바꿨다면 짝이 어긋났을 가능성) 본다.
   - 접두어만 눈으로 확인한다: 클라이언트 키는 `test_gck_`, 시크릿 키는 `test_gsk_`로 시작하는지, 그리고 **둘 다 `docs_`가 들어간 공용 예제 키(`test_gck_docs_…` · `test_gsk_docs_…`)가 아닌지**. 값 전체를 복사해 채팅 · 문서 · 알림에 붙이지 않는다.
   - 환경변수를 바꾼 뒤에는 **새 배포가 있어야 서버가 새 값을 읽는다**(서버는 요청 때 읽지만 배포 환경에서는 변경 후 재배포가 필요하다). 마지막 수정 시각과 배포 시각을 비교한다. (클라이언트 키는 서버가 화면에 건네므로 브라우저에 박혀 있는 옛 값이 따로 남지는 않는다 — `app/checkout`이 서버에서 읽은 값을 전달한다.)
3. **토스 개발자센터(읽기만).** 로그인 → 사용 중인 **상점(MID)** 선택 → API 키 메뉴의 **결제위젯 연동 키** 한 세트의 클라이언트 키 · 시크릿 키를 Vercel 값과 **끝 4글자만** 눈으로 대조한다(둘이 같은 세트인지). 결제위젯 설정 화면에서 **결제 UI(`DEFAULT` 등 `TOSS_WIDGET_VARIANT_KEY`와 같은 이름)가 게시돼 있는지 · 카드 결제수단이 켜져 있는지**도 본다. 값을 바꾸지 않는다.
4. **(운영자 PC에서만, 선택) 시크릿 키 한 세트가 상점에 묶여 있는지 읽기 전용 조회 한 번.** 이 개발 환경은 외부 결제 API를 부르지 않는다. 운영자가 원하면 자기 PC에서 환경변수에 시크릿 키를 담아 **`GET https://api.tosspayments.com/v1/payments/orders/<임의의 존재하지 않는 주문번호>`를 한 번** 보고 응답의 `code`만 읽는다(키는 출력 · 기록하지 않는다). `NOT_FOUND_PAYMENT`이면 키가 상점에 묶여 조회가 정상 동작하는 것이고, `NOT_FOUND_MERCHANT`이면 그 시크릿 키 자체가 상점에 묶이지 않은 것(후보 B)이다. 이 조회는 결제 · 환불을 일으키지 않지만 **외부 호출이므로 운영자가 직접 판단해서 하고, 개발 세션은 하지 않는다.**

## 5. ① 결제 화면만 따로 가르는 방법 (키와 무관한 환경 요인 분리)

- **알림 본문**(`/admin` 알림 목록 · 텔레그램)에 `브라우저 · 보안 연결 · 저장소 · 쿠키 · 결제 칸 N개 · 화면 보임 · 최상위 창` 값이 있다. `결제 칸`이 2 이상이면 옛 칸 id 충돌(이미 고침), `화면 보임`이 `hidden`이면 눈에 보이지 않는 탭에서 열린 것, `최상위 창`이 `아니요`이면 다른 화면 안에 들어 있는 것이다. **자동 브라우저(CDP)로 연 화면이면 응답을 붙잡아 두는 자동화 설정(document-response pause)이 iframe을 `about:blank`로 남길 수 있다 — 운영자가 이 가능성을 이미 의심했고, 이 세션도 단정하지 않는다.**
- **실제 휴대폰(일반 Safari · Chrome)에서 같은 주문 화면을 열어** 카드 선택 화면이 뜨는지 본다(운영자 확인 중). 뜨면 키 세트 · 위젯 설정은 일단 작동하는 것이고 ①은 자동 브라우저 환경 요인이다. 안 뜨면 같은 알림이 휴대폰에서도 오는지 보고(알림 본문에 `브라우저`가 휴대폰 브라우저로 남는다), 3장 후보 A · B · D를 4장으로 가른다.
- **결과가 갈리는 방식**: ①이 휴대폰에서 정상이고 ②만 계속되면 ②는 시크릿 키 · 이전 주문 문제로 따로 처리한다. ①이 휴대폰에서도 같으면 키 세트(A) 또는 위젯 설정(D)을 먼저 본다.
