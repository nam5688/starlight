# 미유캐시 — 구현된 동작(가안)과 운영자가 정할 것

- 상태: **기능은 구현됨, 가격 · 정책은 모두 가안.** 운영자 방향(2026-10-15): *질문 한 번에 3캐시 · 10개 단위 충전 · 많이 충전하면 보너스 · 충전 화면 + 결제 연동.* 아래 수치는 제안이며 확정 전에는 화면에 "가안"으로 표시한다.
- 코드: `lib/config/product.ts`(`MIYU_CASH` — 값은 여기 한 곳) · `lib/commerce/cash.ts`(견적 · 보너스 계산) · `lib/services/cash-service.ts`(충전 주문 시작 · 지갑 조회) · `supabase/migrations/20261023000000_miyu_cash.sql`(13번 DB 변경) · `app/cash/`(충전 화면 · 서버 동작) · `components/cash/`
- **실제 결제(토스 실결제)는 켜지 않았다.** 검증은 가짜 결제사 · 가짜 Supabase 환경에서만 했다(7절).

## 1. 지금 동작하는 방식

1. 회원이 `/cash`에서 충전 개수를 고른다(빠른 선택 5개 또는 직접 입력, 10캐시 단위, 10~500캐시).
2. 서버가 **개수로 금액 · 보너스를 계산**해 주문을 만든다(상품 번호 `cash-charge:<캐시>:<보너스>:<임의번호>`). 브라우저가 보낸 금액은 쓰지 않는다.
3. 기존 결제 흐름(`/checkout/<주문번호>` → 토스 결제창 → 서버 승인 확인)을 그대로 쓴다.
4. **서버가 결제 승인을 확인해 주문이 "결제 완료"가 되는 같은 처리 안에서 DB 트리거(`orders_cash_change`)가 지갑에 캐시를 넣는다.** 성공 주소로 이동했다는 것만으로는 들어가지 않는다. 같은 승인을 다시 처리해도 한 번만 들어간다.
5. 질문 한 번에 3캐시가 쓰인다(`spend_cash`) — 답을 받지 못하면(호출 실패 · 검사에 걸림) 되돌린다(`restore_cash_spend`).
6. 결제가 취소(환불)되면 그 주문으로 들어온 캐시(보너스 포함)를 **지갑에 남은 만큼 회수**한다. 이미 쓴 만큼은 음수로 만들지 않고 "회수하지 못한 몫(shortfall)"으로 기록해 운영자가 확인한다.

- 충전 주문은 **리포트를 만들지 않는다**(대기열 · 생성 · 다시 만들기 모두 막음). MY의 리포트 목록에도 끼지 않고 결제내역에만 "미유캐시 N개 충전"으로 남는다.
- 충전 주문은 본인의 검사 결과 하나에 붙는다(주문 표가 검사 결과 번호를 요구해서). 충전한 캐시는 결과와 무관하게 회원 지갑에 쌓인다. 검사 결과가 하나도 없는 회원은 먼저 무료 분석을 해야 충전할 수 있다.
- **13번 DB 변경 전에는 충전을 막는다**(지갑이 없으면 결제가 승인돼도 캐시를 넣을 수 없어 돈만 빠진다). 화면은 "충전을 준비하고 있어요"로 밝히고 주문도 만들지 않는다.
- 새 구매를 받지 않는 상태(AI 용량 · 하루 예산)에서는 충전도 받지 않는다 — 질문을 이어 갈 수 없는 때 미리 받지 않는다.
- 지갑 · 내역은 본인만 조회할 수 있고(RLS) 쓰기는 DB 함수 · 트리거만 한다. 내역은 고치거나 지울 수 없다(쌓기만). 내역에는 질문 · 답 내용이 없다.
- 회원 탈퇴: **잔액이 남아 있으면 탈퇴를 막는다**(안내). 지갑 · 내역은 주문 · 결제 기록처럼 거래 기록으로 남는다.

## 2. 가안 값 (한 곳 — `MIYU_CASH`)

| 항목 | 가안 | 근거 / 메모 |
| --- | --- | --- |
| 1캐시 | 100원 | 질문 한 번 = 3캐시 = 300원. 채팅 한 번 호출 비용 어림(약 17원, 시험 4건 기준)과 결제 수수료 · 운영비를 넘기는 폭을 둔 제안 |
| 충전 단위 · 범위 | 10캐시 단위(1,000원), 10~500캐시(1,000~50,000원) | |
| 보너스 | 50캐시 이상 10% · 100캐시 이상 15% · 300캐시 이상 20% (소수점 버림) | 가장 높은 구간 하나만. 보너스 캐시도 질문에 똑같이 쓰인다 |
| 빠른 선택 | 10 · 30 · 50 · 100 · 300캐시 | |
| 질문 글자 수 | 무료 500자 · 유료(캐시 · 리포트 구매) 1,000자 | 운영자 확정(2026-10-15) |

## 3. 운영자가 정해야 하는 것

| # | 결정 | 지금(가안) | 고려할 점 |
| --- | --- | --- | --- |
| 1 | **환불 기준** | 정하지 않음. 결제가 취소되면 지갑에서 회수만 한다 | 쓰지 않은 캐시의 환불 가능 여부 · 기간(청약철회와의 관계) · 환불 시 보너스 처리. **법률 검토 필요.** 환불은 미유가 실행하지 않고 토스 관리자에서 취소한다 |
| 2 | **유효기간** | 없음(지갑에 계속 남는다) | 선불 충전금의 유효기간 · 소멸 안내는 법령 · 약관상 기준이 있을 수 있다. 정하면 새 마이그레이션 + 정기 작업 |
| 3 | **보너스의 환불 · 회수** | 결제 취소 시 보너스도 회수 | 이미 쓴 몫은 shortfall로 기록(자동으로 고치지 않음) |
| 4 | **가격 · 보너스 구간** | 2절의 가안 | 질문 한 번의 실제 AI 비용을 더 모은 뒤 조정. 바꿀 때는 `MIYU_CASH`만 고친다 |
| 5 | **회계 · 세무** | 충전 매출은 리포트 매출과 따로 센다(관리자 지표) | 선불 충전 매출을 언제 매출로 인식할지는 세무 확인 전 |
| 6 | **탈퇴 시 잔액** | 잔액이 있으면 탈퇴를 막는다 | 환불 기준(1번)이 정해지면 "환불 후 탈퇴" 안내를 정한다 |
| 7 | **약관 · 처리방침 문구** | 초안에 한 줄씩 추가(미유캐시 · 다시 받기) | 정책 확정 뒤 구체 문구로 교체. 확정하면 `MIYU_CASH.policyDecided`를 true로 바꾸고 충전 화면의 "아직 정해지지 않았어요" 문구를 정책에 맞게 고친다 |
| 8 | **미성년** | 가입은 만 14세 이상 | 미성년 결제 · 법정대리인 동의 기준 확인 |

## 4. DB 적용 (13번)

- 파일: `supabase/migrations/20261023000000_miyu_cash.sql` — 더하기만 한다(지갑 · 내역 표, 함수 3개, 주문 트리거, 탈퇴 함수 교체). 기존 검사 · 회원 · 주문 · 결제 데이터를 지우거나 바꾸지 않는다.
- 적용 이력 확인: `supabase/check-migrations.sql`(13번 행) · 충전 · 지갑 점검: `supabase/check-cash.sql`(읽기 전용 — 지갑 합계와 내역 합계가 어긋난 회원, 결제 완료인데 들어가지 않은 충전, 회수하지 못한 몫).
- **순서**: 새 코드를 먼저 올려도 안전하다(13번 전에는 충전과 캐시 질문이 막혀 있다). 13번을 적용한 뒤부터 충전 화면이 열린다.

## 5. 운영 중 확인

- `/admin/metrics`: "미유캐시 충전(별도)" 줄 — 리포트 매출 · 한 건당 계산에는 넣지 않는다.
- 결제 완료 · 환불 알림(텔레그램)에는 "미유캐시 N개 충전"으로 나온다.
- 환불이 발생하면 `check-cash.sql`로 회수하지 못한 몫이 있는지 본다.

## 6. 만들지 않은 것

- 캐시 선물 · 양도, 자동 충전, 정기 결제, 캐시로 리포트 구매. (모두 별도 결정 후)
- 캐시 사용 내역의 질문 · 답 내용(저장하지 않는다).

## 7. 확인한 것 · 못 한 것

- 확인함: 단위 테스트(견적 · 보너스, 충전 주문, 승인 전 지갑 비어 있음, 두 번 승인해도 한 번만 충전, 금액 불일치 거부, 환불 회수와 shortfall, 지갑 표 없는 DB, 리포트 미생성, 지표 분리, 질문 차감 · 복구) · 실제 DB(로컬 Postgres) 위의 DB 테스트 · 가짜 토스 결제 흐름 브라우저 시험.
- **못 함**: 실제 Supabase 호스팅 · 실제 토스 결제(테스트 키 포함)에서의 확인, 환불을 토스 관리자에서 실행한 뒤 회수되는지.
