# 스테이징 통합 시험 계획 (2026-10-17)

> **운영 DB · 실결제 · 공개 배포 · 실제 보상 지급 없이** 별도의 시험 환경에서 아래 흐름을 처음부터 끝까지 확인하는 계획이다. 운영자 지시(2026-10-17): DB 19~23(지금은 25)의 운영 적용은 승인하지 않았으며, 가입 · 추천 · 포인트 · 쿠폰 · 0원 주문 · 질문권 · 사주 궁합 · 환불을 스테이징에서 먼저 통합 시험한다.
> **지금까지 한 것은 개발용 임시 DB(로컬 Postgres) + 가짜 결제사 + 모의 AI까지다.** 스테이징(실제 Supabase 프로젝트 · 토스 테스트 키 · 실제 메일)에서는 아직 한 번도 돌리지 않았다 — 아래 "스테이징에서 직접 확인" 칸이 그 몫이다.

## 1. 환경 (모두 운영과 분리)

| 항목 | 값 |
| --- | --- |
| Supabase | **스테이징용 새 프로젝트**(운영 프로젝트가 아니다). 마이그레이션 1~25번을 `docs/db-rollout-19-25.md` 순서로 적용하고 `check-migrations.sql`이 모두 "적용됨" |
| 앱 | Vercel **Preview** 배포(Production 아님) 또는 운영자 PC의 `npm run dev` — 스테이징 Supabase 키를 `.env.local`에만 둔다 |
| 결제 | 토스 **테스트 키**(`test_gck_` · `test_gsk_`) · `PAYMENTS_LIVE_MODE=false`. 실결제 키를 넣지 않는다. 실제 카드 승인은 일어나지 않는다 |
| AI | 기본은 로컬 가짜 AI(`AI_PROVIDER=mock-local`) 또는 개발용 규칙 생성기. **실제 AI는 `docs/real-ai-approval-proposal.md`의 승인 뒤에만** |

| 시험 계정 | 시험용 이메일 계정 3~4개(A · B · C · 관리자). 실제 고객 정보 · 실제 연락처를 쓰지 않는다 |

## 2. 시험 순서와 기대 결과

각 줄: **자동 시험이 이미 확인한 것**(로컬 임시 DB · 가짜 결제사 · 모의 AI)과 **스테이징에서 직접 확인할 것**을 나눈다. 자동 시험의 통과는 스테이징 통과가 아니다.

## 3. 통과 기준

- 위 12줄 모두 "스테이징에서 직접 확인" 칸이 **통과**이거나, 통과하지 못한 사유 · 오류번호 · 재현 방법이 기록돼 있다.
- 돈이 오가는 줄(2 · 4 · 6 · 7 · 8)은 **주문 상태 · 결제사 기록 · 질문권 · 포인트 장부가 서로 일치**한다(관리자 주문 조회 · 결제 대조 · `check-payments.sql`).
- **새 구매를 막는 것은 있어도 이미 결제한 고객의 리포트를 막는 것은 없다.**
- 시험이 끝나면 모든 혜택 스위치 · 판매 스위치를 끈다(판매 스위치는 코드 상수이므로 `MIYU_TEST_OPEN_SALES`를 지운다).

## 4. 보고 형식 (시험한 사람이 채팅에 붙이는 것)

줄 번호별: 통과 / 실패 + 한 줄 사유 · 실패는 오류번호(`ERR-XXXXXXXX`)와 시각 · 사용한 시험 계정(이메일 앞부분) · 결제 테스트 주문번호. **키 · 비밀번호 · 고객 개인정보는 붙이지 않는다.**

## 5. 이 계획이 하지 않는 것

- 운영 DB 적용 · 실결제 · 환불 실행 · 공개 배포 · 실제 보상 지급.
- 실제 휴대폰 · 카카오톡 인앱 브라우저 확인은 따로 한다(`launch-checklist.md` 모바일 사용성 줄).
- 부하 시험 · 보안 침투 시험 · 법률 검토.
