## 2. 월 구독료와 API 비용은 다르다

| | 월 구독 (ChatGPT Plus · Claude Pro 등) | API (미유 서버가 쓰는 것) |
| --- | --- | --- |
| 무엇인가 | 사람이 앱 · 웹에서 대화하는 **이용권** | 프로그램이 호출하는 **종량제** (쓴 토큰만큼) |
| 미유에 쓸 수 있나 | **쓸 수 없다** (구독이 있어도 API 호출은 별도) | 쓴다 |
| 가입 | 이미 있어도 무관 | **별도 API 계정**, 결제수단 등록 또는 선불 충전, 키 발급 |

- 선불 충전에는 회사별 **최소 금액**이 있을 수 있다. **실제로 쓰는 금액은 승인한 한도 안이지만 충전 금액은 그보다 클 수 있다** — 가입 화면에서 확인하고 필요 이상으로 충전하지 않는다.
- 두 회사 콘솔에서 **월 사용 한도(spend limit)** 를 걸어 두는 것을 권한다 (미유 쪽 하드스톱과 별도의 이중 안전장치).

## 3. 비용 다시 계산 (토큰 · 재시도 · 환율 가정 포함)

계산은 `node scripts/compare-ai-dry-run.ts`로 다시 할 수 있다 (AI를 부르지 않는다). 아래는 2026-10-12 실행 결과다.

**가정**
- 환율 **1,600원/달러**(2026-10 실제 환율 미확인) · 부가세 등 여유율 **10%**.
- 입력 토큰: 글자마다 한글 등은 **2토큰**, 영문 · 숫자 · 기호는 0.5토큰, 메시지마다 64토큰으로 **보수적으로 크게** 잡는다. 실제 토큰 수는 회사마다 다르다. **1단계의 첫 호출 사용량으로 이 추정을 보정**한다(실제 ÷ 추정을 기록).

## 4. 총예산을 넘기기 전에 호출을 멈추는 방법 (구현 · 검사 완료)

코드: `lib/report/ai/budget.ts`(예산 관리) · `compare-plan.ts`(단계 실행기) · `compare-personas.ts`(가상 인물). 실제 AI 없이 가짜 모델로 모두 검사한다 (`budget.test.ts` 11개 · `compare-plan.test.ts` 10개).

1. **호출 전 예약:** 모든 호출은 먼저 `(입력 추정 × 입력 단가 + 최대 출력 × 출력 단가) × 환율 × 여유율`의 **최악 비용**을 예약한다. `이미 쓴 비용 + 진행 중인 예약 + 이번 최악 > 한도`이면 **제공사에 요청을 보내지 않고** 거절한다 (제공사를 부르지 않으므로 청구되지 않는다).
2. **호출 후 정산:** 실제 사용량(usage)으로 바꿔 기록한다. **사용량을 모르면**(응답에 없음 · 시간 초과 · 알 수 없는 오류) 예약한 **최악 비용을 그대로** 쓴다. 속도 제한 · 인증 오류처럼 제공사의 생성에 닿지 않았다고 보증된 오류만 0원이다.
3. **동시 호출도 포함:** 진행 중인 호출의 예약이 한도에 들어가므로 동시에 여러 건을 보내도 합이 한도를 넘지 않는다.
4. **추정이 틀리면 전체 멈춤:** 실제 비용이 예약한 최악보다 크면(입력 토큰 추정이 모자랐다는 뜻) 이후 모든 호출을 멈춘다.
5. **회사별 한도**를 따로 걸 수 있다 (한 회사가 전체 예산을 다 쓰지 못하게).
6. **단계 승인 기록 없이는 실행하지 않는다:** 승인한 단계 · 금액이 실행할 단계 · 한도와 맞지 않거나, 예산 관리기의 한도가 승인 금액보다 크면 모델을 한 번도 부르지 않고 멈춘다.
7. 무작위 5,000회 호출 · 정산에서도 `정산 + 예약 ≤ 한도`가 항상 지켜지는지 검사한다.

이 한도는 **가정한 환율 · 추정 토큰**에 기대므로 실제 청구와 다를 수 있다. 그래서 회사 콘솔의 월 사용 한도(2장)를 이중 안전장치로 건다.

## 5. 단계별 승인 — 소수 샘플부터

### 1단계 — 가상 인물 2명 × 후보 2개 = 생성 4건 (한도 3,000원)

- 인물: 2명은 일간이 다르고, 한 명은 "내 고민 자세히 알려주기"가 있고(적은 고민 반영 경로), 한 명은 없다. 실제 고객 정보는 쓰지 않는다. 이름 · 생년월일 원문은 AI에 보내지 않는 제품 방식 그대로다.
- 보는 것: ① 첫 시도 형식 통과 · 재시도 후 통과 ② 지어낸 사건 · 날짜 · 직업 · 나이 0건 ③ 실제 입력 · 출력 토큰(추정 보정) ④ 건당 비용 ⑤ 응답 시간 ⑥ **내용 차이 검사** 결과 ⑦ 두 인물의 글이 서로 얼마나 같은 말인가 ⑧ 읽어 본 첫인상.
- **4건으로는 순위를 정하지 않는다.** 후보 사이의 우열이 아니라 "작동하는가 · 비용이 예상대로인가 · 명백한 결함이 있는가"만 본다.
- 명백한 결함(지어낸 사건 · 날짜 1건 이상, 형식을 거의 못 지킴 등)이 있으면 그 후보는 지시문을 고쳐 다시 확인한다 (추가 비용은 새로 요청).

### 2단계 — 가상 인물 10명 × 후보 2개 = 생성 20건 (한도 8,000원, 1단계 결과를 보고 따로 승인)

- 일간 10종 · 성별 · 태어난 시각 있음/모름 · 내 고민 자세히 알려주기 있음(4명)/없음(6명) · 응답 패턴이 섞인 10명.
- 20개 글을 A/B 이름 없이 섞어 운영자가 채점한다 (6장).
- 둘 다 기준에 못 미치면: 지시문 개선 → 재확인(추가 비용은 새로 요청) → 그래도 안 되면 판매를 미룬다. 최상위 등급 확인은 **별도로 승인을 요청한다.**

## 6. 평가 방법과 합격 기준 (결과를 보기 전에 고정)

**자동 측정:** 첫 시도 형식 통과율 · 재시도 후 통과율 · 금지 표현 위반 수 · 근거 ID 오류 수 · 글자 수(보고만) · 응답 시간 · 입력/출력 토큰 · 건당 비용.

**내용 차이 검사** (`lib/report/v2/depth.ts`, 길이는 기준이 아니다)

| 검사 | 기준 | 거르는 것 |
| --- | --- | --- |
| 조건 · 상황 | "~할 때는 · ~하면 · 다만" 같은 조건이 있는 문단이 60% 이상 | 조건 없이 단정하는 글 |

**한계:** 낱말 · 표지를 세는 어림이다. 얕은 글을 걸러 낼 수 있어도 좋은 글임을 보증하지 않는다. 사람이 쓴 목표 수준 예시는 통과하고, 모의 모델의 글(근거 문장을 이어 붙인 글)은 통과하지 못한다는 것, 그리고 범용 문장 · 길이 부풀리기 · 약속 누락을 걸러 낸다는 것을 테스트로 확인했다(`depth.test.ts` 8개). 첫 실행에서 목표 예시의 실천 제안 2개가 시간 단서 낱말 목록의 누락(미리 · 오늘 · 내일 · 한 문장)으로 걸려 **낱말 목록만 넓혔고 통과 기준은 바꾸지 않았다.** "구체적인가 · 새로 알게 됐나 · 읽을 만한가"는 사람이 가려 읽고 판단한다.

**블라인드 평가 (운영자):** 인물마다 두 후보의 글을 X · Y로 섞어 1~5점. 사람이 쓴 목표 수준 예시도 같은 채점표로 본다. 사용자가 적은 고민을 사주로 알아맞힌 것처럼 쓴 문장이 있는지도 따로 본다 (제품 검사가 막지만 사람이 한 번 더 본다).

| 채점 항목 (5점) | 보는 것 |
| --- | --- |
| 구체성 | 이름을 가려도 이 사람의 이야기로 읽히는가 |
| 조건 · 상황 | "~할 때 / ~하면 / 다만 ~는" 같은 조건 · 예외가 있는가 |
| 근거 일치 | 문단이 단 근거와 내용이 맞는가 |
| 새로 알게 된 것 | 무료 미리보기에서 얻지 못한 것이 있는가 |
| 한국어 자연스러움 | 번역투 · 반복 · 어색한 문장 |
| 구매 판단 | 읽고 나서 9,900원을 낼 만했는가 / 더 알고 싶은가 |

**합격 기준**
- 지어낸 사건 · 날짜 · 직업 · 나이: **0건** (하나라도 있으면 그 후보는 지시문을 고쳐 다시 확인)
- 첫 시도 형식 통과율 80% 이상, 재시도 후 100%
- 내용 차이 검사의 실패 항목 없음 (경고는 사람이 읽고 판단)
- 평가 "새로 알게 된 것"과 "구매 판단" 평균 4.0 이상
- 건당 비용 400원 이하 (고쳐 쓰기 포함 평균)

**이 비교로 알 수 없는 것:** 사주 해석 자체의 정확성(해석 규칙은 전문가 검토 전 초안), 실제 고객의 만족도, 새 자체 문항(적용 전)으로 만든 근거에서의 품질. 이번 입력은 현재 개발용 문항의 5개 관점이다. **글이 더 매끄러워지는 것은 사주 해석이나 성향 검사가 더 정확해졌다는 뜻이 아니다.**

## 8. 승인 요청 — 9장의 미리보기(가상 인물 · 리포트 구성 · 목표 문장)를 운영자가 확인한 뒤 1단계만 요청한다

(이전 운영자 답변: "아직 승인하지 않는다 · 결제하거나 API 키를 발급할 단계가 아니다" — 2026-10-13 운영자가 "미리보기를 확인하고 3,000원 테스트를 승인하겠다"고 했으므로 지금은 승인 직전이다. **승인 기록이 생기기 전에는 아무것도 부르지 않는다.**) **1단계만** 먼저 요청한다.

> 가운데 등급 두 모델(`claude-sonnet-5-5` · `gpt-6.1-sol`)로 가상 인물 2명 × 2 = 생성 4건에 **총 3,000원 한도**의 유료 API 호출을 해도 되는가. 실제 고객 정보는 쓰지 않는다. 키는 대화창에 붙여넣지 않는다.

승인 후 순서 (운영자가 하는 일은 1번뿐):
1. **운영자:** 두 회사 API 계정 만들기 → (최소 충전 금액 확인 후) 소액 충전 → 콘솔에서 월 사용 한도 걸기 → 키 발급 → `.env.local`에만 입력 (단계별로 안내한다. **키는 채팅에 보내지 않는다**).
2. ~~이 시점에야 어댑터를 만든다~~ → **2026-10-13 운영자가 "실행 준비가 끝나면 알려 달라"고 해서 호출 없이 미리 만들었다.** 두 회사의 연결 코드(`lib/integrations/ai/providers.ts`, `TextModel` 약속만 지킴, 새 의존 패키지 없음)와 실행 스크립트(`scripts/run-ai-compare.ts`)가 있고, 가짜 fetch로만 시험했다(호출 0회). 아직 `AI_PROVIDER`(서비스 설정)에는 연결하지 않았다. 스크립트는 **옵션 없이 실행하면 비용 계산만** 하고, 실제 호출은 운영자가 승인 금액 · 날짜를 직접 적어야 시작하며, 키가 없으면 첫 호출 전에 멈춘다. **호출 직전에 아래 8-1의 비용을 한 번 더 보여 준다.**
3. 운영자 PC에서 실행한다 (키는 나에게 보이지 않는다). 결과는 `pilot-data/ai-compare/<단계>-<시각>/`에 X · Y로 가린 글(`blind/`) · 채점표(`evaluation-sheet.md`) · 사람이 쓴 예시(`reference-…md`)로 나오고, 열쇠 파일(`key-open-after-scoring.json`)과 비용 기록(`cost-and-checks.json`, 글 내용 없음)은 따로 둔다. 실행 방법은 [`update-guide.md`](./update-guide.md) 7장.
4. 1단계 결과 보고 → 2단계 승인 여부 판단.

### 8-1. 지금 제품 형식(읽기 구조 `reading-v1`)으로 다시 계산한 1단계 비용 (호출 없음 — `node scripts/compare-ai-dry-run.ts`)

1단계에서 쓰게 하는 지시문은 이제 **지금 제품의 개인 통합 리포트(읽기 구조)** 지시문이다 (`lib/report/reading/prompt.ts`, `reading-v1-prompt-0.1`). 자기 이해 풀이(철학적 풀이 비교용 v0)는 별도 비교 대상으로 남아 있고, `--variant philosophical-v0`로 계산할 수 있다.

| | 값 |

실제 청구는 제공사 콘솔에서 확인한다. 입력 토큰 추정이 실제와 얼마나 달랐는지는 실행 뒤 `cost-and-checks.json`의 `estimateRatio`로 기록된다.

### 8-2. 두 회사 문서로 다시 확인한 결과 (2026-10-13, 유료 호출 없음 — 문서만)

**"공식 문서로 확인"은 문서에 적힌 내용을 읽었다는 뜻이다. 실제 응답이 코드와 한 글자도 다르지 않다는 보증이 아니며, 그것은 첫 승인 호출에서 확인한다.**

| 항목 | Anthropic Claude Sonnet 5.5 | OpenAI gpt-6.1-sol |
| --- | --- | --- |
| 모델 ID | `claude-sonnet-5-5` — 모델 개요 표의 "Claude API ID"로 확인 | `gpt-6.1-sol` — 모델 문서로 확인 |
| 가격 (100만 토큰) | 입력 $2 · 출력 $10 (가격표 · 모델 개요). 1M 컨텍스트 전체가 기본 가격 | 입력 $2 · 출력 $10 (272K 입력 이하). 272K 초과는 입력 2배 · 출력 1.5배 — 우리 입력은 약 1.5만 토큰이라 해당 없음 |
| 생각 · 추론 토큰 | 출력으로 과금되고 `max_tokens`에 합산(생각 문서) | `max_output_tokens`에 보이는 글 + 추론 토큰이 함께 들어간다(요청 문서). 과금 문구는 가격 문서에 없고, `usage.output_tokens_details.reasoning_tokens`가 출력 토큰의 세부 내역이라 출력에 포함으로 읽는다 |
| 요청 | `POST /v1/messages` · 머리글 `x-api-key` · `anthropic-version: 2023-06-01`(오류 문서 예시) · `model` · `max_tokens` · `system` · `messages` · `thinking: {type: "adaptive"}` · `output_config.effort`(low · medium · high · xhigh · max) | `POST /v1/responses` · `Authorization: Bearer` · `model` · `instructions` · `input` · `max_output_tokens` · `reasoning.effort`(이 모델은 low · medium · high · xhigh · max, 기본 medium) · `store` |
| 응답 | `content[]`(text · thinking 블록) · `usage.input_tokens` · `usage.output_tokens` · `stop_reason`(end_turn · max_tokens · refusal …) | `output[]`(message → `content[]` → `output_text`) · `usage.input_tokens` · `usage.output_tokens` · `status`(completed · incomplete …) · `incomplete_details.reason`(max_output_tokens …) |
| 기본 강도 | high (우리는 medium을 명시) | medium |
| 오류 | 400 요청 · 401 인증 · **402 결제** · 403 권한 · 404 · 413 · 429 속도 제한(월 지출 상한도 429) · 500 · 504 · 529 과부하. **지출 한도에 닿으면 400** | 400 · 401 · 403 지역 제한 · 429(속도 제한과 잔액 · 지출 한도 모두 429, `error.code`로 구분: `credit_balance_exhausted` · `*_spend_limit_exceeded`) · 500 · 503 과부하 |
| 실패한 요청의 청구 | 문서에서 확인하지 못함 | 문서에 없음 |

**이 확인으로 고친 것:** ① 402(결제 문제)를 별도 오류(`BILLING`, 청구 없음)로 분리하고 그 밖의 4xx는 요청 오류로, 408 · 5xx(504 · 529 · 503 포함)는 재시도하되 청구 없음으로 보증하지 않게 했다 ② **최대 출력을 16,000 → 24,000토큰으로 올렸다** — 두 회사 모두 생각 · 추론 토큰이 최대 출력에 합산돼 16,000이면 글이 중간에 잘릴 수 있다. 비용은 실제로 쓴 만큼만 나가고 한도는 그대로다(최악 계산만 커졌다) ③ 호출 한 번의 제한 시간을 2분 → 5분으로 늘렸다(정상 응답이 시간 초과로 끊겨 비용만 나가는 것을 막는다) ④ 잔액 · 한도 문제로 보이는 429 · 401 · 402 문구에 원인을 안내했다.

**아직 확인하지 못한 것(첫 승인 호출에서 확인):** 두 회사의 실제 응답 모양 · 실패한 요청의 청구 여부 · 긴 글(최대 2만 토큰대)을 한 번에 받는 비스트리밍 요청이 네트워크에서 끊기지 않는지(공식 문서는 아주 긴 요청에 스트리밍을 권한다. 우리 최대 출력은 문서가 말하는 10분 한계보다 훨씬 짧다). 응답 모양이 다르면 그 호출은 재시도 없이 멈추고(`INVALID_RESPONSE`), 사용량을 읽지 못하면 비용은 최악 비용으로 센다 — 한도는 지켜진다. 가격 · 모델 ID는 문서에 적힌 값이며 운영자가 독립적으로 확인한 값이 아니다.

### 8-3. 운영자 승인 기록 · 이번 비교의 대상

- **승인 (2026-10-13, 운영자):** 가상 인물 2명 × 모델 2개 = 생성 4건, **총 3,000원 한도, 재시도 비용 포함.** 키 발급과 입력은 운영자가 직접 하며, 승인 금액 · 날짜는 실행 명령에 운영자가 직접 적는다(`--approved-cap-krw 3000 --approved-on 2026-10-13`). 이 승인은 1단계에만 해당하고, 2단계(20건, 8,000원)는 결과를 본 뒤 따로 승인한다.
- **이번 비교는 "개인 통합 리포트"(9,900원 상품, 읽기 구조 `reading-v1`)다.** 고민 반영 리포트(4,900원, `generateConcern`)는 AI 지시문이 아직 옛 규칙이라 이 비교에 넣지 않았고 **검증되지 않았다.** 인물 1명이 "알려 준 고민"을 가지고 있어 개인 통합 리포트 안에 "알려 주신 고민까지 반영한 해석" 구역이 생기지만 그것은 고민 반영 리포트 상품이 아니다. 두 상품을 모두 검증한 것으로 처리하지 않는다.
- **한 모델만 먼저 실행할 수 있다(`--only A` 또는 `--only B`)** — 승인한 범위(4건 · 3,000원) 안의 부분 실행이다. Claude만이면 2건, 예상 약 460원이다. 이름을 가린 비교가 아니며 한 모델만으로는 우열을 말할 수 없다. 결과를 본 뒤 나머지 모델을 추가해도 새로 생성하므로 그 비용은 다시 든다.
- **리허설(`--rehearsal`):** 키 · 네트워크 · 비용 없이 같은 실행 흐름(생성 → 파일 저장 → 화면용 원본)을 모의 글로 끝까지 돈다. 결과 폴더는 `rehearsal-…`로 시작하고 `--execute`와 함께 쓸 수 없다. 흐름의 오류를 유료 호출 전에 찾는 용도이며 AI 품질에 대한 정보는 없다. 실제 실행에서는 **결과 JSON · 비용 기록을 가장 먼저 저장**하고, 읽기 쉬운 파일(가린 글 · 채점표 등) 만들기가 실패해도 이미 쓴 비용으로 만든 결과가 사라지지 않게 했다.
- **결과 읽기:** 파일뿐 아니라 실제 미유 리포트 화면으로 읽는다 — 개발용 화면 `/dev/compare`(내 PC에서만 열림, 후보 이름 가림).

**내용 차이 검사:** 읽기 구조 글은 `lib/report/reading/depth.ts`로 본다 (6장과 같은 표지 · 같은 기준값 — 조건이 있는 부분 60% 이상 · 범용 문장 20% 이하 · 부분끼리 겹침 35% 이하 · 서로 다른 실천 3개 이상 · 구체적 행동 2/3 이상, 무료와의 차이 · 긴 문장은 경고). 사람이 쓴 예시(서윤)가 이 검사를 통과하고 모의 글은 통과하지 못한다는 것을 테스트로 확인했다. 기준값은 예시에 맞춰 바꾸지 않았다. 사주 근거를 반드시 다는 것은 형식 검사(`validate.ts`)가 주제마다 막는다.

**평가표 항목 하나를 더했다:** "읽기 쉬움"(결론 → 짧은 요약 → 쉬운 예시 순서로 읽히는가, 문장이 짧고 쉬운가). 새 읽기 구조를 위해 더한 항목이라 기존 합격 기준(6장, 결과를 보기 전에 고정한 값)에는 넣지 않고 기록만 한다.

### 8-4. 첫 실제 호출 기록 (2026-10-13, 운영자 PC)

- **실행:** `--only A`(Claude만) · 가상 인물 2명 · 승인 3,000원 중 **621원 사용**(P01 307원 · P02 314원, 인물마다 호출 2회 = 처음 응답 + 고쳐 쓴 응답).
- **알게 된 것:** Claude 호출 자체는 성공했다 — 요청이 받아들여졌고, 응답을 읽어 사용량 · 비용이 기록됐다. 응답 모양에 대한 우리의 가정이 이 범위에서 맞았다는 뜻이며, 글의 품질이나 다른 응답 형태(긴 글 잘림 · 거절 등)까지 확인한 것은 아니다.
- **알게 된 것(나쁜 쪽):** 두 인물 모두 형식 검사(`lib/report/reading/validate.ts`)를 처음 응답에서 통과하지 못했고, 고쳐 쓴 응답도 통과하지 못해 **0/2건 실패**했다. 이 실행기는 그때 실패 이유를 저장하지 않아서 **원인은 모른다.** 검사 항목이 많고(글자 수 범위 · 문장 수 · 근거 ID · 쉬운 말 · 금지 표현 · 해 · 반복) 어느 것이 걸렸는지는 이유 없이는 추정할 수 없다. 추정으로 검사 기준을 느슨하게 바꾸지 않는다.
- **고친 것:** 실패한 응답마다 걸린 이유 전체를 화면에 보이고(`cost-and-checks.json`의 `attempts[].errors`), 그때의 글은 `failed/` 폴더에 따로 저장한다(가상 인물의 글, 저장소에 올라가지 않는 폴더). `--persona P01`로 한 인물만, `--already-spent-krw 621`로 이미 쓴 금액을 승인 총액에서 빼고 남은 2,379원 안에서만 다시 돌릴 수 있다. 실패 경로는 `--rehearsal-fail`(호출 없음)로 시험한다.
- **다음:** 한 인물만 다시 돌려 이유를 본다(예상 약 230원, 고쳐 쓰기까지 최악 약 1,050원) → 이유가 검사 기준의 문제인지 지시문의 문제인지 보고 고친 뒤 다시. 승인 총액(3,000원 · 재시도 포함)을 넘기지 않는다.

- **같은 날 두 번째 실행(P01 한 명, `--already-spent-krw 621`):** 333원 사용, **1/1건 통과**(처음 응답은 형식 검사에 걸렸고 고쳐 쓴 응답이 통과). 이 실행까지 실제 호출은 Claude 3건, 누적 **954원**(승인 3,000원 중 남은 2,046원). 한 번 통과한 것은 "이 지시문으로 형식 검사를 통과하는 글이 나올 수 있다"는 것뿐이며 글이 좋은지는 아직 읽어 보지 않았다.
- **2026-10-14 운영자 확인("응"):** 지시문을 `reading-v1-prompt-0.5`로 고친 뒤 **같은 방식으로 P01 한 명만 Claude로 1건** 돌려 봐도 된다고 답했다(남은 승인액 2,046원 안, 예상 약 230~330원 · 고쳐 쓰기까지 가는 최악 약 1,060원). 이 클라우드 작업 환경에는 API 키가 없어 **운영자 PC에서 운영자가 직접** 명령을 입력해 실행한다(승인 금액 · 날짜 옵션을 직접 적는다). 이 실행의 결과는 이전 지시문(0.3) 결과와 비교하되, 한 건이라 우열의 근거로 쓰지 않는다.
- **2026-10-14 세 번째 실행(P01 한 명, 지시문 0.5, 운영자 PC):** **305원 사용, 1/1건 통과**(결과 폴더 `stage-1-20261014-005132`). 처음 응답은 **글자 수 범위 두 곳**에서만 걸렸고(핵심 키워드 `cards.flow.keyword` 19자 — 허용 4~18자, 한 주제의 요약 36자 — 허용 40~220자) 고쳐 쓴 응답이 통과했다. 이 실행까지 실제 호출은 **Claude 4건, 누적 1,259원**(승인 3,000원 중 남은 약 1,741원). 한 건이라 우열의 근거가 아니며, 읽어 본 결과는 아래와 같다.
  - 좋았던 점: 사주 용어 · 점수 · 나이 · 임의의 해 없이 형식 검사를 통과했고, 문장이 쉬운 해요체로 이어졌다.
  - 아쉬운 점(가려 읽는 사람이 판단할 부분이 남음): ① 같은 표현이 여러 주제에 되풀이됐다("상황이 바뀌면 방향을 빠르게" 등) ② 알려 준 고민이 제목 · 카드 · 관계 · 행동까지 전체를 덮었다 ③ 근거 문구보다 한 걸음 더 나간 표현이 몇 군데 있었다. 말만 바꾼 되풀이는 글자 검사로 찾지 못한다.
  - 이 결과를 보고 바꾼 것(호출 없음): 같은 표현이 12글자 이상 두 곳에 나오면 고쳐 쓰게 하는 **반복 검사(`lib/report/reading/repeat.ts`)** — 고쳐 쓰기 요청에만 쓰고 실패 사유로 막지 않는다(`repairRepeats`, 비교 실행기에서만 켬). 지시문 0.6("고민은 한 곳에")은 리포트 구성 방향(`chat-report-v3-proposal.md`)이 정해진 뒤로 미뤘다.

### 8-6. 채팅 자유 질문 첫 실제 호출 결과 (2026-10-14 밤, 운영자 PC, 승인 600원 · 14회 중)

- **실행:** 무료 맛보기의 연애 방에서 질문 4건(위기 안내 없는 이별 · 우울 고민 1건 + "상황에 따라 달라요" 이어 가기 1건 + 상대 속마음 1건 + 이어지는 질문 1건). 4건 모두 답이 도착했고 검사를 통과했다(고쳐 쓰기 없음으로 보인다). 첫 질문 1건의 사용 기록: **입력 2,983 · 출력 455토큰, 비용 어림 16.8원(여유율 포함 18.5원), 응답 1~2초.** 제 어림(31~74원, 입력 4,400~7,000 · 출력 900~2,800토큰)보다 낮았다 — 한국어 토큰이 글자당 약 0.75개로 추정되고 생각 토큰은 거의 쓰이지 않았다(생각 강도 "낮음").
- **잘 된 것:** 마음을 먼저 받아 주고, 일반적인 이별 · 우울 고민이 위기 안내로 막히지 않았고, 결정을 대신 내리지 않았고, 상대 속마음을 단정하지 않았고, 이어서 묻는 질문은 앞선 말을 이어받았고, "상황에 따라 달라요" 뒤에는 알려 준 사실과 리포트에서 읽은 것을 구분했다. 해요체, 사실을 지어내지 않음.
- **고칠 것(지시문 0.3에 반영, 실제 AI로는 아직 확인하지 않았다):** ① "맛보기 리포트에는 …내용만 있어서 읽을 수 없어요"가 답마다 반복됨 ② 마지막 줄 "더 깊은 풀이는 리포트에서 이어져요"가 매번 붙음 ③ 공감 첫 문장과 먼저 고른 상황 언급이 답마다 비슷함 ④ 결정을 못 내리는 이유를 "맛보기라서"로 댐(원칙으로 말해야 함).
- **구조적으로 알게 된 것:** 응답에서 읽힌 반응이 없는 사람의 무료 맛보기에는 "가까운 관계"가 "가볍게 살펴봤어요" 한 줄뿐이라 AI가 쓸 재료가 거의 없다(지어내지 않는 규칙 때문이며 코드 오류가 아니다). 무료 첫 질문은 그 사람에게 **공감 + 스스로 확인할 질문** 중심이 되고, 내 분석에 근거한 답은 리포트에서 이어진다. 운영자 판단(2026-10-15): "리포트를 하지 않으면 무료 질문은 의미가 없다 → 무료 분석(무료 리포트)을 먼저 하게 하고 그 뒤에 상담방을 고르게 한다" — 검사 · 로그인 뒤의 이동을 결과 화면 먼저로 바꿨다.
- **아직 못 한 것:** 진로 · 재무 방의 답변 초점 구분, 나를 알아보기 방, 힘든 마음의 표현("사라지고 싶어요") 뒤 안내 문단은 실제 AI로 시험하지 않았다(가짜 서버로만 확인). 남은 호출 10회 · 무료 질문 4번.

| 붙어 있기 | 모든 해석 문장은 원국 · 응답 · 알려 준 내용 · 조건("~할 때") · 시점이나 분량 중 하나에 붙어 있어야 한다. 붙을 곳이 없는 추상적인 문장은 쓰지 않는다. |
| 근거 ID | 문단마다 근거 ID를 단다. 목록에 없는 근거 · 사건 · 날짜는 쓰지 않는다. |
| 개인정보 | 이름 · 생년월일 원문은 보내지 않는다 (제품 방식 그대로). 이름은 "{name}님" 자리표시만 쓴다. |

### 9-2. 비교에 쓰는 가상 인물 2명 (실제 고객 아님)

| 인물 | 원국(만세력 엔진 계산) | 응답(개발용 문항에 가상으로 답한 값) | 알려 준 고민 | 시험하는 것 |
| --- | --- | --- | --- | --- |
| P01 | 기토(己) 일간 · 여성 · 태어난 시각 있음. 토 4개 · 목 3개, 금 · 수 없음. 정관(규칙 · 책임) 3자리 · 비겁(나와 같은 편) 3자리 · 식상(마음을 꺼내는 힘) 없음 · 재성 없음. 현재 대운 신해 · 다음 대운 경술 | 신중함 · 타인 반응 민감도 높음, 새로움 추구 · 지속성 낮음, 관계 불안 낮음 · 거리 두기 높음. 본인이 알려 준 MBTI는 INFJ | 있음(연애): "연락이 뜸해지면 먼저 할지 기다릴지 계속 고민돼요" · "대화가 길어지면 말수가 줄고 혼자 정리하려고 해요" | 고민을 풀이에 반영하되 사주로 알아맞힌 것처럼 쓰지 않는가 · 선택지가 결정을 대신하지 않는가 |
| P02 | 경금(庚) 일간 · 남성 · 태어난 시각 있음. 금 3개 · 토 3개, 화 · 수 없음. 인성(배움 · 검토) 3자리(편인) · 식상 없음 · 관성 없음. 현재 대운 무오 · 다음 대운 기미 | 타인 반응 민감도 · 지속성 낮음, 거리 두기 낮음. MBTI는 ENTP | 없음 | 고민이 없는데 "알려 주신"이나 지어낸 고민 · 선택지가 나오지 않는가 · 같은 틀을 쓰면서도 P01과 다른 말인가 |

주의: 응답은 **현재 개발용 문항**(4유형 개발용 규칙)으로 만든 값이며, 새 자체 문항(30문항 초안)을 적용한 값이 아니다. 문항 수가 모자라 읽을 수 있는 관점이 5개뿐인 상태이므로, 이 비교는 **글의 품질**을 보는 것이지 성향 읽기의 정확도를 보는 것이 아니다.

### 9-3. 목표 문장 예시 — 이 정도로 구체적이고 근거가 보이는 글 (`docs/samples/stage1-target-sentences.json`)

사람이 쓴 기준선(2판)이며 AI가 베끼게 하려는 것이 아니다. 기계로는 근거 ID가 두 인물의 계산 결과에 있는지, 본문에 사주 용어 · 응답 점수 숫자가 없는지, 막는 표현이 없는지, 한계 문구를 되풀이하지 않는지만 확인했다(`stage1-targets.test.ts` 6개). **근거가 결론을 실제로 뒷받침하는지는 기계로 확인할 수 없어, 각 문단의 "이렇게 읽은 이유"를 근거 문구와 나란히 놓고 사람이 읽어야 한다. 좋은 글인지의 보증이 아니다.**

### 9-4. 평가 기준 (결과를 보기 전에 고정)

**자동 점검** — 낱말 · 표지를 세는 어림이며 얕은 글을 걸러 낼 수 있어도 좋은 글의 보증은 아니다. 글자 수는 보고만 한다.

| 점검 | 실패 | 경고 |
| --- | --- | --- |
| 형식(구성 순서 · 개수, 글자 범위, 고민 유무에 따른 항목, 질문 · 행동 모양) | 어기면 실패(한 번 고쳐 쓰게 하고 다시 점검) | |
| 근거 ID 오류 · 없는 해(계산된 시기 밖) · 앞날 단정 | 1건이라도 실패 | |
| 지어낸 배경 · 부풀린 추상어 · 결정 대신 내리기 · 금지 표현 | 1건이라도 실패 | |
| 고민이 없는 인물에서 "알려 주신" · 선택지 · 정하지 않는다는 안내 | 1건이라도 실패 | |
| 상황 표지(원국 · 응답 · 알려 준 내용 · 조건 · 분량)가 없는 추상 문장 | 4개 이상 | 1~3개 |
| 사주 근거를 단 덩어리의 몫 | 80% 미만 | |
| 구체적인 행동(시점 · 분량 + 동작)의 몫 | 2/3 미만 | |
| 덩어리끼리 겹침 | 35% 초과 | |
| 조건 표지가 있는 덩어리 · 사주와 응답 근거를 함께 단 덩어리 | | 각각 60% 미만 |
| 응답 점수 숫자(예: "88점" · 백분위)를 본문에 씀 | | 1건이라도 |
| 서로 다른 두 인물의 풀이끼리 같은 말 | 기록만 | |

**블라인드 평가 (운영자)** — 인물마다 두 후보의 글을 X · Y로 섞어 5점 만점으로 본다. 사람이 쓴 목표 문장(9-3)도 같은 표로 본다. 후보 이름은 결과를 모두 채점한 뒤에 확인한다.

| 항목 (5점) | 보는 것 |
| --- | --- |
| 장면의 구체성 | 이름을 가려도 이 사람의 이야기로 읽히는가. "~할 때" 같은 생활 장면이 있는가 |
| 중요하게 여기는 것 | 가설로 쓰였고 근거와 맞으며, "그럴 수 있겠다"고 느껴지는가 (단정 · 일반론이면 낮게) |
| 내 안의 갈등 | 서로 부딪히는 두 마음이 각각 무엇을 지키는지 보이는가 (한쪽 편들기 · 뻔한 대립이면 낮게) |
| 잘하는 점이 부담이 되는 때 | 부담이 되는 때가 구체적인 장면인가 |
| 선택지 (P01만) | 지키는 것 · 내려놓는 것 · 확인할 것이 있고 결정을 대신하지 않는가 |
| 추상적 위로 · 누구에게나 맞는 말 | 읽으면서 "아무에게나 해당하는 말"이라고 느낀 문장 수를 센다 (**적을수록 좋다**, 역채점) |
| 근거가 결론을 뒷받침하는가 | "이렇게 읽은 이유"의 근거만으로 그 결론까지 갈 수 있는가 (근거 문구에 없는 능력 · 욕구 · 원인을 만들었으면 낮게) · 알려 준 이야기를 사주로 알아맞힌 것처럼 쓴 문장은 없는가 |
| 한국어 자연스러움 | 번역투 · 반복 · 어색한 문장 |
| 돈을 낼 만한가 | 읽고 나서 "내가 왜 이랬는지 알겠다"는 느낌이 있는가 · 통합 리포트 9,900원을 냈다면 아깝지 않은가 · (P01) 고민 반영 4,900원을 냈다면 아깝지 않은가 |

**1단계의 합격선** (아래를 모두 지키면 그 후보는 2단계에 올린다. 어느 하나라도 못 지키면 지시문을 고쳐 다시 확인하며 추가 비용은 새로 요청한다)
- 지어낸 배경 · 사건 · 날짜 · 직업 · 나이: **0건**
- 자동 점검의 실패 항목 없음 (고쳐 쓰기 1회 안에서). 이것은 필요조건일 뿐 합격의 근거가 아니다. 경고는 사람이 읽고 판단
- 블라인드 평가: "장면의 구체성" · "근거가 결론을 뒷받침하는가" · "돈을 낼 만한가" 평균 4.0 이상, "추상적 위로 · 누구에게나 맞는 말"은 한 편에 3문장 이하
- 건당 비용 400원 이하 (고쳐 쓰기 포함 평균)

### 9-5. 1단계(생성 4건)로 알 수 있는 것과 없는 것

- **알 수 있는 것:** 두 후보가 이 지시문대로 구성을 지키는가 · 지어낸 내용이 있는가 · 비용과 시간이 예상 범위인가 · 같은 근거로 쓴 두 글이 눈에 띄게 다른 질감인가.
- **알 수 없는 것:** 어느 회사가 더 낫다는 순위(4건은 우연의 폭이 크다), 사주 해석의 정확성(해석 규칙은 전문가 검토 전 초안), 실제 고객의 만족, 새 자체 문항으로 만든 근거에서의 품질. 글이 더 깊어 보이는 것이 곧 해석이 맞다는 뜻도 아니다. 후보 중 하나가 지금 이 작업을 하는 Claude와 같은 계열이므로 **이름을 가린 채 운영자가 채점하는 것**이 판단의 기준이다.

### 9-6. 1단계 비용 (호출 없는 계산 — `node scripts/compare-ai-dry-run.ts --variant philosophical-v0`)

가정: 환율 1,600원/달러, 여유율 10%, 입력 토큰은 한글 글자당 2토큰으로 보수적으로 추정, 출력 평소 1만 토큰 · 최대 1만 6천 토큰. 두 후보 모두 입력 $2 · 출력 $10 (100만 토큰당, 공식 문서 확인일 2026-10-12, 운영자가 따로 확인한 값은 아님).

| 구분 | 금액 |
| --- | --- |
| 생성 1건 (평소) | 약 217원 |
| 생성 1건 (많이) | 약 333원 |
| 생성 1건 (많이 + 고쳐 쓰기 1회) | 약 728원 |
| **1단계 평소 예상 (4건)** | **약 890원** |
| 1단계 첫 호출만 쓰는 최악 | 약 1,313원 |
| **1단계 모든 생성이 고쳐 쓰기까지 하는 최악** | **약 2,869원 (승인 한도 3,000원 안)** |

한도 3,000원은 이 테스트의 사용 한도이며 API 계정의 선충전 금액과는 다를 수 있다. 실제 청구는 환율과 실제 토큰 수에 따라 다르다. 호출 전에 최악 비용을 예약하고 한도를 넘길 호출은 보내지 않으며, 승인 기록이 없으면 실행하지 않는다 (4장).
