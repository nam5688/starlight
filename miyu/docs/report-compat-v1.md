# 리포트 궁합 (v1) — 구현 현황 · 권한 · 확인한 것과 못 한 것

> 운영자 확정(2026-10-17): 리포트 궁합은 **두 사람이 각자 분석을 마치고, 서로 궁합 생성에 동의한 뒤, 한 쌍의 지정된 결과로 한 번 결제하면 두 사람이 같은 글을 읽는** 상품이다. 상대의 원래 답 · 개인 리포트 · 비공개 상담은 보이지 않고, 두 사람이 모두 뚜렷하게 답한 영역만 비교한다. 가격은 9,900원(운영자 확정, `PAIR_COMPAT`).
> **판매 스위치(`PAIR_COMPAT.saleOpen`)는 꺼 둔다.** 실제 AI 검증 · 결제 QA · 법률 검토를 마치기 전에는 열지 않는다. 지금 구현은 개발 · 테스트 환경에서만 확인했다(실제 Supabase · 실제 AI · 실제 결제 · 실제 휴대폰 확인 없음).

## 1. 흐름

1. 두 사람이 각자 무료 분석을 마친다(검사 결과 + 사주 계산이 있어야 한다).
2. **A**가 `/pair`에서 동의를 체크하고 초대 링크(`/pair/join/<무작위 24자 토큰>`, 이름 · 생년월일 · 회원번호 없음, 14일)를 만든다.
3. **B**가 링크를 열어 로그인하고(링크 화면에는 초대한 사람의 닉네임만 보인다) 자기 가장 최근 분석 결과로 동의하면 연결된다(DB 함수 `pair_join`이 행을 잠그고 한 명만 연결 — 동시에 6명이 눌러도 1명).
4. 둘 중 한 사람이 `/pair/<쌍 번호>`에서 결제한다(상품 번호 `report-compat:<쌍 번호>`, 주문은 결제한 사람의 검사 결과에 묶임). **쌍마다 결제 완료 주문은 하나**(DB 고유 조건 `orders_one_paid_pair`) — 상대의 두 번째 결제는 서비스가 `already-paid`로 막고 DB가 한 번 더 막는다.
5. 결제가 승인되면 생성이 시작되고(결제 상태와 생성 상태는 따로), 끝나면 두 사람이 모두 같은 글을 `/pair/<쌍 번호>`에서 읽는다. 열 때마다 새로 만들지 않는다.

## 2. 무엇을 쓰고 무엇이 보이는가

| 구분 | 내용 |
| --- | --- |
| 생성에 쓰는 것 | 두 사람의 **사주 계산 결과**(`compatOf` — 간단 궁합 · 사주 궁합과 같은 엔진), 각자 직접 답한 응답에서 **뚜렷한 방향**(`pair-evidence.ts`, 두 사람 모두 뚜렷한 영역만 · 한쪽만 뚜렷하면 비교하지 않고 "비교하지 않은 영역"으로만 센다), 입력한 MBTI(알려 준 경우, 알파벳 없이 선호 방향만) |
| AI에 가는 것 | 이름 · 생년월일 원문 · 문항별 답이 아니라 사주 계산 결과와 응답 방향을 요약한 근거 문장. 두 사람은 "A님 · B님" |
| 저장되는 글 | 이름 · 생년월일 · 응답 원문 · 점수 · MBTI 글자 없음(시험이 확인) — 화면이 읽는 사람에게 "이 글에서 A님은 나" 를 알려 준다 |
| 상대에게 보이는 것 | 내 닉네임 + 두 사람의 궁합 글. 문항별 답 · 개인 리포트 · 상담 내용 · 생년월일은 보이지 않음 |
| 위쪽 요약(커플 유형 · 궁합 지수 · 핵심 한 줄) | **무료 간단 궁합 · 사주 궁합과 같은 함수 `cardOf`**로 코드가 채움 — AI가 쓰지 않음(시험이 같은 값을 확인) |
| A와 B 각자의 실천 | 행동 묶음 셋(A님→B님 · B님→A님 · 함께) + 건넬 말 한 문장. 화면은 읽는 사람의 묶음을 먼저 보이고 "내가 해 볼 행동 · 상대가 해 볼 행동"을 표시 |

## 3. 열람 권한 표 (설계 결정 — 법률 검토 항목)

| 일이 생기면 | 새 생성 | 결제한 사람 | 상대 |
| --- | --- | --- | --- |
| **연결 해제**(더 이상 새로 만들지 않음) | 막힘 | 이미 완성된 글 계속 읽음 | 계속 읽음 |
| **동의 철회**(내 자료를 새 생성에 더 쓰지 않음) | 막힘(철회 시각 기록) | 철회한 사람의 열람만 끝 | 계속 읽음 |
| **환불** | — | 열람 막힘 | 열람 막힘 |
| **계정 탈퇴** | 막힘(트리거가 쌍을 끊고 철회로 기록) | 탈퇴한 사람의 리포트 행은 지워짐 → 그가 결제자면 상대도 읽을 수 없게 됨 | 상대가 결제자였다면 계속 읽음 |
| 결제는 됐는데 글이 만들어지기 전에 연결이 끊김 | 막힘 | "연결이 끊겨 글을 만들 수 없어요" + 운영자 알림 `pair.paid_not_generated`(환불 여부 확인) | 같음 |

- 해제와 철회는 **다르다**(해제는 철회 시각을 남기지 않는다). "한 번 동의하면 영구 철회 불가"라고 쓰지 않는다.
- 이미 만들어진 글의 삭제 · 처리정지 요구에 응하는 방식, 결과 글에 포함될 수 있는 상대 식별 정보, 탈퇴한 결제자의 글을 상대가 계속 읽게 할지는 **법률 검토 대상**이다(결정 전 임시 규칙).
- 쌍 표(`pairs`)는 서버(service_role)만 읽고 쓴다. 로그인한 본인 · 익명은 표를 읽지 못하고 함수를 부르지 못한다(DB 시험이 확인).
- **쌍 표는 검사 결과를 외래 키로 묶지 않는다**: 회원 탈퇴가 주문이 없는 검사 결과를 지우는데, 외래 키가 있으면 탈퇴가 실패한다(DB 시험에 이 경우를 넣었고, 외래 키를 넣어 보면 시험이 실패하는 것도 확인했다). 지워진 검사 결과는 서비스가 "쓸 수 없는 결과"로 읽는다.

## 4. 사주 궁합 엔진과 충돌하지 않는다는 확인

- 같은 엔진 `compatOf` · 같은 카드 `cardOf` · 같은 근거 ID `compat.*`를 쓴다. 리포트 궁합 글의 위쪽 요약은 사주 궁합 · 간단 궁합과 같은 함수의 값이고(`pair-service.test.ts` — 커플 유형 · 지수 · 핵심 한 줄 · 규칙 버전 일치), 응답 비교(`pair.*` 근거)는 그 위에 **더해진 별도 영역(`response`)**이다. 사주 궁합 지시문은 글자 단위로 바뀌지 않았다(리팩터 전후 비교, 보관본 `docs/samples/prompts/compat-v1-prompt-0.3.txt`와 같은지 시험이 확인).
- 응답 비교는 점수 · 궁합 지수를 새로 만들지 않고 "같은 쪽 · 서로 다른 쪽"으로만 말한다. 애착 유형 이름 · 상대 속마음 · 성격 단정은 검사(`PAIR_ECHO` · `ATTACHMENT_TYPE`)가 막는다.

## 5. 판매 스위치와 시험 환경 열기

- 코드 상수 `PAIR_COMPAT.saleOpen = false`가 기본이다. 로컬 · 스테이징 시험에서만 `.env.local`에 `MIYU_TEST_OPEN_SALES=report-compat`(사주 궁합은 `saju-compat`, 쉼표로 함께)을 적으면 열린다. **결제가 테스트 모드(`PAYMENTS_LIVE_MODE`가 true가 아님)일 때만 듣고, 실결제 모드에서는 적어도 열리지 않는다**(`lib/config/sale-switch.ts` · 시험). 실제 AI 연결(`AI_PROVIDER` · 승인 값)이 없으면 시작하지 않는다(`generatorReady`).

## 6. 확인한 것 (개발 · 테스트 환경 — 실제 환경 검증이 아니다)

- 서비스 단위 시험 19개(`lib/services/pair-service.test.ts`): 스위치 · AI 연결 · 초대 한도 · 링크 화면 노출 정보 · 연결 보호(동의 · 본인 · 남의 검사 결과 · 한 번만 · 기간) · 결제 시작(연결된 쌍만 · 결제자의 검사 결과에 묶임 · 대기 주문 하나 · 상대 busy) · 한 사람 결제 → 두 사람 열람 · 이미 결제된 쌍 재결제 불가 · 저장된 글의 개인정보 · 사주 궁합과의 일치 · 생성 입력 · 해제 / 철회 / 환불 / 탈퇴별 열람 · 지표 분리.
- DB 시험 9개(`supabase/tests/pairs.db.test.ts`, 실제 Postgres 임시 DB): 접근 정책 · 동시 연결 1명 · 연결 보호 · 제약 · 해제 / 철회 구분 · 쌍마다 결제 완료 주문 하나 · 결제 → 생성 → 두 사람 열람 → 철회 → 환불 · 탈퇴 두 경우.
- 화면: `/pair`(소개 · 목록 · 초대) · `/pair/join/<토큰>` · `/pair/<쌍>`(초대 링크 · 연결 · 결제 · 만드는 중 · 완성된 글 · 해제 · 철회) · MY 목록 · 결제 화면 안내 · 주문 추적.

## 7. 하지 못한 것 · 남은 일

- **실제 AI로 한 번도 시험하지 않았다.** 지시문 `pair-v1-prompt-0.1`은 모의 작성기(자리 표시 글)로 흐름 · 검사 · 저장 · 열람만 시험했고, **대리 작성기(AI 하위 작업자)가 이 지시문으로 쓴 글도 아직 읽어 보지 않았다.** 실제 글의 반복 표현 · 근거 없는 사건 추정 · 잘못된 시기 해석은 실제 호출 승인 뒤에 읽어야 한다(사주 궁합과 같은 방식).
- 실제 Supabase · 실제 토스 결제 · 실제 휴대폰 · 이메일 인증(SMTP) 환경에서 확인하지 않았다. 운영 DB에 24번을 적용하지 않았다.
- 초대받은 사람이 분석이 없을 때: 지금은 "무료 분석을 마친 뒤 이 링크를 다시 열어 주세요"로 안내한다(링크를 기억하는 쿠키는 만들지 않았다 — 출시를 막는 문제는 아니고 마찰이다).
- 동의 문구 · 처리방침의 AI 전달 설명(원국 여덟 글자가 근거 문장에 들어간다) · 철회 · 삭제 · 환불 문구는 **법률 검토 전 초안**이다. 약관에 리포트 궁합 조항을 아직 적지 않았다.
- 장면형 질문(`couple-scenes-v1`) 연결은 하지 않았다(운영자 D6 — 별도 단계).
