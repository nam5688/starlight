## 2. 입력 규칙

- **사이와 성별은 필수 선택이다.** 기본 선택이 없고, 비어 있으면 이유를 알려 주고 진행하지 않는다. 클라이언트 · 서버가 같은 규칙으로 다시 확인한다(`parseRelationship` · `isCompatGender` — 정해진 값이 아니면 "입력 형식이 올바르지 않아요").
  - ⚠ 운영자 확인 항목: 지시문의 "선택 항목"을 **필수 선택**으로 구현했다("선택 미완료 처리" 지시 · "임의 기본값 금지"에 맞춤). 선택 사항으로 바꾸려면 서버 검사의 필수 조건 한 곳만 풀면 된다(그 경우 사이를 고르지 않은 입력은 아래 6장의 중립 풀이로 간다).
- **성별은 사주의 10년 시기(대운) 계산에만 쓴다.** 궁합 지수 · 커플 유형 · 근거 목록(`compatOf`)은 성별 조합으로 바뀌지 않는다(시험: 4가지 조합이 카드 전체가 같음). 무료 간단 궁합의 결과는 성별에 의존하지 않는다 — 입력은 유료와 같은 계산 입력을 유지하려는 것이다(⚠ 무료 화면에서는 성별이 보이는 효과가 없다는 점이 사용자에게 군더더기일 수 있다: 운영자 판단 항목).
- **이름은 화면의 호칭에만 쓴다.** AI에는 이름 · 생년월일 · 성별을 값으로 보내지 않는다(아래 4장).
- **리포트 궁합 · 사주 궁합의 "내 성별"**은 분석 때 입력한 성별(내 사주 계산에 이미 쓰였다)과 **충돌하면 조용히 덮어쓰지 않고 멈춘다**: `분석할 때는 "여자"로 입력하셨어요. 궁합은 그 분석 결과를 그대로 쓰기 때문에 같게 선택해 주세요. 성별을 잘못 입력했다면 무료 분석을 새로 받아 주세요.` 화면에는 분석 때 입력한 성별을 미리 알려 준다. 성별을 받기 전에 저장한 예전 분석 결과(저장된 성별 없음)는 고른 값을 확인만 하고, 그 사람의 대운 근거는 원래 없다.
- **리포트 궁합의 사이는 초대한 사람이 고르고(쌍에 저장), 초대받은 사람이 링크 화면에서 그 사이를 보고** 자기 성별을 고른 뒤 동의해 연결한다. 사이가 실제와 다르면 연결하지 말고 새 링크를 부탁하라고 안내한다. (⚠ 운영자 확인 항목: 초대받은 사람이 사이를 따로 고르거나 정정하는 흐름은 만들지 않았다 — 한쪽이 정하고 다른 쪽이 확인한다.)

## 3. 풀이 연결

### 3-1. 무료 간단 궁합 — 비용 없는 결정론적 풀이
`relationFrameOf(사이, 엔진 신호)`가 같은 입력이면 늘 같은 글을 만든다. 엔진이 읽은 **끌림(0~2) · 부딪힘(0~2) · 속도(4가지)**에 따라 문장을 고르므로 사이를 고르는 것이 장식이 아니고, 같은 사이라도 사주에 따라 풀이가 달라진다(시험: 사이마다 끌림 3 · 부딪힘 3 · 속도 4 · 행동 2가지가 모두 다름). 칸은 **잘 맞는 부분 · 부딪히기 쉬운 부분 · 서로 이해할 점 · 지금 해 볼 행동**이다.

| 사이 | 중심 |
| --- | --- |
| 연인 | 대화와 서운함 · 갈등 조율 |
| 결혼준비중 | 생활 · 시간 · 돈 · 역할의 합의(결혼이 잘 풀린다는 뜻이 아님을 밝힘) |
| 썸타는중 | 속도 · 경계 · 대화. "상대의 마음이 어떤지는 사주로 알 수 없다"고 밝히고 마음 확정 · 연애 확정을 쓰지 않음 |
| 결혼함 | 일상 협력 · 다툰 뒤 회복(앞날을 판정하거나 보장하지 않음) |
| 친구 | 우정 · 거리감 · 협력(연애 · 배우자 · 결혼 말 없음) |
| 기타 | 어떤 사이인지 짐작하지 않는 중립적 이해(구체 관계 이름 없음) |

표시 규칙: 커플 유형 이름은 연인 · 결혼준비중 · 결혼함(과 사이를 모르는 예전 카드)에서만 보이고, 썸 · 친구 · 기타는 사이의 제목을 쓴다(내부 유형 · 점수는 그대로). 엔진 문구의 "배우자 자리"는 썸 · 친구 · 기타에서 "가까운 사이를 보는 자리"로 **표시만** 바꾼다(계산값 · 순서 불변, "이 지수는 이렇게 계산했어요" 설명 포함 — 브라우저 검사에서 이 설명에 남아 있던 것을 찾아 고쳤다).

근거 없는 갈등 · 과거 사건 · 재정 상황 · 상대 감정을 사실처럼 쓰지 않는다 — 고정 문구 전체(사이 6 × 끌림 3 × 부딪힘 3 × 속도 4)를 시험이 검사한다.

### 3-2. 사주 궁합 · 리포트 궁합 — 기존 생성 경로에 정식 연결
- **지시문(시스템 프롬프트) `compat-v1-prompt-0.5` · `pair-v1-prompt-0.3`는 글자 하나도 바꾸지 않았다**(보관본과 같음을 시험이 확인). 사이는 **사용자 메시지의 `relationship` 항목**으로 간다: `{ id, label, given, read, avoid }` — 사용자가 직접 알려 준 사이라는 점 · 그 사이의 읽는 법 · 쓰지 않을 것. 사이가 없으면 이 항목 자체가 없어 **메시지가 예전과 글자까지 같다**(승인된 1회 상한 656.30 · 701.40원의 근거 입력이 바뀌지 않는다; 사이가 있으면 입력이 수백 토큰 늘지만 승인 값은 건드리지 않았다 — 실제 호출은 하지 않았으므로 늘어난 비용은 어림이다).
- **검증(`validate.ts`)**: 사이에 맞지 않는 글은 저장하지 않는다 — 친구 · 기타에 연애 · 배우자 · 결혼, 기타에 구체 관계 이름, 썸에 서로의 마음 · 연애 확정 · 배우자 · 결혼, 결혼준비중 · 결혼함에 앞날 보장 · 이혼 · 지어낸 재정 사정. 사용자가 알려 준 사이 자체("결혼한 사이" · "사귀고 있")는 지어낸 사건으로 막지 않는다(다른 사이에서는 여전히 막음). 모든 글 조각(제목 · 모든 장 · 행동 · 추천 질문)에 걸린다.
- **조립(`assemble.ts`)**: 저장된 글에 `relationship`이 남고(없으면 필드 자체가 없음), 5번 장 이름표가 사이를 따르며(연애와 오래 함께하는 방식 / 결혼 준비와 생활 합의 / 다가가는 속도와 서로의 선 / 함께 사는 일상과 회복 / 우정과 오래 가는 거리감 / 오래 함께 지내는 방식), "사이는 직접 알려 주신 값으로 읽는 관점만 바꿨다"는 안내가 붙는다.
- **화면(`compat-report-view.tsx`)**: 사이 표시 · 썸/친구/기타는 커플 유형 숨김.
- 성별을 받으면 두 사람의 대운이 계산돼 기존 시기 근거(`compat.timing.luck`)가 생긴다(상대 성별이 없던 예전 입력은 대운만 빠짐).

## 5. DB — migration 26 (파일만 준비 · 어떤 외부 DB에도 적용하지 않았다)

`supabase/migrations/20261105000000_pair_relationship.sql`

```sql
alter table public.pairs
  add column relationship text
  check (relationship is null or relationship in ('lover', 'engaged', 'some', 'married', 'friend', 'other'));
```

- **영향**: 열 하나(nullable) 추가. 기존 쌍 · 결제 · 열람 권한 · 인덱스 · 함수(`pair_join` 등) · RLS 정책은 그대로. 값이 없는(null) 기존 쌍은 **특정 관계로 채우지 않고** 중립으로 읽는다. 사주 궁합은 DB 변경이 필요 없다(기존 jsonb).
- **롤백**: `alter table public.pairs drop column relationship;` — 이미 만든 쌍의 사이 값이 사라지고 코드는 그 열을 읽지 않으면 null(중립)로 돌아가지만, 새 초대 만들기는 다시 "준비 중"으로 멈춘다. 코드 롤백과 DB 롤백은 따로 판단한다(`runbook.md`). 이 프로젝트의 규칙상 되돌리는 마이그레이션 파일은 만들지 않는다.
- 확인 SQL: `supabase/check-migrations.sql`에 26번 행을 더했다(읽기 전용). `supabase/apply-staging-all.sql` · `apply-4-to-10.sql`은 `node scripts/render-apply-sql.ts [--staging]`로 다시 만들었다.
- **미적용 DB(예: miutest가 붙은 외부 Supabase)에서의 동작** — 코드를 먼저 배포해도 깨지지 않는다:

| 기능 | 26번 미적용 시 |
| --- | --- |
| 개인 리포트 · 무료 분석 · 기존 결과 조회 · 채팅 · 결제 | 쌍 표를 쓰지 않아 **영향 없음** |
| 무료 간단 궁합 | DB를 쓰지 않아 영향 없음 |
| 사주 궁합 | 기존 jsonb라 영향 없음(사이 · 성별이 함께 보관됨) |
| 기존 리포트 궁합 쌍 읽기(`select *`) | 새 열 이름을 부르지 않아 **그대로 동작**, 사이는 null |
| **새 리포트 궁합 초대 만들기** | insert가 "열 없음"(PostgREST `PGRST204` / Postgres `42703`)으로 실패 → 저장소가 `42P01`로 통일 → 서비스가 **"리포트 궁합을 준비하고 있어요"(db-not-ready)로 멈춤**. 사이를 빼고 성공한 척하지 않고 쌍도 만들어지지 않는다 |
| (참고) 리포트 궁합 판매 스위치 | 기본 꺼짐이라 일반 사용자에게는 원래 열리지 않는다 |

실제 PostgREST로 확인(로컬 임시 DB, 적용 전): 없는 열 insert → `PGRST204 / 400 "Could not find the 'relationship' column"` → 저장소 `createPair`가 `42P01`("DB 변경 26번 필요")을 던짐 · 읽기 정상 · 쌍 행 불변.

## 6. 기존 데이터 호환

- 이 기능 이전에 보관된 사주 궁합 요청(사이 · 성별 없음) → `relationship = null`, 상대 대운 근거만 빠짐. 이 기능 이전의 **저장된 글은 예전 화면 그대로**(사이 표시 없음 · 커플 유형 표시 · 5번 장 예전 이름표)다 — 로컬 DB에 이전에 만들어 둔 리포트 궁합 글 2건을 실제 화면으로 열어 확인했다. 저장된 결과를 사후에 재생성하지 않는다.
- 사이 값이 비었거나 정해진 여섯 값이 아닌 입력은 어디에서도 특정 관계로 바뀌지 않는다(임시 보관 · 저장소 읽기 포함).

## 8. 새로고침 유지와 개인정보 안내

간단 궁합은 입력을 서버에 저장하지 않는다. 새로고침 · 뒤로 가기에 입력이 사라지지 않게 **기존 분석 입력과 같은 방식(이 브라우저 탭의 sessionStorage, `lib/profile/draft.ts`)** 을 따르되 더 짧다:

- 서버로 보내지 않는다 · 쿠키 · localStorage를 쓰지 않는다 · 탭을 닫으면 지워진다 · **1시간** 지나면 읽을 때 버린다(분석 입력은 6시간).
- [입력 지우기] · [다른 두 사람으로 다시 보기]를 누르면 화면과 보관이 함께 지워진다. 사주 궁합 구매 폼은 결제 화면으로 넘어갈 때 지운다.
- 화면 안내(무료 간단 궁합 폼만): "입력한 정보는 궁합 계산을 위해 서버에 전달되지만 서버에는 저장하지 않아요. 새로고침해도 이어 쓸 수 있도록 이 브라우저 탭에 1시간 동안 임시 보관해요. 탭을 닫거나 [입력 지우기]를 누르면 지워져요." — 처음 문구는 "서버에서 쓰고" 뒤에 "(서버로 보내지 않아요)"가 이어져 모순으로 읽혔다. 지금은 **계산을 위한 서버 전달 / 서버 비저장 / 탭 임시 보관(1시간) / 지우는 때**를 따로 말한다.
- 유료 사주 궁합 구매 폼의 안내(상대 정보를 리포트가 만들어지는 동안 보관한다는 별도 안내)는 이 무료 안내와 섞지 않았고 바꾸지 않았다. 다만 그 안내 속 "(서버로 보내지 않아요)"도 임시 보관 자체를 가리키는 말이라 같은 방식으로 읽힐 수 있다 — 운영자 확인 항목.

## 9. 운영자 확인이 필요한 항목

1. 사이 · 성별을 **필수**로 둔 해석이 맞는지(2장).
2. 법률 검토(처리방침 3-2는 사실만 적은 상태): 사이 값의 AI 전달(4장) · 브라우저 임시 보관 · 신규 수집 항목에 대한 재동의 필요 여부(`TERMS_VERSION`을 올리지 않았다).
3. 초대받은 사람의 사이 확인 방식(2장 마지막).
4. 무료 간단 궁합에서 성별 입력이 결과에 보이는 효과가 없다는 점.
5. migration 26의 외부 DB 적용 시점(승인 전 미적용).
6. 실제 AI로 사이별 글 품질 확인(별도 승인 · 운영자 PC) — 승인 6/6 · 궁합 2종 상한은 이번에 건드리지 않았다.
