# 첫 화면 "한눈에 기억되는 결과" 제안 — 유형명 · 럭키 지수 · 궁합 점수 · 커플 유형 · 무료 궁합 사이트

> 운영자 전달(2026-10-16). **제안이며 구현하지 않았다.** 코드 · 화면 · 저장 형식은 바뀌지 않았다.
> 이 문서는 받은 제안을 잃지 않게 적고, **지금 프로젝트 규칙과 부딪히는 곳**과 **운영자가 정해야 할 것**을 가른다. 제안의 근거(통계 · 시장 반응)는 이 저장소에서 확인한 것이 없다.

## 1. 받은 제안

| 묶음 | 내용 |
| --- | --- |
| 대표 결과 | 첫 화면에 핵심 문장 바로 아래 **유형명 하나**("신중 몰입형" + 한 줄). 감성 별명 · 동물 이름은 빼고 직관적인 이름. 질문 하나 → 유형 하나가 아니라 **사주 + 장면 응답 + 성격 축**을 합쳐서 |
| 럭키 지수 | "사주에서 본 나의 럭키 지수 82" + 구성 4개(사람·귀인 · 기회·타이밍 · 재물 흐름 · 회복·반전) + 가장 높은 것 하나를 풀이. **하한(65점 이상)을 정하지 않고**, 점수 구간의 뜻을 바꿔서(50~64 = "기다리는 운보다 내가 만드는 힘이 큰 편") 낮은 점수도 나쁘지 않게. 점수는 **코드가 계산하고 AI는 설명만**. "미유 럭키 지수 = 현재 분석하는 원국 구조와 시기 흐름으로 만든 콘텐츠 지표"로 표시 |
| 궁합 점수 | 총점 + 영역별(대화 · 친밀감 · 갈등 조율 · 생활 리듬 · 함께 성장) + "점수보다 중요한 한 가지". 확률이 아니라 요소의 조화도라고 한 번 설명 |
| 커플 유형 | "액션 로봇 커플 · 줄다리기 · 딱풀 · 마이웨이 · 온도차 · 거울 · 시소 · 자석 · 롤러코스터 · 단짝 · 찰떡 · 브레이크 · 직진 · 핑퐁 · 숨바꼭질 · 고무줄 · 한팀 · 퍼즐 · 티키타카 · 평행선" 20개(짧은 일상 단어 + 커플), 좋고 나쁨이 느껴지지 않게 설명을 붙임. 유명 캐릭터(짱구 · 도라에몽 등)는 쓰지 않고 자체 이름 |
| 무료 궁합 사이트 | 생년월일만 넣는 가벼운 무료 사이트("우리 둘은 무슨 커플일까?") → 커플 유형 + 궁합 점수 + 공유 카드 → 결과 아래에서 "이건 사주만 본 결과예요. 실제 성격까지 넣으면?" → ME:U 리포트 궁합. `by ME:U` 표기. 무료는 한 주제만 완결(유형 · 총점 · 강한 영역 1 · 부딪히기 쉬운 영역 1) |
| 두 레이어 | 위 = 재미 · 호기심(유형 · 지수 · 궁합 · 공유 카드), 아래 = 돈 낼 가치(왜 그런지 · 사주 구조 · 응답을 함께 본 해석 · 관계 · 일 · 돈 · 시기 · 행동 · 채팅 상담) |

## 2. 지금 규칙과 부딪히는 곳 (CLAUDE.md · 설계 문서 기준)

| 제안 | 지금 규칙 · 상태 | 판단 |
| --- | --- | --- |
| 유형명을 첫 화면에 | 2026-10-15 운영자 결정으로 "~형" 이름표를 앞에 세우지 않고 설명 문구("관계에서 확인을 중요하게 여기는 편")로 바꿨다. 이유는 **유형 분류가 확정 전**이기 때문이다. 12유형 설계(`docs/tendency-types-v2.md`)는 운영자 검토 전 · 문항이 모자라 분류 불가 | **운영자가 이름을 되살리겠다고 정하면 가능**하다. 다만 이름 체계(지금 4유형 개발용 vs 12유형 초안)와 분류 근거가 먼저다. "신중 몰입형"은 감성 별명이 아니라 규칙에 어긋나지 않는다 |

| 럭키 구성 4개를 코드로 계산 | 엔진이 **계산하는 것**: 원국 · 십신 분포 · 합충형 · 대운 · 세운 · 월령 · 통근 · 투간 · 강약 후보 · 조후 후보. **계산하지 않는 것: 용신 · 격국 · 희신 · 기신 · 신살**(귀인은 신살 계열) | "사람·귀인 88"과 "회복·반전 84"를 계산할 **근거가 지금 엔진에 없다.** 억지로 숫자를 만들면 내부 매핑(예: 재성 있음 + 대운 재성 → 재물 +10)이 설계자의 가설일 뿐이고, 나중에 사용자가 구조를 알면 신뢰가 떨어진다는 제안 자신의 우려가 그대로 온다 |

## 3. 지금 규칙 안에서 먼저 해 볼 수 있는 것 (제안)

1. **점수 없는 첫 화면 훅**: 지금 첫 화면에는 핵심 해석 한 문장 · 대표 경향 설명 · 카드 3개가 있다. 숫자 없이 "한눈에 기억되는 결과" 하나를 더하는 방법 — 예: "나의 운이 쓰이는 방식"을 숫자가 아니라 설명 카드 한 장(예: "기회가 먼저 오기보다 내가 움직일 때 붙는 타입")으로 — 사주 근거(재성 · 식상 · 인성 분포와 대운 주제)에서 규칙으로 고르고 AI는 설명만. 높고 낮음이 없고 계산 근거를 설명할 수 있다.
2. **점수는 궁합에서 먼저**: 규칙에 부합하고(영역별 · 계산 설명 · 확률 아님), 사람들이 가장 먼저 궁금해하는 숫자이며, 럭키 지수보다 계산 근거(두 사람의 십신 · 합충 관계)가 엔진에 이미 있다. 단 궁합 서비스를 만든 뒤.
3. **유형명**은 12유형 설계 확정과 함께: 운영자가 이름을 쓰겠다고 정하면, 분류 규칙 · 이름 · 설명 문구를 한 번에 정한다(`tendency-types-v2`).

## 4. 운영자가 정할 것

1. 첫 화면에 **유형 이름**을 다시 쓰겠는가(2026-10-15 결정의 변경). 쓴다면 4유형(개발용)이 아니라 어떤 이름 체계인가.
2. **럭키 지수를 숫자로** 낼 것인가. 낸다면 "사주 점수 금지 · 개인 예측 검증 전 금지" 규칙을 어떻게 바꾸는가(계산 근거가 없는 신살 계열 하위지수는 빼고 지금 엔진이 계산하는 것만 쓰는 안 포함). 숫자 없는 카드 안(3-1)으로 갈 것인가.
3. **무료 궁합 사이트**를 어느 시기에, 어떤 입력으로(출생정보를 저장하지 않고 계산만) 열 것인가. 먼저 `docs/compat-proposal.md`의 궁합(사주 궁합 · 리포트 궁합)을 만들어야 한다.
4. **캐릭터 · 이름 · IP**: 자체 캐릭터 이름의 상표 · 중복 확인과 "Peeky" IP 이용 허락 확인은 운영자가 한다.

## 5. 만들게 된다면 (설계 원칙)

- 점수는 **코드가 계산**한다(같은 입력은 항상 같은 값 · 규칙 버전을 저장 · `lib/saju/interpret/` 아래 순수 계산 · AI는 점수를 정하지 않고 설명만). 계산 규칙은 `rule-meta.ts`에 출처 · 조건 · 예외 · 검토 상태(draft)를 적는다.
- 점수의 **하한 · 상한을 먼저 정하지 않는다**(제안과 같은 의견). 가상 입력 수만 건으로 분포를 세어 문서에 적는다(특정 날짜의 예시를 분포의 근거로 쓰지 않는다).
- 엔진이 계산하지 않는 것(용신 · 격국 · 신살)에 기대는 하위지수는 만들지 않는다.
- 화면에는 점수 옆에 "미유가 정한 규칙으로 계산한 콘텐츠 지표이며 예측이 아니다"를 작게 두고, 어떤 근거로 계산했는지 한 줄을 보인다(숨기지 않는다).
- 재물 문장은 "쉽게 들어온다"가 아니라 조건형("재물과 이어지는 활동이 커지는 시기가 있어요")으로(제안과 같은 의견).

## 6. 하지 못한 것

- 제안의 효과(공유율 · 전환율)를 확인하지 못했다. 이 문서의 판단은 규칙 대조이며 시장 판단이 아니다.
- 럭키 지수의 계산식 · 분포 · 근거 검증을 만들지 않았다.
- 상표 · 저작권 · 개인정보에 대한 법적 검토를 하지 못했다.

## 7. 무료 궁합 결과 화면 구성 (운영자 2차 전달 2026-10-16 — 제안 · 구현하지 않음)

> 1~6장의 제안에 이어 받은 **무료 궁합 결과 화면**의 구성 다듬기다. 궁합은 아직 만들지 않았고(홈의 두 입구도 "준비 중") 이 문서의 내용은 코드 · 화면 · 저장 형식을 바꾸지 않았다.

### 7-1. 받은 제안

- 흐름: 무료 궁합 결과 → 궁금증을 남김 → 미유 리포트 궁합으로 연결. 이 흐름은 자연스럽다고 보고, 손볼 곳 세 가지를 짚었다.
  1. "우리가 **실제** 잘 맞는 점" — 무료 사주 궁합도 궁합인데 "실제"라고 하면 무료 결과가 가짜처럼 들릴 수 있으므로 쓰지 않는다.
  2. "연애운이 강해지는 시기" · "주의해야 할 시기"는 **두 사람의 대운 · 세운을 함께 비교하는 기능이 구현됐을 때만** 넣는다.
  3. "추천 날짜"는 무엇인지 모호하고(데이트하기 좋은 날인지 고백 · 결혼 날짜인지) **실제 날짜 계산 기능이 없다면 지금은 뺀다.**
- 무료 결과 화면의 모양(다듬은 안): 이름 × 이름 → 커플 유형 이름 + 한 줄 → "최종 궁합 지수" **한 개 총점** + 풀이 두 줄 → "우리 커플의 핵심" 한 줄 → [결과 공유하기]. 세부 영역 점수를 총점 아래에 여러 개 깔지 않는다 — 무료 바이럴 화면은 **총점 하나 + 커플 유형 + 핵심 한 줄**이 깔끔하고, 세부 영역 점수는 미유 상세 궁합(유료)에서 공개해도 된다.
- 무료 결과 아래의 연결 문구: "이건 두 사람의 사주만으로 본 **간단 궁합**이에요. 그런데 실제 성격까지 더하면 우리 궁합은 어떻게 달라질까요?" → 두 사람의 사주에 **각자가 직접 답한 성격 · 기질 · 애착과 입력한 MBTI**를 함께 연결 → 리포트 궁합에서 볼 수 있는 이야기 목록(점수 상세 풀이 · 자연스럽게 잘 맞는 부분 · 같은 상황에서 다르게 반응하는 부분 · 반복해서 부딪히는 지점과 이유 · 서로에게 필요한 표현과 대화 방식 · 가까워질수록 필요한 거리와 친밀감 · 생활 속도와 역할을 맞추는 방법 · 주의 깊게 볼 시기 · 관계 흐름이 좋아지는 시기와 활용 방법) → [우리의 리포트 궁합 보기]. 마지막 목록은 "사주 + 성향을 같이 봐야만 알 수 있는 것" 위주로 구성해 무료 사주 궁합과 유료 리포트 궁합의 차이가 바로 이해되게 한다.

### 7-2. 지금 규칙 · 상태와 대조

### 7-3. 정리

- 그대로 받는 것: "실제" 표현 제거, 시기 항목 보류, 추천 날짜 제거, 무료 화면은 **총점 하나 + 커플 유형 + 핵심 한 줄**, 영역별 점수는 상세 궁합에서, 연결 목록은 "사주 + 성향을 같이 봐야만 아는 것" 위주.
- 조건을 붙이는 것: 총점의 계산 근거 한 줄 · 확률이 아니라는 안내 · 두 사람이 모두 동의한 경우의 성향 연결 · "정확도" 주장 금지.
- 운영자가 정할 것(1~4장과 같은 결정 항목에 더한다): 무료 궁합에 **총점 하나**를 쓸지(영역별 원칙의 예외로 둘지), 총점 계산 규칙을 어떻게 설명할지, 커플 유형 분류 규칙을 먼저 만들지, 무료 사주 궁합을 `by ME:U` 별도 사이트로 낼지 미유 안에서 먼저 열지.
- 하지 못한 것: 이 화면 구성이 공유율 · 전환율에 어떤 영향을 주는지 확인하지 못했다. 점수 · 유형의 계산 규칙 · 분포 · 상표 · 법적 검토도 하지 않았다.
