# 내 고민 자세히 알려주기 · 나의 고민 기록소

개인 통합 리포트를 받은 고객이 **지금의 고민을 적고, 그 고민으로 새 리포트를 따로 발급받는** 기능이다. 예전 이름은 "나를 더 반영하기"였다.

- 고민을 쓰고 · 고치고 · 저장하는 것은 **무료**이고 리포트를 만들지 않는다.
- 저장한 뒤 「이 고민으로 새 리포트 발급 · 4,900원」을 **따로** 눌러야 새 리포트가 만들어진다.
- 기존 리포트는 **덮어쓰지 않는다.** 새 리포트는 같은 검사 · 같은 사주에서 별도 기록으로 발급된다.
- 리포트마다 **발급 당시의 고민 내용과 작성 시점**이 기록으로 남고, 이후에 고민을 고쳐도 과거 리포트의 고민 · 해석은 바뀌지 않는다.

가격 4,900원은 **가안**이다 (`lib/config/product.ts`의 `CONCERN_REPORT` 한 곳에서만 고친다). 최초 구매에 무료 발급을 몇 회 포함할지는 정해지지 않았고, 지금은 없다.

## 1. 고객이 보는 흐름

화면 이름은 **나의 고민 기록소** (`/results/[id]/context`)다. 맨 위에는 항상 이 안내가 보인다:

> 고민을 작성하거나 수정해도 기존 리포트는 바뀌지 않습니다. 저장 후 ‘이 고민으로 새 리포트 발급하기’를 누르면 변경한 내용이 반영됩니다.

| 상태 | 화면 | 버튼 |
| --- | --- | --- |
| 아직 적은 고민이 없음 | **작성 기록 없음** | 작성하기 |
| 고민을 적어 저장함 (개인 통합 리포트 구매 · 준비 완료 · AI 연결) | 적어 둔 고민 + 새 리포트 발급 안내 | **이 고민으로 새 리포트 발급 · 4,900원** (켜짐) |
| 고민을 고쳐 저장함 | 같은 화면 | 위 버튼이 **다시 켜짐** (이전 기록 · 리포트는 그대로) |
| 지금의 고민으로 이미 발급함 | 같은 화면 | **이 고민이 반영된 리포트 보러가기** |
| 개인 통합 리포트를 아직 구매하지 않음 | 같은 화면 | 발급 버튼 비활성화 + "개인 통합 리포트를 구매한 분께 열려 있어요" |
| 개인 통합 리포트가 아직 만들어지는 중 | 같은 화면 | 비활성화 + "준비되면 발급할 수 있어요" |
| AI가 아직 연결되지 않음 (개발용 생성기) | 같은 화면 | 비활성화 + 이유 안내 |

- 같은 내용을 다시 저장하면 "바뀐 내용이 없어 그대로 두었습니다" — 저장 시점이 바뀌지 않으므로 발급 버튼 상태도 그대로다.
- 이전에 발급한 고민 내용으로 되돌려 저장하면 **다시 결제하지 않고** 그 기록의 리포트로 안내한다 (같은 글에 두 번 돈을 내지 않게).
- 화면 아래에는 **고민 기록 목록**이 있다. 발급할 때마다 한 칸씩 쌓이고(최근 발급이 위), 한 칸에는 발급일 · 고민 주제 · 고민 작성 시점 · 상태 · "그때 적은 고민 보기" · 리포트로 가는 버튼이 있다. 결제 전의 임시 저장본은 목록에 나오지 않는다.
- **MY**에는 개인 통합 리포트와 별도로 "내 고민 반영 리포트" 목록이 생긴다. 발급일 · 고민 주제 · 작성 시점으로 이전 리포트와 새 리포트를 구분하며, 결제내역에는 상품 이름(개인 통합 리포트 / 내 고민 반영 리포트)이 따로 나온다.
- 발급 버튼은 누르는 순간 잠긴다. 서버도 같은 저장본이면 같은 기록 · 같은 대기 주문으로 이어 주므로 두 번 눌러도 한 건만 발급된다.
- 만들기에 실패하면 결제는 그대로 유효하고, 기록의 리포트 화면에서 **같은 발급 건으로 다시 만들기**를 누른다 (추가 결제 없음). 방금 시도한 직후에는 "1분 뒤에 다시" 안내만 나온다.
- 고객은 현재 고민 · 발급 때 남긴 고민 기록의 내용을 직접 보고, 현재 고민은 고치고 지울 수 있고, 기록의 내용은 지울 수 있다 (지워도 리포트 · 주제 · 작성 시점은 남는다). 회원 탈퇴 때 모두 삭제된다.

## 2. 데이터 구조

| 무엇 | 어디 | 바뀌나 |
| --- | --- | --- |
| 현재 고민 | `personal_contexts` (검사 결과당 하나) | 언제든 고치고 지울 수 있다 |
| 고민 기록 (발급 순간의 저장본) | `concern_records` (11번 DB 변경) | **고치지 않는다.** 허용되는 변경은 내용 지우기뿐 (DB 트리거가 강제) |
| 새 리포트 주문 | `orders`, 상품 번호 `concern-report:<기록 번호>`, 4,900원 | 기존 주문 규칙(상태 변경 규칙 · 금액 변경 금지) 그대로 |
| 새 리포트 | `reports` (주문마다 하나, `kind: "concern-v1"`) | 완성되면 바뀌지 않는다 (기존 규칙) |
| 기존 개인 통합 리포트 | 그대로 | 건드리지 않는다 |

- 기록은 같은 검사 결과의 같은 작성 시점(저장본)에 **하나**만 생긴다 (DB 고유 조건, 내용을 지운 기록은 제외). 기록마다 결제 완료 · 결제 대기 주문은 하나뿐이다 (기존 주문 고유 조건이 상품 번호별로 걸려 있다).
- 리포트 본문 `basis.concern`에는 기록 번호 · 주제 · 적은 항목 이름 · 작성 시점만 있고 **고민 내용은 없다.** 다만 본문에서 AI가 고객의 말을 받아 쓴 문장은 리포트에 남는다 (기록의 내용을 지워도 그 글은 남는다 — 고객에게 그렇게 안내한다).
- 결제 전 임시 저장본(결제를 시작했지만 끝내지 않은 기록)은 고민을 고치거나 지울 때 내용이 지워진다. 결제 대기 중이거나 결제 · 환불된 주문이 있는 기록은 그대로 둔다.
- 개인 통합 리포트 구매 여부(결과 화면 · MY 카드 · 결제 시작)는 상품 번호로 구분해서 본다. 새 리포트를 샀다고 개인 통합 리포트를 산 것으로 보이지 않고, 그 반대도 마찬가지다.

## 3. 발급 자격과 발급을 막는 경우

발급(= 결제 시작)은 아래를 모두 만족해야 한다. 어긋나면 결제는 시작하지 않고 이유를 알려 준다.

1. 본인의 검사 결과이고 현재 고민이 저장되어 있다.
2. 개인 통합 리포트를 결제했고 그 리포트가 **준비 완료**다 (이미 준 내용과 달라야 하므로 기준이 필요하다).
3. 고민을 해석에 반영하는 AI 생성기가 연결되어 있다 (`server/concern.ts`). **개발용 규칙 생성기에는 고민 리포트를 만드는 기능을 넣지 않았다** — 고민이 반영되지 않은 글을 판매하지 않기 위해서다.
4. 지금 새 구매를 받는 중이다 (용량 · 하루 예산 — 기존 판매 문).
5. 11번 DB 변경이 적용되어 있다 (아니면 "준비 중"으로 막힌다. 고민을 적고 저장하는 것은 그 전에도 된다).

이미 이 고민으로 발급한 경우는 위 조건과 관계없이 그 리포트로 안내한다 (환경이 바뀌어도 열람은 된다).

## 4. 새 리포트가 "다시 살 만한 글"이 되게 하는 장치

개인 통합 리포트에 문단 몇 개를 더한 글이면 팔지 않는다. 장치는 세 겹이다.

- **지시문** (`lib/report/concern/prompt.ts`): 이미 준 리포트의 요지를 **되풀이하지 말 것**으로만 보내고(이름은 `{name}`으로 바꿈), 고객이 적은 상황마다 "왜 그런지 → 해 볼 선택"을 새로 쓰게 한다. 이전에 발급한 고민 리포트가 있으면 이번 고민과의 차이를 의식하게 한다. 연애 · 결혼 고민에서도 상대의 나이 · 직업 · 만나는 날짜는 쓰지 않는다. AI에는 이름 · 생년월일 원문을 보내지 않는다.
- **형식 검사** (`validate.ts`): 문단마다 근거 ID, 고객이 알려 준 내용임을 밝히며 시작, 상황별 해석 3~5개, 계산된 시기만, 4~6개의 행동, 반복 문장 · 금지 표현 · 사주로 알아맞힌 표현 차단.
- **내용 차이 검사** (`depth.ts`) — 글자 수가 아니라 내용을 본다:

| 검사 | 기준 | 어기면 |
| --- | --- | --- |
| 고객이 적은 낱말이 해석에 나오는가 | 핵심 낱말의 35% 이상(최소 2개) | 막음 (이유를 알려 한 번 고쳐 쓰게 함) |
| 상황별 해석이 고객의 말에서 출발하는가 | 상황 항목의 60% 이상이 고객의 낱말을 포함 | 막음 |
| 이미 준 리포트의 문단을 가져오지 않았는가 | 겹치는 문단 15% 이하 (한 문단의 절반 이상이 같으면 "가져온 것") | 막음 |
| 조건 · 상황 표지 / 범용 문장 / 시점 · 분량이 보이는 행동 / 이전 고민 리포트와의 겹침 | 기준 이하이면 | 알림으로 저장(`basis.quality.warnings`), 막지 않음 |

고쳐 써도 통과하지 못하면 리포트는 **실패**로 남는다. 결제는 유지되고 같은 발급 건으로 다시 시도할 수 있다 (시도 횟수 상한은 기존 리포트와 같다).

**이 검사는 낱말 · 표지를 센 어림이다.** 통과했다고 좋은 글이라는 뜻이 아니다. 실제 AI가 쓴 글이 "또 살 만하다"고 느껴지는지는 가려 읽는 사람의 평가로 봐야 한다.

## 5. 확인한 것과 못 한 것

**개발 환경(가짜 카카오 · 가짜 토스 · 가짜 AI, 로컬 Postgres 16 + 실제 브라우저)에서 확인함**

- 단위 테스트: 고민 낱말 고르기 · 형식 검사 · 내용 차이 검사(반영 · 기존 리포트 베끼기 · 일반 해석 차단) · 생성기(고쳐 쓰기 · 실패) · 서비스 흐름(저장과 발급 분리, 별도 기록 · 주문 · 리포트, 기존 리포트 보존, 되돌려 저장, 더블 클릭, 재시도, 지우기, 소유자 확인, MY, 탈퇴).
- DB 시험 (`npm run test:db`): 접근 정책(본인 조회만 · 브라우저 직접 쓰기 거부) · 소유자 불일치 거부 · 고치기 거부 · 내용 지우기만 허용 · 같은 저장본 하나 · 상품 번호별 주문 하나 · 탈퇴 삭제 · **11번 적용 전(표 없음)에도 기존 화면 · 결제가 동작하고 발급만 막힘**.
- 브라우저 시나리오 21개 + AI 미연결 1개 (390px · 1440px, 가로 넘침 없음): 작성 기록 없음 → 작성 → 저장(주문 · 리포트 · 기록 없음, AI 호출 없음) → 같은 내용 저장 → 더블 클릭 → 결제(4,900원) → 기록의 리포트 → 기존 리포트 해시 불변 → 고쳐 저장하면 버튼 재활성화 → 두 번째 발급(주제 바꿈, AI에 이전 리포트 · 기존 리포트 요지 전달) → MY 구분 → 생성 실패(일반 해석을 내용 차이 검사가 막음) → 같은 발급 건 재시도(주문 증가 없음) → 내용 지우기 → 다른 회원 접근 불가.
- 가짜 AI(모의 작성기)가 쓴 글에 대한 내용 차이 측정 한 예: 고객 낱말 20/20 반영, 기존 리포트와 같은 문단 0%, 새로운 말의 평균 몫 86%. **이것은 모의 작성기가 고객의 말을 받아 조립한 글에 대한 값이며 실제 AI의 품질이 아니다.**

**아직 확인하지 못함 (미완료)**

- **실제 AI의 글 품질**: 실제 AI 제공사가 연결되지 않았고 예산도 승인 전이다. 그래서 새 리포트가 개인 통합 리포트와 충분히 다르고 상황별 제안이 구체적인지는 실제 글로 확인하지 못했다. 연결 뒤 가려 읽기 평가(`ai-quality-comparison-plan.md`와 같은 방식)로 확인하고, 내용 차이 검사의 기준도 실제 글로 다시 맞춰야 한다.
- 실제 토스 서버에서의 4,900원 결제 · 환불 흐름 (개발 환경은 가짜 토스).
- 실제 Supabase에서의 11번 적용 · 접근 정책 · 탈퇴 (개발 환경은 로컬 Postgres). 적용 방법은 [`update-guide.md`](./update-guide.md) 2장.
- 실제 휴대폰(카카오톡 인앱 · iPhone Safari)에서의 화면.
- 약관 · 처리방침에 "고민 기록 · AI 해석 서비스로의 전달 · 탈퇴 시 삭제" 반영 (`TERMS_VERSION` 올리기 포함).

## 6. 운영자가 정해야 하는 것

1. **가격 4,900원 확정** — 지금은 가안이다. 실제 AI의 글을 읽어 본 뒤 정하는 것을 권한다.
2. **최초 구매에 무료 발급을 포함할지** — 지금은 포함하지 않는다. 포함한다면 결제 없는 발급 경로를 따로 설계해야 한다 (현재 코드에는 없다).
3. 발급 가능 횟수 상한이 필요한지 (지금은 상한 없음 — 매번 결제하므로 비용은 매출과 함께 움직이지만, AI 비용 · 하루 예산 장치는 그대로 적용된다).

## 7. 문의 · 운영

[`runbook.md`](./runbook.md) 2장의 "고민 리포트" 항목을 본다. 요약: 결제는 됐는데 리포트가 안 열리면 주문번호로 `/admin` 검색 → 리포트 상태 확인 → 같은 발급 건으로 다시 만들기. 환불은 기존과 같이 토스 관리자에서 취소하면 미유가 "환불됨"으로 맞추고 그 기록의 리포트 열람 권한이 사라진다.
