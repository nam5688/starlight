# DB 변경 19~25번 — 운영 적용 계획 (백업 · 순서 · 확인 · 되돌리기)

> **운영 DB 적용은 승인되지 않았다(운영자 2026-10-17). 이 문서는 계획이다 — 어떤 번호도 운영 DB에 실행하지 않았다.** 19~25번은 모두 개발용 임시 DB(로컬 Postgres)에서만 적용해 확인했다. 먼저 **별도의 스테이징 Supabase 프로젝트**에서 `docs/staging-test-plan.md`를 끝낸 뒤에, 운영자가 운영 적용을 따로 승인했을 때만 아래 순서를 쓴다.

## 2. 적용 전에 (운영자 · 순서 고정)

1. **스테이징 시험을 끝낸다**(`staging-test-plan.md`의 모든 줄이 통과 또는 사유 기록).
2. **백업**: Supabase 대시보드 → Database → Backups에서 최신 자동 백업이 있는지 확인하고, 가능하면 지금 시점의 수동 백업(또는 `pg_dump`)을 따로 받아 둔다. 백업 시각과 이름을 적어 둔다. (자동 백업의 보관 기간 · 복원 방법은 이용 중인 Supabase 요금제에 따라 다르며 이 문서가 확인한 값이 아니다.)
3. **적용 전 상태 기록**: `supabase/check-migrations.sql`을 SQL Editor에서 실행해 결과 표를 그대로 저장한다(19~25번이 모두 "아직 안 함"이어야 하고, 1~18번이 "적용됨"이어야 한다. 하나라도 다르면 멈추고 결과를 알려 준다).
4. **적용 전 데이터 확인(읽기 전용)**:
   - 25번이 방문 단계 이름 검사를 새 목록으로 바꾼다. 기존 행이 새 목록 밖의 이름을 갖고 있으면 25번이 실패한다 — 미리 `select name, count(*) from public.funnel_events group by name order by 2 desc;` 로 이름이 `visit · analyze_start · analyze_complete · preview_view · report_view`뿐인지 본다.
   - 20번이 `orders`의 금액 제약을 바꾼다 — `select count(*) from public.orders where amount <= 0;`이 0인지 본다.
5. 코드(앱)를 이 DB 변경과 **같은 버전**으로 배포해 둔다(순서는 코드 먼저 → DB 나중이 안전하다). 판매 스위치 · 혜택 스위치는 모두 꺼진 상태로 둔다.
6. 점검 시간대를 정한다(주문이 진행 중이지 않을 때 — 20번이 `orders`의 제약을 잠깐 바꾼다).

## 3. 적용 순서 (한 번에 하나씩, 매번 확인)

번호 순서 **19 → 20 → 21 → 22 → 23 → 24 → 25**로 SQL Editor에서 파일 하나씩 실행한다. **19번이 있어야 20 · 21 · 22 · 25가, 22번이 있어야 이후가** 맞게 동작하므로 순서를 바꾸지 않는다(함수 · 설정 · 트리거가 앞 번호에 기대는 곳이 있다).

각 파일마다:
1. 파일 전체를 `begin;` 과 `commit;` 사이에 붙여 실행한다(오류가 나면 `rollback;` — SQL Editor가 파일을 한 트랜잭션으로 실행하는지 이 문서가 확인하지 못했으므로 직접 감싼다. 19~25번 파일에는 `begin` · `commit`이 없다).
2. 끝나면 `check-migrations.sql`을 다시 실행해 **방금 번호가 "적용됨"**인지 본다. "일부만"이면 그 번호는 멈추고 결과를 알려 준다(다음 번호로 가지 않는다).
3. 앱의 기존 핵심 화면(홈 · 무료 분석 · 로그인 · 결과 · MY)이 그대로 열리는지 본다.

번호별 추가 확인:

| 번호 | 확인 |
| --- | --- |
| 19 | `select count(*) from public.benefit_settings;`이 0보다 크고 `select key, value from public.benefit_settings where key like 'feature.%';`의 값이 모두 false |
| 20 | 기존 주문 수가 그대로(`select count(*) from public.orders;` 적용 전후 같음) · 앱에서 가짜(테스트) 주문을 한 건 시작해 결제 화면까지 열리는지 |
| 21 | `check-migrations.sql` 21번 줄 "적용됨" |
| 22 | **탈퇴 함수가 바뀐다** — 시험 계정으로 탈퇴 흐름이 되는지 스테이징에서 먼저 봤는지 확인(운영에서는 실제 회원 탈퇴를 시험하지 않는다) |
| 23 · 24 · 25 | check 줄의 모든 항목(표 · 함수 · 트리거 · 서버 권한)이 true |

## 4. 적용 뒤

1. `check-migrations.sql` 최종 결과가 1~25번 모두 "적용됨"인지 저장한다.
2. **스위치는 그대로 꺼 둔다.** 켜는 것은 각각 별도 승인이다: 혜택 스위치(관리자 `/admin/benefits`) · 사주 궁합 · 리포트 궁합 판매 스위치(코드 상수) · 후기 보상(`feature.review_reward`). 판매 스위치는 실제 AI 검증과 결제 QA를 마치기 전에는 열지 않는다.
3. 운영 기록(`/admin`)에서 새 오류(예: `42P01` 외의 DB 오류)가 없는지 본다.

## 5. 되돌리기 계획

- **마이그레이션은 되돌리는 파일을 만들지 않는다**(더하기만 하는 규칙). 문제가 생기면 **새 마이그레이션**으로 고친다.
- **코드 되돌리기와 DB 되돌리기는 따로 판단한다.** 앱을 이전 버전으로 되돌려도 새 표 · 열은 남지만 이전 코드는 그것을 쓰지 않으므로 동작에 영향이 없다(새 열은 모두 비어 있어도 되거나 기본값이 있다).
- **새 기능을 끄는 것이 되돌리기다**: 혜택 스위치를 모두 끄고(`/admin/benefits` 또는 설정 함수) · 판매 스위치는 코드에서 꺼져 있고 · 후기 보상은 끄면 지급이 멈춘다. 새 표는 비어 있는 채로 남는다.
- **데이터를 지우는 되돌리기는 하지 않는다**(새 표를 삭제하지 않는다 — 탈퇴 · 환불 기록과 어긋날 수 있다). 꼭 필요하면 백업 시점으로의 복원은 운영자가 별도로 판단한다(복원은 그 시점 이후의 주문 · 결제 기록도 되돌리므로 마지막 수단이다).
- 20번이 바꾼 `orders` 금액 제약은 새 제약(`amount > 0` 이거나 혜택 주문의 0원)이 기존 제약을 포함하므로 되돌릴 필요가 없다. 0원 주문은 `grant_benefit_order` 함수 없이는 만들어지지 않는다(트리거가 막고 DB 시험이 확인).
- 25번이 바꾼 `funnel_events` 이름 검사는 새 이름 2개를 더한 **나열형**이라 결제 이벤트 같은 이름은 계속 거절된다(DB 시험 확인).

## 6. 확인한 것 · 확인하지 못한 것

- 확인(개발용 임시 Postgres 16, 마이그레이션 1~25번을 처음부터 순서대로 적용): 전체 DB 시험 91개 통과(`npm run test:db`) · `check-migrations.sql` 24 · 25번 줄 "적용됨" · 표가 없는 상태에서 앱이 깨지지 않음.
- **확인하지 못한 것**: 실제 Supabase 프로젝트(스테이징 · 운영)에서의 적용 · 실제 운영 데이터의 모양(위 2장 4번의 읽기 전용 확인으로 미리 본다) · Supabase SQL Editor의 트랜잭션 동작 · 백업 · 복원의 실제 절차와 시간 · 점검 시간대의 주문 동시성.
