# 회원 탈퇴 — 구현된 동작(초안)과 정책 결정 항목

- 상태: **기능은 구현됨, 정책은 초안.** 아래 "결정 필요" 항목이 확정되면 문구 · 보관 기간을 고친다. 약관 · 개인정보 처리방침 확정 전에는 공개하지 않는다.
- 코드: `lib/membership/withdrawal.ts`(안내 문구 · 보관 기간) · `lib/services/member-service.ts`(`withdrawMember`) · `supabase/migrations/20261020000000_account_withdrawal.sql`(DB 함수 `withdraw_member_data`) · `app/my/withdraw/`(화면 · 서버 동작)
- 검증: 단위 테스트 5개 · DB 테스트(실제 DB 위에서 삭제 · 보관 · 권한 · 반복 호출) · 브라우저 8개 시나리오 (개발 클라우드, 가짜 카카오). **실제 Supabase · 카카오 환경에서는 확인하지 않았다** (특히 Supabase Auth의 탈퇴 처리가 호스팅에서도 같은 결과인지).

## 1. 지금 동작하는 방식

MY → "회원 탈퇴" → 지워지는 것 · 남는 것 안내 → 확인 체크 + "탈퇴" 입력 → 탈퇴 → 완료 화면.

| 구분 | 처리 |
| --- | --- |
| **삭제** | 검사 결과(닉네임 · 생년월일 · 출생시간 · MBTI · 응답 · 사주 계산 결과), 구매한 리포트 내용(개인 통합 · 내 고민 반영 리포트), 내 고민 자세히 알려주기 입력과 발급 때 남긴 고민 기록(그때 적은 내용), 저장된 대화(`talk_rooms` — 눌렀던 행동과 자유 질문 · 미유의 답)와 질문 횟수 기록(`chat_questions`), 채팅 요약(`chat_summaries` — 직접 저장한 요약과 저장하지 않고 끝낸 대화의 참고 기록 모두), 맛보기 리포트(`taste_reports` — AI가 쓴 글, 17번 DB 변경이 탈퇴 함수에 삭제 한 단계를 더함), 리포트 만족도, 거주 · 활동 지역, 프로필 닉네임 |
| **비움** | 주문이 가리키는 검사 행은 지우지 않고 내용만 비운다 (주문과의 연결 유지를 위한 빈 껍데기, 생년월일 자리는 형식 맞춤용 1900-01-01) |
| **보관** | 주문 · 결제 기록(주문번호 · 금액 · 결제 시각 · 승인 / 취소 기록), 가입 동의 기록(동의 항목 · 약관 버전 · 시각) |
| **로그인 연결** | Supabase Auth의 탈퇴 처리로 카카오 식별 정보 · 이메일 · 프로필 정보를 지운다 (계정 행은 남겨 주문 기록과의 연결을 유지). 같은 카카오 계정으로 다시 가입하면 **새 계정**이 만들어지고 이전 결과는 복구되지 않는다 |
| **막는 경우** | 결제 확인 중인 주문(1시간 이내)이나 리포트 생성 중이면 탈퇴하지 않고 이유를 알린다 |
| **순서** | ① DB 개인정보 삭제(한 번에 처리, 여러 번 해도 같은 결과) → ② 로그인 연결 삭제. ②가 실패해도 ①은 끝난 상태이므로 같은 화면에서 다시 누르면 마무리된다 |
| **분석 기록** | 방문 단계 기록(`funnel_events`)은 익명 번호만 있어 회원과 연결되지 않으므로 삭제 대상이 아니다. 운영 기록(`ops_events`)에는 고객 정보가 없다 |
| **운영 기록** | 탈퇴가 처리되면 개인정보 없이 `member.withdrawn`(삭제된 건수)을 남긴다 |

## 2. 정책 결정이 필요한 것 (구분해서 정한다)

| # | 결정 | 지금(초안) | 선택지와 고려할 점 |
| --- | --- | --- | --- |
| 1 | **주문 · 결제 기록 보관 기간** | 5년 가정 | 전자상거래 관련 법령은 대금결제 · 재화 공급 기록 5년, 계약 · 청약철회 기록 5년, 소비자 불만 · 분쟁 기록 3년을 두는 것으로 알려져 있다. 세무 증빙은 별도 기준이 있을 수 있다. **법률 · 세무 검토로 확정.** 처리방침에도 같은 기간을 적어야 한다 |
| 2 | **보관하는 항목** | 주문번호 · 금액 · 결제 시각 · 승인 / 취소 기록 | 결제 기록의 상점 ID · 결제수단 종류도 남는다. 더 줄일 수 있는지(예: 결제수단 종류 제외) 검토 |
| 3 | **보관 기간이 지난 기록의 삭제** | **미구현** | 기간이 지난 주문 · 결제 기록과 계정 껍데기를 지우는 정기 작업이 필요하다 (보관 기간 확정 뒤 새 마이그레이션 + 점검 작업으로) |
| 4 | **동의 기록 보관** | 보관 (탈퇴 후에도) | 동의했다는 증빙으로 보관하는 것이 일반적이나 기간 · 근거를 처리방침에 적어야 한다 |
| 5 | **구매한 리포트 삭제 시점** | 탈퇴 즉시 삭제 (복구 불가) | 일정 기간(예: 14~30일) 유예해 탈퇴를 철회할 수 있게 할지. 유예하면 그 기간 개인정보가 남는다 — 처리방침에 적어야 한다 |
| 6 | **환불 가능 기간 안의 탈퇴** | 막지 않음 (안내만: "환불이 필요하면 탈퇴 전에 문의") | 환불 · 청약철회 가능 기간에 탈퇴하면 환불 처리 때 본인 확인이 어렵다. 막을지 · 안내만 할지 결정 |
| 7 | **재가입** | 제한 없음 (새 계정) | 탈퇴 후 일정 기간 재가입 제한이 필요한지 (보통 불필요) |
| 9 | **저장된 대화의 보관 기간**(2026-10-15 서버 저장 도입) | 회원이 방마다 "새로 시작하기"로 지우거나 탈퇴할 때까지 보관(오늘의 한 장 방은 저장할 때 지난 날짜를 함께 지움). 질문 횟수 표는 질문 내용 없이 누가 · 언제 · 어느 방만 담고 탈퇴 때 삭제 | 자유 질문 · AI 답은 고민처럼 사적인 이야기일 수 있다. 일정 기간(예: 마지막 대화 뒤 1년) 지난 대화를 자동으로 지울지, 질문 횟수 기록을 며칠 뒤 지울지(하루 한도만 세면 되므로 짧아도 된다) 정한다 — 정하면 정기 작업 + 새 마이그레이션 |
| 11 | **채팅 요약의 보관**(2026-10-15 도입, 14번 DB 변경) | 직접 저장한 요약은 회원이 지우거나 탈퇴할 때까지 보관(최대 100개). **저장하지 않고 끝낸 대화는 보이지 않는 참고 기록으로 남기되 90일 뒤 자동 삭제**(운영자 결정 2026-10-15, 방마다 최근 12개까지만, 다음 질문에서 AI가 참고) — 회원이 MY의 "이전 대화 기록 모두 지우기"로 먼저 지울 수 있고 탈퇴 때 함께 삭제. 대화 종료 안내창과 처리방침 3-1에 알린다 | 정기 점검이 매시 도는 것이 전제다(미연결이면 기간이 지난 기록을 쓰지 않을 뿐 지우지는 못한다). 90일이 적당한지 · 직접 저장한 요약의 보관 기간을 둘지 |
| 10 | **결제해 두고 쓰지 않은 질문이 있는 탈퇴**(2026-10-15 도입, 선불 충전은 없앴다 — 예전 충전 잔액도 같은 규칙) | **남아 있으면 탈퇴를 막고 안내**한다. 장부 · 내역은 주문 · 결제 기록처럼 거래 기록으로 남고(질문 · 답 내용 없음) 보관 기간은 1번과 같게 가정 | 환불 기준(`docs/question-payment.md` 3절)이 정해지면 "환불 후 탈퇴"로 바꿀지, 소멸 안내 후 탈퇴 가능으로 할지 정한다 |
| 8 | **개인정보 열람 · 정정 · 삭제 요청의 다른 경로** | 내 고민 자세히 알려주기는 직접 고치고 지울 수 있음. 그 밖은 문의 | 이메일 · 문의 창구와 응답 기한을 처리방침에 적는다 |

## 3. 이 구현을 바꾸는 방법

- 안내 문구 · 보관 기간 표시: `lib/membership/withdrawal.ts` (고친 뒤 `npm run check`).
- 삭제 · 보관 범위: DB 함수가 처리하므로 **새 마이그레이션**으로 함수를 교체한다 (이미 적용한 파일은 고치지 않는다). 바꾸면 DB 테스트(`supabase/tests/db.test.ts`의 탈퇴 테스트)도 같이 고친다.
- 문구와 DB 처리가 같은지는 단위 · DB 테스트가 확인한다.
