# 운영 매뉴얼 (runbook)

고객 문의 · 알림이 왔을 때 무엇을 보고 무엇을 하는지 적었다. **미유는 환불을 실행하지 않는다** — 환불은 토스페이먼츠 관리자에서 운영자가 직접 하고, 미유는 결제사의 취소 기록을 보고 주문을 "환불됨"으로 맞춘다. 주문 · 결제 상태를 손으로 "결제 완료"로 바꾸는 기능은 없으며, 만들지 않는다 (결제사의 실제 기록만 기준).

공개 배포 전에는 아래 절차 중 **확인되지 않은 것**(표시된 부분)을 먼저 끝낸다. 상태 · 검증 환경은 [`launch-checklist.md`](./launch-checklist.md).

## 1. 매일 · 매주 보는 것

- **고객 문의는 카카오톡 채널 "미유톡"의 CS 전용 상담톡으로 온다**(`http://pf.kakao.com/_xjxnqmX/chat`, 사이트 하단 · 약관 9조에 표시). 문의 대응 순서는 아래 표를 따른다. 상담톡에는 비밀번호 · 카드번호 · 키를 받지 않고 주문번호 · 결제 시각 · 닉네임만 받는다.
- **관리자 화면 `/admin`** (ADMIN_USER_IDS에 내 회원번호가 있을 때만 열린다): "지금 처리할 것"의 숫자가 0이면 조치할 것이 없다.
  - 결제 확인 대기 · 리포트 생성 실패 · 생성 지연 · 최근 24시간 오류 · 새 구매 상태 · 대기 / 생성 중 · 오늘 AI 비용
  - "결제 · 리포트 전체 점검 지금 실행"으로 정기 점검을 바로 돌릴 수 있고, "알림 시험"으로 알림이 가는지 확인한다.
- **사업 지표 `/admin/metrics`**: 단계별 흐름 · 광고 채널 · 순매출 · AI 비용 · 만족도. 매출은 실결제만 센다 (테스트 · 중복 의심은 따로 표시).
- 텔레그램을 연결했다면 알림만 봐도 된다 (같은 문제는 6시간에 한 번만 온다). 알림에는 주문번호 · 오류번호 · 종류만 있고 고객 정보는 없다.
- 한 달에 한 번 `npm run deps` (의존성 점검).

## 2. 고객 문의별 대응

| 문의 | 확인 | 조치 |
| --- | --- | --- |
| "결제했는데 리포트가 안 보여요" | 고객에게 **주문번호**(MY → 결제내역)를 받아 `/admin`에서 검색 → 결제 상태 · 결제 처리 기록 · 리포트 상태 | ① 결제 `대기`인데 결제사에 승인 기록이 있으면 **"결제사와 대조해 맞추기"** (결제사 기록을 보고 결제 완료로 맞추고 리포트 준비를 시작) ② 결제사에도 기록이 없으면 청구되지 않은 것 — 다시 결제를 안내 ③ 고객은 MY → 주문 상세의 "결제사에 다시 확인하고 맞추기"를 직접 눌러도 된다 |
| "결제가 두 번 됐어요" | 주문번호로 검색 → 결제 처리 기록에 `DUPLICATE_PAYMENT` / 운영 기록에 `reconcile.anomaly` | 토스 관리자에서 **중복된 결제를 취소(환불)**. 취소가 반영되면 재확인이 주문을 "환불됨"으로 맞춘다. 미유 쪽 구매 권한은 처음 결제한 주문 하나만 있다 |
| "결제 확인 중이라고만 나와요" | 주문 상태 `결제 확인 중` (결제를 시작한 지 1시간 안) | **다시 결제하지 말라고 안내.** 자동으로 맞춰진다(화면을 열 때 · 5~10분마다 정기 점검). 1시간이 지나도 결제사에 기록이 없으면 "결제 미완료"로 정리된다. 결제사 조회가 계속 실패하면 `reconcile.error` 알림이 온다 |
| "오류가 났어요 (오류번호 ERR-…)" | `/admin` 검색창에 오류번호 | 운영 기록의 종류 · 주문번호 · 시각을 본다. `server.error`는 화면 오류, `confirm.save_failed`는 결제사 승인 후 저장 실패(재확인이 자동으로 맞춤) |
| "리포트가 너무 오래 걸려요" | 주문 → 리포트 상태 · 시도 횟수 · 마지막 오류 | 30분 넘으면 고객 화면에 "평소보다 오래 걸림 · 환불 문의 가능" 안내가 나간다. 관리자 **"리포트 다시 만들기"**(시도 횟수 상한과 별개). 계속 실패하면 환불 판단 |
| "환불해 주세요" | 결제 · 리포트 상태 확인 | 정책(약관 확정 전)에 따라 토스 관리자에서 취소 → 재확인이 "환불됨"으로 맞추고 열람 권한이 사라진다. **질문 3개 묶음(유료 질문) 주문은 부분 환불도 장부에 반영된다**(DB 16번 이후에 결제한 묶음 · 정책은 아직 확정 전이라 개별 판단). 절차: ① `/admin`에서 그 주문번호를 찾는다 → "이 묶음의 사용 · 환불"과 **"환불 금액 안내"**(예: 질문 1개 환불 → 834원)를 본다 ② 토스 관리자에서 **안내된 금액만큼** 부분 취소한다(누적 환불액이 결제액 2,500원을 넘지 않는 값이다. 이미 쓴 질문은 안내에 없다) ③ **같은 화면의 [결제사와 대조해 맞추기]를 한 번 누른다**(웹훅이 오지 않았을 때 맞춘다 — 이미 반영됐으면 "일치합니다". 누르지 않아도 **고객이 그 질문을 쓰는 순간 결제사 기록을 다시 확인해 환불이 먼저 반영되고**, 남은 질문이 있는 묶음은 결제한 지 7일이 지나도 정기 점검이 계속 본다 — 그래도 눌러서 바로 확인하는 것을 운영 절차로 둔다) ④ 다시 보면 환불 수 · 남은 질문이 줄어 있다. **안내된 금액이 아닌 값으로 취소하면 미유는 질문을 회수하지 않고 `PARTIAL_REFUND_MISMATCH` 확인 필요 알림을 보낸다**(맞는 누적 금액 834 · 1,667 · 2,500원이 알림에 적혀 있다 — 이미 취소된 금액은 되돌릴 수 없으니 남은 질문을 어떻게 할지 운영자가 판단한다). **16번 전에 결제한 묶음**은 묶음 장부가 없어 `PARTIAL_REFUND_NO_PACK`으로 알리고 자동 반영하지 않는다(질문은 운영자가 직접 판단). 환불받은 질문 중 이미 쓴 질문이 있으면(전액 취소 · 환불 중 사용) "회수하지 못한 몫"으로 남고 `check-cash.sql`에도 나온다. 카드 부분 취소는 토스가 영업일 3~4일이 걸린다고 안내한다. 환불 신청을 받는 화면 · 문의 채널은 아직 없다([`question-pack-policy-proposal.md`](./question-pack-policy-proposal.md)) |
| "환불해 주세요" — **토스에서 취소가 안 돼요** (카드 결제 후 1년 이상 등) | 토스 관리자의 취소 실패 문구 · 주문번호 · 결제 시각 | **계좌 송금 환불(수동 · 기록 절차, 정책은 확정 전 — `question-pack-policy-proposal.md` P8)**: ① 취소 실패 문구와 주문번호를 메모(계좌 · 이름은 적지 않는다) ② 고객에게 계좌 송금 환불을 안내하고 본인 확인(주문번호 · 결제 시각 · 닉네임, 질문 내용 · 생년월일은 받지 않는다). 계좌는 상담톡(카카오 채널)으로 받으므로 **상담 기록에 남는다** — 송금 뒤 대화 삭제를 권하고 미유 DB · 이 절차의 기록에는 적지 않는다 ③ SQL Editor에서 **`supabase/manual-refund-check.sql`**(읽기 전용, 주문번호만 바꿈)을 돌려 "송금할 금액" 표를 본다(질문 1개 834원 · 2개 1,667원 · 3개 2,500원에서 **이미 환불한 누적액을 뺀 금액**) ④ **은행에서 그 금액을 고객에게 직접 송금한다**(미유는 송금하지 않는다) ⑤ **`supabase/manual-refund-apply.sql`**의 세 값(주문번호 · 환불해 준 질문 개수 · 메모)만 바꿔 돌린다 → 그 묶음의 "환불한 질문"이 늘고 지갑에서 남은 질문이 회수되며 운영 기록(`admin.manual_refund`: 주문번호 · 질문 수 · 송금액 · 메모)이 남는다. **오류가 나면 아무것도 바뀌지 않은 것이다**(메모에 계좌 · 전화번호처럼 숫자가 9자리 넘게 이어지면 거부한다) ⑥ check 파일을 다시 돌려 환불한 질문 · 남은 질문 · "지난 송금 환불 기록"을 확인한다. **지켜야 할 것**: 한 주문은 한 가지 방법으로만 환불한다(토스에서 취소했거나 취소할 주문은 이 절차로 반영하지 않는다) · 이 절차는 주문 상태를 바꾸지 않아(결제 완료 그대로) 결제 재확인이 이상으로 보지 않지만 **사업 지표의 매출에는 송금 환불이 빠지지 않는다**(운영 기록의 송금액을 직접 뺀다) · 송금 직전에 고객이 질문을 쓰면 회수하지 못한 몫으로 남으니 ③과 ⑤ 사이를 짧게 둔다 · 묶음 장부가 없는 예전 주문(DB 16번 전)은 이 절차로 처리하지 않는다. 현금영수증 · 매출 취소 등 세무는 세무사 확인 항목이다. 자주 생기면 `/admin` 버튼 + DB 17번 함수로 바꾼다(미구현) |
| 고객이 "언제 답을 주나요 / 환불은 언제 되나요?" | — | **세 가지를 따로 답한다**(`question-pack-policy-proposal.md` P9): ① 문의 첫 답변은 고객센터 운영 시간(**운영자 확정 전**) ② 환불 **처리 기한**은 사업자 약속(**확정 전**, 적용 법령 확인 뒤) ③ 카드는 처리 뒤 카드사에서 실제로 돌아오는 데 토스 안내로 매입 전 취소는 바로, **매입 후 취소 · 부분 취소는 요청 후 영업일 기준 3~4일**(카드사에 따라 다를 수 있음). "3영업일 안에 답변"과 "3영업일 안에 환불"을 한 문장으로 약속하지 않는다 |
| "고민 리포트를 발급했는데 안 열려요 / 만들지 못했대요" | 주문번호(MY → 결제내역, 상품 "내 고민 반영 리포트")로 `/admin` 검색 → 리포트 상태 · 시도 횟수 · 마지막 오류 | 결제가 완료이고 리포트가 `실패`면 고객 화면(나의 고민 기록소 → 그 기록의 리포트)에서 **"같은 발급 건으로 다시 만들기"**를 누르게 한다 — **추가 결제 없음, 새로 결제하라고 안내하지 않는다.** 마지막 오류가 "고민 리포트 검사 실패 … 고민의 말이 해석에 거의 나오지 않습니다 / 이미 준 개인 종합 리포트와 거의 같은 문단"이면 AI가 고민을 반영하지 못한 글을 쓴 것이라 저장하지 않은 것이다(정상 동작). 반복되면 관리자 "리포트 다시 만들기" → 그래도 안 되면 환불 판단 ([`concern-records.md`](./concern-records.md) 4장) |
| "고민을 고쳤는데 예전 리포트가 안 바뀌어요" | — | 정상이다. 발급할 때 그 순간의 고민이 기록으로 남고 리포트는 그 기록을 바탕으로 한 별도 리포트다. 고친 고민으로는 "이 고민으로 새 리포트 발급"(4,900원 가안)을 따로 누른다. 기존 리포트는 덮어쓰지 않는다 |
| "발급 버튼이 안 눌려요 / 비활성화예요" | 화면 안내 문구 | 개인 통합 리포트를 구매하지 않았거나(기존 구매자 전용) 아직 만드는 중이거나 AI가 연결되지 않은 경우다. 문구가 이유를 알려 준다. "DB 변경 11번" 문구면 11번 마이그레이션이 필요하다 |
| "고민 내용만 지워 주세요" | 고객이 직접 가능 | 나의 고민 기록소(현재 고민 지우기) · 기록의 리포트 화면(그때 적은 고민 지우기). 리포트가 만들어지는 중이거나 실패해 다시 시도해야 하는 동안에는 지울 수 없다. 리포트 본문에 AI가 받아 쓴 문장은 남는다 |
| "내 정보를 지워 주세요 / 탈퇴하고 싶어요" | MY → 회원 탈퇴 (결제 확인 중이거나 리포트 생성 중이면 완료 뒤에 안내) | 고객이 직접 한다 (`/my/withdraw`). 개인정보는 바로 삭제되고 주문 · 결제 기록만 이름 없이 보관된다. 환불이 필요하면 **탈퇴 전에** 처리해야 한다. 보관 기간 · 항목은 정책 확정 전 초안 ([`withdrawal-policy.md`](./withdrawal-policy.md)). 탈퇴 오류가 나면 오류번호로 검색 — "DB 변경 10번" 문구면 마이그레이션 10번 적용 필요 |
| "질문을 결제했는데 질문이 안 들어왔어요" (유료 질문, 3개 묶음 2,500원) | 고객에게 **주문번호**(MY → 결제내역, 상품 "유료 질문 3개")를 받거나 `/admin`의 **최근 주문 30건**에서 닉네임 · 결제 시각 · 금액으로 찾아 주문번호를 눌러 조회 → "질문 장부" 행 | ① 결제 상태가 `결제 확인 중`이면 **"결제사와 대조해 맞추기"** (결제사에 승인 기록이 있으면 결제 완료로 맞춰지고 질문은 그 처리 안에서 자동으로 들어간다) ② 결제 `완료`인데 장부에 질문이 없다고 나오면 **"결제사 확인 후 질문 넣기"** — 버튼이 결제사 기록을 **다시 조회해 결제 완료로 확인될 때만** 주문에 적힌 만큼(묶음이면 질문 3개)을 넣는다(주문 한 건에 한 번만, 이미 들어가 있으면 더 넣지 않음, 환불 · 금액 불일치 · 결제사에 기록 없음이면 넣지 않음). 운영 기록에 `admin.credit_question`이 남는다 ③ "이 DB에는 아직 질문 수동 반영 기능이 없습니다"가 나오면 SQL Editor에서 **15번 파일**(`20261025000000_admin_credit_question.sql`)을 먼저 실행 ④ 결제가 안 된 주문 · 결제사에 기록이 없는 주문은 청구되지 않은 것이라 질문을 넣지 않는다 ⑤ 질문이 이미 들어가 있는데 안 보인다는 문의면 장부의 "쓸 수 있는 결제한 질문 N개"를 확인 — 고객은 그 방에서 결제 없이 바로 묻는다 |
| "다른 계정으로 로그인해서 내 리포트가 안 보여요" (카카오 ↔ 이메일, 카카오 계정이 둘 등) | 리포트는 결제한 **로그인 계정**에 붙어 있다. 먼저 처음 로그인한 방법(카카오 / 이메일)으로 다시 로그인해 보게 안내 | 그래도 안 되면 `/admin`의 **최근 주문 30건**에서 닉네임 · 결제 시각 · 금액으로 주문을 찾고(닉네임은 검사할 때 적은 이름, 회원번호 앞 8자로 같은 사람인지 가린다) 고객이 말한 주문번호 · 결제 시각 · 카드 승인 문자와 맞는지 **운영자가 본인 확인**한 뒤 → 조회 화면의 **"저장된 리포트 보기"**(읽기 전용, 열람이 운영 기록 `admin.view_report`에 남는다)에서 **글로 복사해 보내기** 또는 화면 캡처로 보낸다. **주문 · 리포트의 소유 계정을 다른 계정으로 옮기는 기능은 없다**(결제 기록의 소유자를 바꾸는 일이라 만들지 않았다). 채팅 대화 · 고민은 운영자 화면에 나오지 않으므로 보내 줄 수 없다 |
| "채팅 대화를 복구해 주세요 / 탈퇴 · 대화 삭제 뒤에 되살려 주세요" | 고객이 방의 "새로 시작하기"나 탈퇴로 지운 것인지 확인 | **복원하지 않는다.** 지우면 서버에서도 지워지고(탈퇴 시 개인정보 · 리포트 · 대화 모두) 백업에서 개별 회원만 되살리는 절차도 만들지 않았다 — 정책상 맞다 ([`withdrawal-policy.md`](./withdrawal-policy.md)). 저장해 둔 채팅 요약은 MY → 저장한 채팅 요약에서 고객이 직접 본다. 환불이 필요한 결제는 탈퇴 **전에** 처리해야 한다 |

## 3. 알림 종류와 뜻

| 알림 종류 (`kind`) | 뜻 | 할 일 |
| --- | --- | --- |
| `payment.approved` (정보) | 서버가 결제사 승인을 확인해 주문이 결제 완료로 바뀜 (주문당 한 번, 실결제가 아니면 `[미유·테스트]`) | 할 일 없음 (매출 확인용) |
| `payment.non_card` (주의) | **카드 외 결제수단**(계좌이체 · 가상계좌 · 간편결제 · 휴대폰 등)으로 승인됨 — 출시 초기에는 카드만 운영한다(`LAUNCH_PAYMENT_METHODS`) | 결제는 정상 처리된다. 토스 개발자센터의 결제위젯 설정에서 카드만 보이게 되어 있는지 확인하고, 이 주문의 환불은 결제수단별 취소 가능 기간(계좌이체 180일 · 가상계좌 보통 365일 · 휴대폰은 결제한 달)을 확인해 진행 |
| `pack.verify_failed` (주의) | 고객이 결제한 질문을 쓰려는 순간 **결제사 기록을 확인하지 못해 확인 없이 진행**함(결제사 조회 장애 등 — 같은 주문은 하루 한 번만 알린다) | 질문은 막지 않았다. 토스 장애가 풀린 뒤 `/admin`의 **결제 재확인**(또는 정기 점검)이 환불된 질문을 맞춘다. 반복되면 토스 상태 · 키를 확인 |
| `payment.refunded` (정보) | 결제사 취소를 확인해 주문이 환불됨으로 바뀜 (주문당 한 번) | 환불 처리가 끝난 것 — 고객에게 안내 |
| `reconcile.anomaly` (오류) | 결제사 기록과 우리 주문이 다르다 (금액 불일치 · 중복 승인 · 결제 완료인데 결제사에 없음 등) | 주문번호로 검색 → 토스 관리자에서 해당 결제 확인. 자동으로 고치지 않는다 |
| `confirm.save_failed` (오류) | 결제사는 승인했는데 우리 저장이 실패 | 보통 정기 점검이 자동으로 맞춘다. 맞춰지지 않으면 "결제사와 대조해 맞추기" |
| `confirm.rejected_charged` (오류) | 승인된 결제를 반영하지 못함 (중복 등) | 환불 여부 판단 |
| `report.failed` (오류) / `report.delayed` (주의) | 리포트 생성 실패 / 15분 넘게 지연 | "리포트 다시 만들기". AI 제공사 상태 확인 |
| `sales.paused` (주의) | 리포트 준비가 밀리거나 하루 예산에 가까워 **새 구매를 멈췄다** (이미 결제한 고객은 계속 처리) | 대기열이 줄면 자동으로 다시 열린다. 한도를 바꾸려면 환경변수(`AI_*`) 조정 |
| `budget.warn` (주의) | 하루 AI 예산의 80% 사용 · 예약 | 비용 확인 |
| `server.error` (오류) | 처리하지 못한 화면 · 요청 오류 | 오류번호로 검색 |

## 4. 정기 점검 (cron)

`GET /api/cron/reconcile` (헤더 `Authorization: Bearer <CRON_SECRET>`)을 호출한다. **Vercel에서는 저장소의 `miyu/vercel.json`이 하루 한 번(UTC 18:17 = 한국 03:17 무렵) 호출하게 해 두었다** — Hobby 요금제는 하루 한 번만 허용되고 정해진 시(時) 안의 아무 때나 불리며(±59분), **Production 배포에서만 호출된다**(Vercel 공식 문서 2026-10-16). `CRON_SECRET` 환경변수를 넣으면 Vercel이 `Authorization: Bearer …`를 자동으로 붙인다. Pro 요금제 · 외부 예약 실행이면 5~10분마다로 바꿀 수 있다(`vercel.json`의 시각을 바꾸고 `server/vercel-config.test.ts`의 하루 한 번 검사도 함께 고친다). 하는 일: ① 오래 대기 중인 주문과 최근 7일 결제 완료 주문, **그리고 남은 질문이 있는 묶음(결제한 지 7일이 지나도)** 을 결제사 기록과 대조 ② 대기 · 멈춘 리포트 이어서 생성(최대 3건) ③ 실패 · 지연 리포트 알림 ④ 보관 기간(90일)이 지난 채팅 참고 기록 삭제(실행할 때마다) — 응답의 `purgedReferenceRecords`는 지운 개수 ⑤ 실행 흔적 남기기(운영 기록 `cron.heartbeat`, 50분에 한 번만 · 개수만 — `/admin`의 "정기 점검 마지막 실행"). `CRON_SECRET`이 없으면 주소가 닫혀 있다(503), 틀리면 401. 응답에는 개수만 있다.
- **확인되지 않음:** 실제 호스팅에서의 예약 실행(Vercel이 **보호된 배포에서도** 호출하는지는 문서에 없다) · 실행 시간 한도(리포트 생성이 길 때 — Vercel 함수는 Hobby 300초). 배포 뒤 첫 24시간 뒤 `/admin`의 "정기 점검 마지막 실행"이 찍혔는지 확인한다([`deploy-vercel-test.md`](./deploy-vercel-test.md) 9단계).
- **정기 점검이 하루에 한 번뿐이어도** 환불된 질문이 쓰이지 않게 하는 장치: 고객이 **결제한 질문을 쓰기 직전**에 그 회원의 남은 질문이 있는 묶음을 결제사 기록으로 다시 확인한다(부분 · 전액 취소를 장부에 먼저 반영). 결제사 조회가 실패하면 질문은 막지 않고 운영 기록 `pack.verify_failed`와 알림이 남는다.
- 남은 질문이 **없는** 묶음은 7일이 지나면 자동 대조 대상이 아니다(쓰이지 않을 질문이 없다). 오래된 구간을 맞춰야 하면 주문번호별로 "결제사와 대조해 맞추기"를 쓴다.

## 5. 백업과 복구

| 항목 | 상태 |
| --- | --- |
| **논리 백업 → 복구 절차** (`pg_dump` / `pg_restore`, public 스키마) | **검증됨 (로컬 DB, 2026-10-12)**: 복원 후 모든 표의 행 수가 원본과 일치(검사 309 · 주문 302 · 리포트 189 · 결제 기록 855 …), 완성 리포트 내용의 해시 일치, 고치기 방지 트리거 복원 확인 |
| Supabase 호스팅의 자동 백업 · 보관 기간 · 시점 복구(PITR) | **확인되지 않음** — 요금제에 따라 다르다. 공개 전에 Supabase 대시보드(Database → Backups)에서 내 요금제의 백업 주기 · 보관 기간을 확인하고, 필요하면 요금제를 올릴지 결정한다 |
| 호스팅 복구 리허설 (실제 프로젝트에서 복구 시험) | **미완료** — 공개 전에 새 임시 프로젝트로 한 번 해 본다 |

개발자용 복구 절차(검증한 방식):
1. `pg_dump -d "<연결 문자열>" --no-owner --no-privileges --schema=public -Fc -f miyu-backup.dump` (연결 문자열은 비밀이므로 대화창에 쓰지 않는다)
2. 복구할 DB에 `auth.users`가 있어야 한다 (Supabase 프로젝트는 이미 있음) → `pg_restore -d "<복구 대상>" --no-owner --no-privileges miyu-backup.dump`
3. 복구 뒤 확인: 표별 행 수 비교, 완성 리포트의 `md5(content::text)` 비교, 고치기 방지 트리거 존재, `/setup`의 DB 상태, 새 검사 · 결제 흐름 한 번.
4. 복구 시점 이후에 생긴 결제는 결제사 기록이 진실이다 → 정기 점검(최근 7일)이 맞추고, 그보다 오래된 구간은 주문번호별로 대조한다.

## 6. 되돌리기 (코드와 DB는 따로 판단)

| 상황 | 코드 | DB |
| --- | --- | --- |
| 새 배포 뒤 화면 · 결제에 문제 | Vercel → Deployments에서 **이전 정상 배포로 되돌리기**(Instant Rollback / Promote). 되돌린 뒤 `/admin` · 결제 한 번 확인 | **건드리지 않는다.** DB 변경은 "더하기만" 하는 규칙이라 옛 코드도 새 DB 구조에서 동작한다 (옛 코드는 새 표 · 열을 쓰지 않을 뿐) |
| DB 변경(마이그레이션) 적용 뒤 문제 | 코드는 그대로 둬도 된다 (없는 표 · 열을 견디게 작성돼 있다) | **되돌리는 마이그레이션은 없다.** 잘못된 구조는 **새 마이그레이션**으로 고친다. 데이터가 망가졌다면 5장의 백업 복구 |
| 데이터가 잘못 바뀜 (사고 · 실수) | 코드는 상관없음 | 백업에서 해당 표만 복구 → 결제는 결제사 기록으로 재대조 |
| 해석 규칙 · 지시문을 바꿨더니 품질이 나빠짐 | 이전 버전 파일로 되돌려 재배포 | 이미 구매한 리포트는 만든 시점의 내용 그대로라 영향 없음. 새로 만들 리포트부터 바뀐다 |

순서: ① 증상이 **화면 · 결제 오류**면 먼저 코드를 되돌려 고객 영향부터 멈춘다 ② 원인이 **DB**인지 확인 ③ DB는 새 마이그레이션 또는 백업 복구로 따로 해결 ④ 해결 뒤 다시 배포. 한 번에 둘을 같이 되돌리지 않는다.
- **확인되지 않음:** 실제 Vercel 프로젝트에서의 롤백 리허설.

## 7. 비밀값이 노출됐다고 의심될 때

대화 · 화면 공유 · 커밋에 키가 노출됐다면 **바로 재발급**한다: ① Supabase secret key(대시보드에서 새로 만들기) ② 토스 시크릿 키(상점 관리자에서 재발급) ③ `CRON_SECRET`(새 값) ④ 텔레그램 봇 토큰(BotFather) → Vercel 환경변수를 새 값으로 바꾸고 재배포 → 옛 키는 폐기. 서버 로그 · 운영 기록은 키 · 토큰 · 이메일 · 전화번호 · DB 오류의 행 내용을 가려서 남기도록 되어 있고(검증됨), 고객의 고민 · 대화 내용은 어떤 기록에도 넣지 않는다.

## 8. 공개 후 검색 등록 (한 번)

미유는 검색 순위를 보장하지 않는다. 공개 주소가 생긴 뒤 아래를 한 번 한다.
1. `SITE_URL`을 실제 주소로 설정하고 재배포 (sitemap · robots · 공유 이미지 주소의 기준).
2. **네이버 서치어드바이저**(https://searchadvisor.naver.com)에서 사이트 등록 → 소유 확인 → 사이트맵 제출 `https://내주소/sitemap.xml`.
3. **구글 서치 콘솔**(https://search.google.com/search-console)에서 속성 추가 → 소유 확인 → 사이트맵 제출.
4. 제출 뒤 `robots.txt`(`/robots.txt`)에 개인 결과 · 결제 · MY · 관리자 주소가 막혀 있는지 한 번 확인한다. **검색 제외(noindex)는 비공개가 아니다** — 개인 정보는 로그인 확인과 DB 접근 정책이 따로 지킨다.
5. 소유 확인용 파일 · 메타 태그가 필요하면 그 값만 추가한다 (키가 아니므로 `app/layout.tsx`의 `metadata.verification`에 넣어도 된다).
