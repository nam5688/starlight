**상태(2026-10-16 운영자 답변 뒤)**: ① **"계정당 3번" = 초대한 사람 한 명이 할인 초대를 3명까지**(초대받은 사람은 첫 구매 1회) ② **5,900원은 초대받은 사람 본인의 심층 리포트(9,900원) 가격이고, 궁합(심층 궁합)은 별도 유료** ③ **"할인 전 가격 표시 금지"의 예외**: 초대 링크로 들어온 사람에게는 **정가 9,900원 → 초대 가격 5,900원**으로 표기한다(이 경우만, 마감 타이머 · 불안 자극 문구는 계속 쓰지 않는다). → 이 세 가지가 정해진 **초대 링크 + 5,900원 할인**(4단계 중 아래 "구현 순서"의 첫 묶음)부터 만들고, 간단 궁합 · 심층 궁합은 아직 만들지 않았다(심층 궁합 가격 · 5번 이하 결정 대기). 운영자가 아래 "결정이 필요한 것"에 답하면 단계별로 만든다. 가격 · 포함 범위는 따로 정하며 개인 통합 리포트 9,900원에 포함된다고 안내하지 않는다(`CLAUDE.md` 상품 원칙).

## 2. 먼저 알아 둘 규칙 (지금 문서 · 코드와 부딪히는 곳)

- **상대 분석은 입력 방식으로 범위를 나눈다**(`CLAUDE.md`): 이 제안은 그중 **"상대가 직접 검사하고 공유에 동의"** 한 경우(두 사람의 자기응답을 활용한 비교)다. 상대 생년월일만 · 내가 대신 입력은 이 제안의 범위가 아니다.
- **문항별 답변 · 개인 리포트 전체 · 비공개 상담(채팅) 내용은 상대에게 자동 공유하지 않는다.** 상대에게 가는 것은 **궁합 결과(영역별 문장)뿐**이어야 하고, 상대가 동의한 뒤에만 만든다.
- 궁합은 **총점 하나가 아니라 영역별**(대화 방식 · 친밀감과 거리 · 갈등 해결 · 생활 속도 · 미래 계획)로 보여 주고, 점수를 쓴다면 무엇으로 계산했는지 설명하며 **관계 성공 확률이 아니라고** 밝힌다. 지금 문항이 재지 않는 영역은 "자료 없음"으로 둔다(AI가 채우지 않는다).
- **"할인 전 가격 · 마감 타이머를 만들지 않는다"**: **초대 링크 할인만 예외로 둔다(운영자 2026-10-16)** — 정가 9,900원과 초대 가격 5,900원을 함께 적는다. 이 예외는 초대 링크로 들어와 **실제로 할인 대상인 사람에게만** 보이고(서버가 대상인지 확인한 뒤), 대상이 아니면(이미 구매했거나 한도가 찼거나 본인 링크) 정가만 보인다. 마감 타이머 · "오늘만" 같은 문구는 쓰지 않는다.
- **결제 · 승인 규칙은 그대로**: 금액은 서버가 정하고(할인 대상인지도 서버가 판단), 결제사 확인 뒤에만 권한을 준다. 쿠폰 · 할인코드를 브라우저가 보내는 값으로 믿지 않는다.
- 데이팅 매칭 · 회원 간 만남 주선은 이 기능이 아니다(`roadmap.md` 보류 목록). 상대의 속마음 · 상대 성격 단정은 쓰지 않는다.

## 3. 단계 제안 (한 번에 하나씩, 앞 단계가 확인된 뒤 다음 단계)

1. **초대 링크 + 상대의 동의 + 쌍 기록**: 내 결과 화면에서 [상대에게 링크 보내기] → 상대가 링크로 들어와 무료 분석(또는 이미 있는 결과 선택) → "OO 님과 궁합을 보는 데 동의해요" → 쌍이 만들어진다. 링크에는 생년월일 · 이름이 없고 **되돌릴 수 없는 무작위 토큰**만 있다(기간 · 사용 횟수 제한, 만료).
2. **간단 궁합(무료, 코드 계산 · AI 미사용)**: 두 사람의 사주 원국에서 읽는 관계(일간 · 일지의 합 · 충 · 오행 상생상극 등 전통 해석을 단순화한 규칙 — `lib/saju/interpret/`에 규칙 이력과 함께 추가, 전문가 검토 전)와 두 사람의 **둘 다 응답한 영역만** 나란히 비교. 영역별 한두 문장, 조건형, 총점 · 확률 없음.
3. **심층 궁합(유료)**: 상품 번호 `compat-deep:<쌍 번호>`, **한 쌍당 한 번 결제**(누가 내는가는 결정 항목). 쌍의 두 사람이 모두 볼 수 있게 할지도 결정 항목. 글은 AI가 쓰되 맛보기 리포트처럼 **근거 목록 안에서만 · 검사 통과분만** 저장한다(상대의 속마음 · 결혼 시기 · 성공 확률 금지).
4. **초대 할인(5,900원)**: 초대한 사람이 **심층 리포트 구매자**이고, 초대받은 사람이 **심층 리포트를 처음 사는** 경우 서버가 금액 5,900원 주문을 만든다. 횟수 제한 · 중복 사용 방지는 DB가 보장한다(아래).

## 4. 데이터 · 보안 구상 (확정 아님)

| 표 | 내용 |
| --- | --- |
| `compat_invites` | 초대한 회원 · 초대한 결과 · 토큰의 해시(원문 저장 안 함) · 만들 당시 초대한 사람의 등급(무료 / 심층) · 만료 · 취소 |
| `compat_pairs` | 두 사람의 회원 · 결과, 동의한 시각(**초대받은 사람이 동의하기 전에는 초대한 사람이 상대 결과를 볼 수 없다**), 상태(철회 포함), 간단 궁합 결과 요약(코드가 만든 문장), 심층 궁합 주문 |
| `invite_discounts` | 초대 할인 사용 기록: 초대받은 회원 · 초대 · 주문. **DB의 고유 조건 + 잠금으로 횟수 제한을 지킨다**(동시에 눌러도 한도를 넘지 않는다) |

- 쓰기는 서버가 소유자를 확인한 뒤에만, 조회는 본인이 속한 쌍만(RLS). 상대가 철회하면 그 쌍의 결과는 더 보이지 않는다. 탈퇴하면 함께 삭제한다(`withdraw_member_data` 갱신, 새 마이그레이션).
- 링크를 받은 사람에게 보이는 것은 **초대한 사람의 닉네임(또는 "친구")뿐**이다(동의 전에는 사주 · 응답 · 결과를 보이지 않는다).
- 비용: 간단 궁합은 코드 계산이라 AI 비용이 없다. 심층 궁합의 AI 비용은 아직 재지 못했다(맛보기 리포트 어림 35~50원보다 입력이 두 사람 몫이라 더 든다 — 가격 정할 때 실제 호출로 잰다).
- 남용: 계정 두 개로 스스로 초대해 할인받는 것을 막는 방법은 완벽하지 않다 — 같은 회원 불가 · 초대한 사람 한 명당 한도 · 결제 승인된 심층 리포트 구매자만 초대 가능 정도는 서버에서 막는다. 그 이상은 운영 지표를 보고 정한다.

## 6. 확인한 것 · 못 한 것

- 확인한 것: 위 규칙이 `CLAUDE.md`의 상대 분석 · 가격 · 할인 표시 규칙과 부딪히는 곳, 필요한 DB 표 구상, 단계 나누기.
- **못 한 것**: ① 궁합의 사주 해석 규칙(합 · 충 · 상생상극을 어떻게 읽는지)은 전통 해석을 단순화해야 하며 **전문가 검토를 받지 못했고 통계로 검증된 것이 아니다**(맞다고 쓸 수 없다) ② 심층 궁합 AI 비용 · 글 품질을 재지 못했다 ③ 초대 할인의 법적 · 약관상 표시(할인 조건 안내, 표시광고)를 확인하지 못했다 ④ 가격 · 횟수 제한을 정하지 않았다.

### 구현한 것 · 못 한 것 (1번 묶음)

- **동작**: ① 심층 리포트를 결제까지 마친 회원의 결과 화면에 "친구 초대하기"(링크 만들기 · 복사 · 쓴 자리 / 남은 자리) ② `/invite/<토큰>`(로그인 없이 열림) — 정가 → 초대 가격, 초대한 사람 정보 없음, [무료 분석 시작하기]가 링크를 쿠키로 기억 ③ 결과 화면 구매 영역이 서버 확인 뒤에만 "정가 9,900원 → 초대 가격 5,900원" ④ 결제를 시작할 때 서버가 5,900원 주문을 만들고 DB가 확정, 실패하면 정가 주문.
- **지키는 규칙(DB 18번)**: 초대한 사람 한 명당 3명(결제 완료 + 결제 대기 1시간 이내) · 초대받은 사람은 한 번(환불해도 다시 안 됨) · 본인 링크 불가 · 초대한 사람의 구매가 확인돼야 · 재구매(다시 받기)는 정가 · 할인 주문이 결제 대기로 1시간을 넘기면 다음 확인 때 취소.
- **쓰는 사람이 알아 둘 것**: 링크의 할인 자리는 한정이라 화면에서 "자리가 있다"고 보여도 결제를 시작할 때 다시 확인해 자리가 없으면 정가가 된다(링크 화면에 안내). 초대한 사람이 환불하면 링크의 할인이 멈춘다.
- **못 한 것**: ① 실제 Supabase에 18번을 적용하지 않았고 실제 토스 테스트 결제로 5,900원 승인을 확인하지 않았다(주문 금액이 5,900원이면 결제 승인은 같은 경로이지만 직접 해 봐야 안다) ② **약관 · 처리방침 · 상품 안내에 초대 할인 조건을 적지 않았다** — 할인 조건 안내 · 표시광고 확인이 필요하다 ③ 계정 두 개로 스스로 초대해 할인받는 것은 완전히 막지 못한다(같은 회원 · 환불 뒤 재사용은 막음) — 운영 지표(`check-invites.sql`)를 보고 정한다 ④ 결제 대기 주문이 취소된 뒤 결제사에서 실제로 승인된 경우 주문이 다시 결제 완료로 맞춰질 수 있다(기존 결제 대조 규칙) — 이때는 5,900원으로 결제됐으므로 한도 숫자가 넘칠 수 있고 `check-invites.sql`에서 보인다 ⑤ 궁합 자체(간단 · 심층)는 아직 없다.

### 8-1. 친구 초대 — 무제한 + 결제당 질문권 1개

| | 지금 구현된 것 | 바뀔 방향 |
| --- | --- | --- |
| 초대한 사람이 보낼 수 있는 인원 | 3명까지 | **제한 없음** |
| 초대받은 사람의 가격 | 본인 첫 심층 리포트 1회 5,900원 | **그대로**(첫 구매 1회, 본인 계정만) |
| 초대한 사람의 보상 | 없음 | 초대받은 사람의 **해당 결제가 완료되면 질문권 1개** |
| 클릭 · 가입만으로 | — | **보상하지 않는다** |
| 보상 횟수 | — | **구매 한 건(주문)에 초대한 사람 한 명, 보상 한 번** |

**막아야 하는 것**: ① 본인 계정으로 초대(지금도 막는다) ② 초대받은 사람이 첫 구매 할인을 두 번 쓰기(지금도 막는다) ③ 같은 주문에 보상을 두 번 주기 — 토스 결제 알림은 재전송될 수 있어도 지급은 주문 번호당 한 번만(지금 질문 묶음 충전이 주문 단위로 한 번만 들어가는 방식과 같게). ④ **한 사람이 계정을 두 개 만들어 5,900원을 받는 것은 지금도 완전히 막지 못한다 — 인원 한도(3명)가 없어지면 이 구멍의 피해 상한도 없어진다.** 그래서 초대 할인으로 팔린 비중 · 보상으로 나간 질문권 수를 지표로 보고(운영 지표 화면에 추가), 필요하면 할인과 보상을 즉시 끌 수 있는 스위치(`lib/config/product.ts`)를 둔다고 제안한다.

**질문권의 뜻(추천)**: 이용할 수 있는 개인 상담방에서 **질문 하나를 보내고 답변 하나를 받는 권리**. 심층 리포트나 궁합 상품을 무료로 여는 권한과는 분리하고, 정상적인 답을 받지 못하면(호출 실패 · 검사에 걸림) 지금의 질문 묶음처럼 차감하지 않는다. 장부 단위는 질문 1개 = 3단위(`MIYU_CASH.perQuestion`)이므로 보상은 3단위다.

**장부(DB 설계 확인 필요)**: 기존 질문 장부의 `bonus` 종류를 그대로 쓰지 않는 것을 추천한다. 그 종류는 "그 주문이 환불되면 그 주문으로 들어온 단위를 회수"하는 DB 규칙과 묶여 있어서(13 · 16번), 보상(초대받은 사람의 주문 → **초대한 사람**의 장부)에 쓰면 환불 때 엉킬 수 있다. 새 마이그레이션에서 보상 표(예: 주문 번호가 유일한 `invite_rewards`)와 장부 종류를 따로 정한다.

**취소 · 환불 처리(운영자 결정 필요)**:

| 안 | 내용 | 비고 |
| --- | --- | --- |
| **(가) 추천** | 초대받은 사람이 **전액 환불**하면 초대한 사람의 **아직 쓰지 않은** 질문권만 회수하고, 이미 쓴 질문권은 회수하지 않는다(회수하지 못한 몫은 운영 기록에 남긴다) | 지금 질문 묶음 환불 처리와 같은 방식이라 규칙이 하나로 통일된다 |
| (나) | 환불 가능 기간이 지난 뒤에 질문권을 준다(지급을 미룬다) | 회수가 필요 없지만 보상이 늦게 보인다 |
| (다) | 환불돼도 회수하지 않는다 | 가장 단순하지만 환불 · 재결제를 반복하는 악용에 약하다 |

**3명 한도를 없앨 때의 변경 범위(정리만 — 아직 고치지 않았다)**:

- **DB**: 18번 파일의 함수 `invite_discount_status` · `claim_invite_discount`의 한도 비교와 `cap` 이유를 없앤다 → **18번 파일을 고치지 않고 새 마이그레이션(19번 이후)으로 함수를 교체**한다. 초대한 사람의 구매 확인 · 첫 구매 1회 · 본인 링크 금지 · 대기 주문 정리는 남긴다. **운영 Supabase에는 이미 18번이 적용돼 있으므로 순서는 "DB 새 마이그레이션 → 코드 배포"**(코드를 먼저 배포하면 화면은 무제한으로 보이는데 DB가 4번째부터 정가로 돌려 어긋난다).
- **설정 · 서비스**: `INVITE_DISCOUNT.maxPerInviter`(`lib/config/product.ts`), `order-service.ts`의 한도 확인, `invite-service.ts`의 남은 자리 · `cap` 상태, 메모리 저장소(DB 함수 미러) · Supabase 저장소 매핑.
- **화면**: 결과 화면 "친구 초대하기"의 "남은 자리 · 한 분이 N명까지" 문구, `/invite/<토큰>`의 "자리가 찼어요" 상태와 안내 문구(링크 화면 · 구매 영역의 "자리가 한정돼 있어서" 안내), 질문권을 받은 개수 표시(새로 필요).
- **시험 · 문서**: 한도 3명 시험(단위 · 실제 Postgres 동시 8요청 · 브라우저)을 "무제한" 시험으로 바꾸고, 보상 중복 지급 · 환불 회수 시험을 더한다. `check-invites.sql` · CLAUDE.md · 약관 · 처리방침의 초대 할인 조건.
- **지키는 것**: **기존 주문 · 결제 · 할인 이력(`orders` · `invite_discounts`)은 지우거나 바꾸지 않는다.** 이미 3명이 찬 링크는 그대로 이어서 쓸 수 있게 열린다. 탈퇴 처리(`withdraw_member_data`)는 보상 표를 어떻게 다룰지 정해 갱신한다(할인 기록처럼 회원번호 · 주문번호만 남기는 쪽을 추천).

**손익 어림(계산 예시 — 실측이 아니다)**: 가정 ① 5,900원이 부가세 포함 가격이고 일반과세자이며 결제 수수료의 매입세액을 공제받는다(운영자의 실제 과세 유형은 확인하지 못했다) ② 일반 카드 수수료 3.4%(+ 부가세 별도) — **토스페이먼츠 공개 요율이라고 전달받은 값이며 이 문서 작성자가 계약 요율을 직접 확인하지 못했다.** 부가세 제외 매출 5,900 ÷ 1.1 ≈ 5,364원, 부가세 제외 결제 수수료 ≈ 201원이면 서비스 비용을 빼기 전 ≈ 5,163원이다. 결제 한 건에 배분되는 **서비스 변동원가**(심층 리포트 생성 + 기본 제공 상담 + 초대한 사람의 질문권 1개 + 구매하지 않은 이용자의 무료 생성비 배분)가 500원이면 약 4,663원, 1,500원이면 약 3,663원, 3,000원이면 약 2,163원이 남는다(고정비 · 광고비 · 환불 손실 · 소득세 차감 전).

- **지금까지 직접 잰 값**: 심층 리포트 한 명 실제 생성 305원(지시문 0.5, 고쳐 쓰기 포함, 2026-10-14 — 지시문 0.6 이후는 아직 재지 못했다) · 채팅 질문 1건 약 17원(입력 2,983 · 출력 455토큰 어림). **맛보기 한 건(35~50원 어림)은 아직 재지 못했다** — 이번 확인에서 `supabase/check-taste-usage.sql`로 잰다. 변동원가에 들어갈 나머지(무료 맛보기의 구매 한 건당 배분, 구매 후 실제 질문 사용량)는 운영하며 쌓아야 한다.
- **놓치기 쉬운 비용**: ① 무료 분석만 받고 구매하지 않는 사람의 맛보기 비용(예: 맛보기 50원 가정, 100명이 받고 5명이 구매하면 구매 한 건당 1,000원) ② 방마다 기본으로 주는 무료 질문(오늘의 운세는 매일)의 누적 사용량.
- **할인 잠식**: 초대 제한이 없으면 정가(9,900원)로 팔릴 사람이 초대 링크로 5,900원에 사는 비중이 늘 수 있다. 수익 계획은 "대부분 9,900원"이 아니라 **5,900원 판매 비중이 높아져도 운영 가능한가**를 기준으로 본다.

### 8-2. 궁합은 두 경로로 나눈다 — 분석 자료의 구분(사주 궁합 / 통합 궁합)과 제공 범위의 구분(간단 / 심층)은 섞지 않는다

| 구분 | **사주 궁합** | **통합 궁합**(리포트 기반) |
| --- | --- | --- |
| 시작 | 한 사람이 **두 사람의 출생정보**를 입력 | **두 사람이 각자 분석한 결과**를 연결 |
| 쓰는 자료 | 두 사람의 사주 원국 | 두 사람의 사주 + 각자가 직접 답한 응답 |
| 상대의 가입 · 검사 | 필요 없는 흐름으로 설계 | 각자의 분석 결과와 **궁합 이용 동의** 필요 |
| 보여 줄 것 | 전통 사주 해석상의 관계 특징과 참고할 점 | 사주 비교 + 실제 응답의 공통점 · 차이점 |
| **만들지 않는 것** | **상대의 응답(기질 · 성격 · 애착)을 대신 만들어 판정하는 것** | 문항이 재지 않은 영역을 AI가 채우는 것 |
| 개인 심층 리포트 구매 | 필수로 묶지 않는다 | 둘 다 무료 분석만 했어도 이용할 수 있게 제안 |
| 유료 상세 | 별도 궁합 상품 | 별도 궁합 상품 |

- **표현**: 통합 궁합이 "더 정확하다"고 쓰지 않는다(검증이 없다). 차이는 "두 사람이 직접 답한 내용까지 비교한다"로만 설명한다. 사주 해석 규칙은 전문가 검토 전이다.
- **가격 안내**: 궁합은 개인 심층 리포트 9,900원이나 초대 가격 5,900원에 **포함된다고 안내하지 않는다.** 무료 간단 궁합과 유료 심층 궁합의 범위 · 가격은 따로 정한다(5장 3~7번).
- **개인정보(검토 필요 — 법률 검토는 하지 못했다)**: 사주 궁합은 상대가 가입하지 않아도 되지만, **상대의 출생정보를 서비스가 처리하는 근거 · 안내 · 보관 · 삭제를 따로 확인**해야 한다. 계산에 필요하지 않은 정보(실명 · 연락처)는 받지 않는 쪽을 추천한다(최소 수집). 상대 출생정보를 저장할지 · 얼마나 보관할지는 결정 항목이다.
- **기존 규칙과의 관계**: `CLAUDE.md`의 "상대 분석은 입력 방식으로 범위를 나눈다"(상대 생년월일만 → 사주 기반 해석 / 내가 관찰한 모습 / 상대가 직접 검사하고 동의)와 같은 방향이며, 이 표는 그중 "상대 생년월일만"을 사주 궁합, "상대가 직접 검사하고 동의"를 통합 궁합이라고 이름 붙인 것이다. 상대가 검사하지 않았는데 기질 · 성격 · 애착을 검사한 것처럼 만들지 않는다.
