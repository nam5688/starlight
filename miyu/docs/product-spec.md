# ME:U(미유) 제품 기획서

- 문서 상태: 2~3단계 일부 구현 반영 (2026-10-12)
- 이 문서는 전체 요구사항을 정리한 것이며, 실제 구현 범위는 [`roadmap.md`](./roadmap.md)의 단계를 따른다.
- "가안", "후보", "미정"으로 표시한 항목은 출시 전에 사용자 확인이 필요하다.

## 1. 서비스 정의

미유는 **사주 + MBTI + 기질 + 애착유형을 함께 다루는 개인 통합 분석 리포트** 서비스다.
궁합이나 소개팅이 아니라, 혼자 분석받는 것만으로 완결되는 상품이 중심이다.

고객이 받았으면 하는 인상:

- 여러 곳에서 따로 보던 나에 대한 분석을 한곳에서 정리해준다.
- 긴 이야기를 읽지 않아도 내 특징과 필요한 행동을 바로 알 수 있다.

핵심 메시지:

- 나에 대한 분석, 한 번에 정리하세요.
- 긴 서론 대신, 필요한 결론부터.
- 사주 · MBTI · 기질 · 애착
- 대표 경향 · 한 줄 요약 · 항목별 점수 · 실천 제안

표현 원칙:

- "완결판"의 느낌은 **분석 범위와 정보 구성**으로 표현한다. 사람을 완벽하게 진단하거나 미래를 맞힌다는 뜻으로 쓰지 않는다.
- 네 가지 분석을 모두 포함하되, 각각의 근거와 한계를 구분한다. 사주를 삭제하거나 선택형 부가상품으로 밀어내지 않는다.
- 검증된 정확도, 임상 진단, 실제 사용자 수, 전문가 감수, 후기를 지어내지 않는다.
- 확인되지 않은 할인 전 가격, 가짜 마감 타이머를 쓰지 않는다.

- **개인 통합 리포트** 하나. 가격 9,900원(가안, `lib/config/product.ts`에서 변경).

- **앱인토스(토스 앱 안 입점)는 보류** — 앱인토스 SDK, 토스 로그인, 앱인토스 인앱결제는 지금 만들지 않는다.
- 다른 채널을 붙일 때를 위해 검사·채점·리포트·주문 규칙은 채널과 무관한 코드로 분리한다 (아래 "코드 구조").

## 4. 화면 구성

### 4-1. 메인 (`/`)

핵심 소개 → 실제 리포트 예시 → 제공 항목 → 이용 방법·가격 → 자주 묻는 질문.

- 제목: "나에 대한 분석, 한 번에 정리하세요."
- 설명: "사주 · MBTI · 기질 · 애착. 네 가지 관점으로 성향과 행동 패턴을 정리합니다."
- 보조 문구: "긴 서론 대신, 필요한 결론부터."
- 버튼: 내 분석 시작하기 / 리포트 예시 보기
- 문항 수·소요 시간은 검증 전이므로 광고 문구로 확정하지 않는다.

### 4-2. 이용 흐름

기본 정보 → 검사 응답 → 무료 요약 → 카카오 로그인 → 상세 리포트 구매 → MY에서 저장된 결과 다시보기.

검사 화면 요구사항:

- 뒤로 가기(화면 버튼 + 브라우저/휴대폰 뒤로 가기), 답변 수정, 진행 상태 표시.
- 답하지 않은 문항이 있으면 다음으로 넘어가지 않고 해당 문항을 알려준다.
- 검사 도중 성격 해석을 보여주지 않는다 (이후 답변 유도 방지).

### 4-4. 결과 화면 순서

1. **대표 경향** — 후보 이름. "분류 규칙 확정 전 · 고정된 성격 유형이 아님" 안내를 함께 표시
2. **한 줄 요약** — 추상적 칭찬 대신 구체적 행동 (예: "관계가 불확실할 때, 상대의 반응을 확인하려는 편입니다.")
3. **핵심 요약** — 내가 편한 환경 / 자주 반복되는 반응 / 스트레스를 받기 쉬운 상황 / 바로 적용해볼 행동
4. **항목별 점수** — 기질·관계 응답을 막대로. 지표마다 낮을 때·높을 때의 의미를 함께 표시. 0~100 환산값이며 백분위·정확도가 아님
5. **네 가지 상세 분석** — MBTI / 기질 / 애착 / 사주를 펼쳐보기. 각각 "무엇을 봤나요 · 결과 · 한계"
6. **통합 해석** — "공통적으로 나타나는 특징"과 "관점이 다른 부분"을 나눠 정리. 억지로 맞추지 않음
7. **실천 제안** — 지금 적용할 짧은 행동

## 5. 검사와 분석의 구현 원칙

### 5-1. 검사 모듈

- MBTI 성향 · 기질 · 관계(애착)는 **각각 독립된 모듈**(`lib/assessment/modules/`). 같은 구조(지표, 문항, 역문항, 버전, 출처 상태)를 따른다.
- 기존 MBTI 입력만 받고 전체 심리검사를 구현했다고 하지 않는다.
- 문항 출처 상태: `dev-example`(개발용 예시) → 이용 조건을 확인한 운영 문항은 `licensed`.
- 공식 MBTI®, TCI, 애착검사(ECR 등) 문항을 인터넷에서 복사하지 않는다. 공개돼 있다는 이유로 상업적 사용이 가능하다고 판단하지 않는다. "MBTI" 명칭·상표 사용 범위도 운영 전에 확인한다.
- 현재 지표 이름(새로움 추구, 신중함, 타인 반응 민감도, 지속성, 관계 불안, 거리 두기)은 개발용 임시 이름이다.

### 5-2. 채점

- 지표별 평균 응답(1~5)을 0~100으로 환산한다. 역문항은 (6 − 응답).
- 운영에서는 **서버에서만 채점**한다. 응답 검증(누락·범위·모르는 문항)을 먼저 통과해야 한다.
- MBTI 성향의 네 글자는 50 기준. 정확히 50이면 `X`로 두고 어느 쪽으로도 정하지 않는다.

### 5-3. 대표 경향 (임시 규칙)

후보: 확인추구형 · 거리유지형 · 안정지향형 · 탐색지향형. 이름과 규칙 모두 확정 전이다.

| 후보 | 신호값 |
| --- | --- |
| 확인추구형 | 관계 불안 |
| 거리유지형 | 거리 두기 |
| 안정지향형 | (신중함 + (100 − 새로움 추구)) ÷ 2 |
| 탐색지향형 | (새로움 추구 + (100 − 신중함)) ÷ 2 |

가장 큰 신호를 고르고, 같으면 위 표 순서. 사주는 이 계산에 넣지 않는다.

### 5-4. 분석 파이프라인 (운영 목표)

```
검사 응답 → 서버 채점 → 구조화된 결과 → AI 해석 → 리포트 저장(버전 고정)
               ↑
     사주: 음양력 변환 + 만세력 엔진 (AI가 원국을 만들지 않음)
```

- AI 입력은 구조화된 결과(점수, 대표 경향, 엔진이 계산한 원국)만. 출력은 정해진 형식으로 검증한 뒤 저장한다.
- 리포트에는 문항 버전, 채점 규칙 버전, 사주 엔진 버전, AI 모델·지시문 버전을 함께 기록한다.
- 구매한 리포트는 저장된 같은 버전을 다시 보여준다. 열 때마다 AI를 다시 호출하지 않는다.
- 실제 엔진·검사가 연결되지 않았으면 화면에 "연결 전"으로 표시하고, 샘플 결과와 실제 결과를 섞지 않는다.

## 6. 사주 엔진 요구사항과 검수 항목

연결 지점: `lib/saju/engine.ts` (`SajuEngine` 인터페이스). 2단계에서 엔진 후보를 검토해 연결한다.

검수 항목:

- [ ] **음력 → 양력 변환**: 윤달 구분, 음력 달 길이(29/30일) 확인, 지원 연도 범위
- [ ] **년주 경계**: 설날이 아니라 입춘 시각 기준 (입춘 전 출생은 전년도 간지)
- [ ] **월주 경계**: 절기(12절) 입절 시각 기준. 절입 당일 전후 출생 처리
- [ ] **일주**: 기준일 검증 — 신뢰할 수 있는 만세력의 알려진 날짜와 대조
- [ ] **시주와 자시**: 23:00~01:00 자시 처리, 야자시/조자시 적용 여부 결정, 23시 이후 출생의 일주 처리
- [ ] **표준시와 지방시**: 한국 표준시(동경 135°)와 서울(약 127°)의 약 30분 차이를 보정할지 결정
- [ ] **과거 표준시 변경**: 1954~1961년 UTC+8:30 사용 기간 반영
- [ ] **서머타임**: 1948~1951, 1955~1960, 1987~1988년 일광절약시간 기간 반영
- [ ] **출생시간 미상**: 시주 생략, 임의 시간 금지, 화면에 "시주 제외" 표시
- [ ] **해외 출생**: 1차 범위에 넣을지 결정 (넣지 않으면 입력 단계에서 안내)
- [ ] **절기 시각 데이터의 출처와 정확도**
- [ ] **엔진 라이선스**: 상업적 이용 가능 여부
- [ ] **회귀 테스트**: 입춘·절기 당일 전후, 자정 전후, 윤달, 서머타임 기간 생년월일을 고정 테스트로 두고 다른 만세력과 대조

## 7. 데이터 구조 (Supabase) — 구현됨

정의: `supabase/migrations/20261011000000_init.sql`. 모든 표는 내부 회원번호(`auth.users.id`)로 연결한다.

| 표 | 내용 | 비고 |
| --- | --- | --- |
| `profiles` | 닉네임, 결제용 구매자 키(`payment_customer_key`) | 가입 시 자동 생성. 카카오 이메일은 없을 수 있다 |
| `assessments` | 입력값(닉네임·생년월일·양/음력·윤달·출생시간 또는 미상·알고 있는 MBTI), 응답, 서버 채점 결과(무료 요약), 사주 엔진 결과, 문항 버전, 출처(`dev-scoring`/`live`) | 저장 후 수정하지 않음 |
| `user_regions` | 시·도, 시·군·구 | 성향 분석과 분리 (장소 추천용) |
| `orders` | 주문번호, 금액(서버 결정), 상태(`pending/paid/failed/canceled/refunded`), 결제 키·수단·승인 시각, 실패 사유 | 결제 상태 |
| `payment_events` | 승인·웹훅·실패 처리 기록 | 카드 번호 등 결제수단 상세는 저장하지 않음 |
| `reports` | 리포트 본문, 생성기 이름·버전, 생성 상태(`queued/generating/ready/failed`), 시도 횟수, 마지막 오류 | 완성(ready) 후 수정 불가 |

DB가 직접 막는 규칙:

- 주문 상태 변경 규칙: `pending → paid/failed/canceled`, `failed·canceled → paid`(결제사 기록상 승인된 경우 맞춤), `paid → refunded`. 그 밖의 변경과 금액·소유자 변경은 거부
- 같은 검사에 결제 완료 주문 하나, 대기 주문 하나만
- 완성된 리포트는 수정 불가
- 회원 탈퇴 처리는 거래 기록 보존 기간을 정한 뒤 설계한다 (지금은 주문·리포트가 있는 회원 삭제를 막아 둠)

## 8. 회원과 데이터 접근 — 구현됨

- 카카오 로그인(Supabase Auth). 이메일 동의를 거절한 사용자도 가입된다 (Supabase의 "Allow users without an email").
- **로그인 전 검사 결과 보관**: 카카오 로그인으로 다른 사이트에 다녀오는 동안, 결과를 **암호화한 HttpOnly 쿠키**에 30분만 보관한다. 로그인 후 서버가 이 회원번호로 저장하고 쿠키를 지운다. 비회원의 생년월일·응답을 서버 DB에 남기지 않고, 브라우저 저장소(localStorage)에도 두지 않는다.
- **접근 정책(RLS)**: 로그인한 사용자는 본인 행만 **조회**할 수 있고, 직접 쓰기는 모두 거부된다. 저장·결제 처리는 서버가 비밀키로 하며, 서버 코드에서 소유자를 먼저 확인한다.
- 화면 조회(결과·MY·결제 화면)는 로그인한 사용자 권한으로 읽어, 서버 코드에 실수가 있어도 DB가 한 번 더 막는다.
- 다른 회원의 결과·결제 주소를 입력하면 '찾을 수 없음'으로 처리한다 (자동 검사로 확인).
- 유료 리포트 내용은 결제가 확인되기 전에는 브라우저로 보내지 않는다.

## 9. 결제 (토스페이먼츠 주문서형 결제위젯) — 테스트 결제 구현됨

흐름:

1. 결과 화면의 **결제하기** → 서버가 새 주문을 만든다. 금액은 서버 설정값(`lib/config/product.ts`)으로 정하고, 남아 있던 대기 주문은 취소 처리한다.
2. 결제 화면(`/checkout/주문번호`)에서 토스페이먼츠 결제위젯을 띄운다. 보여줄 결제수단은 토스 결제위젯 어드민에서 정한다 (카드 기본, 간편결제는 계약 후 추가).
3. 결제 성공 주소(`/payments/success`)로 돌아오면 서버가 **주문 소유자·금액·상태를 확인**한 뒤 결제 승인 API를 호출한다. 주소의 금액이 주문 금액과 다르면 승인하지 않는다 (승인하지 않은 결제는 청구되지 않고 만료된다).
4. 승인되면 주문을 `paid`로 바꾸고 리포트를 만든다. 리포트 생성 실패는 결제 상태에 영향을 주지 않고, 결과 화면에서 다시 만들 수 있다.
5. 웹훅(`/api/webhooks/toss`): 알림 내용은 믿지 않고 결제사에 결제를 다시 조회한 결과로만 주문을 맞춘다. 같은 알림이 여러 번 와도 결과가 같다.

예외 처리:

| 상황 | 처리 |
| --- | --- |
| 결제 버튼 중복 클릭 · 새 탭 | 대기 주문은 하나만 (DB 고유 조건). 새 결제를 시작하면 이전 대기 주문은 취소 |
| 같은 승인 요청 반복(새로고침) | 이미 같은 결제 키로 결제된 주문이면 그대로 완료 처리. 결제사 요청에는 멱등키를 붙임 |
| 결제사 응답을 못 받음(연결 끊김·5xx) | 주문을 대기 상태로 두고 "확인 중" 안내 → 다시 확인 또는 웹훅으로 맞춤 |
| 카드 거절 등 확정 실패 | 주문 `failed`, 결제사 메시지 안내 |
| 결제창에서 취소 | 주문 `canceled`, 다시 결제하기 안내 |
| 결제사에서 취소(환불) | 웹훅으로 주문 `refunded`. 리포트 대신 환불 안내를 보여준다 (가안) |

- **처음에는 테스트 결제만.** `PAYMENTS_LIVE_MODE=true`가 아니면 앱이 `test_` 키만 받는다. 실결제 전환은 PG 계약·심사 후 운영자 승인으로 한다.
- 결제위젯 연동 키(`test_gck_` / `test_gsk_`)를 쓴다.

## 9-1. 리포트 생성 — 개발용 생성기 연결

- 지금은 점수와 임시 규칙으로 문장을 조합하는 **개발용 생성기**(`lib/report/generate-dev-report.ts`, AI 미사용)로 만들고 `dev-scoring` 표시를 붙인다.
- AI 해석은 같은 연결 지점(`ReportGenerator`)에 생성기를 바꿔 끼운다. 입력은 구조화된 결과만, 출력은 형식 검증 후 저장한다.
- 생성은 결제 승인 직후 한 번, 실패하면 `failed`로 남기고 다시 시도할 수 있다 (최대 5회, 넘으면 운영자 확인).
- AI 생성처럼 오래 걸리는 작업은 웹훅 응답 시간(10초) 안에 끝나지 않을 수 있으므로, AI 연결 시 별도 작업 큐로 분리한다.

## 9-2. 코드 구조 — 채널 재사용

| 경로 | 역할 | 의존 |
| --- | --- | --- |
| `lib/assessment`, `lib/report`, `lib/commerce`, `lib/profile`, `lib/saju` | 검사·채점·리포트·주문 규칙 | 순수 TypeScript |
| `lib/services` | 저장·주문·승인·리포트 생성 흐름 | 저장소(`MiyuRepository`)·결제사(`PaymentGateway`)·생성기(`ReportGenerator`) 약속만 |
| `lib/integrations/supabase`, `lib/integrations/tosspayments` | 위 약속의 구현체 | Supabase SDK, fetch (Next.js 무관) |
| `server/`, `app/`, `components/`, `proxy.ts` | 웹 채널 (Next.js) | 위 전부 |

다른 채널(예: 앱인토스)을 붙일 때는 `lib/` 아래를 그대로 쓰고, 로그인·결제 구현체와 화면만 새로 만든다. 핵심 폴더가 Next.js·React·외부 SDK를 불러오지 않는지는 단위 테스트로 확인한다.

## 10. 쿠폰 (4단계 정책)

- 첫 가입 50% 할인 — 계정당 첫 구매 1회, 중복 사용 방지(DB 고유 제약), 유효기간(미정)을 서버에서 관리.
- 할인 금액은 서버가 계산한다. 지금 운영 쿠폰을 발급하지 않는다.

## 11. 텔레그램 운영 알림 (4단계)

- 보낼 이벤트: 결제 완료, 리포트 생성 실패, 환불 요청, 웹훅 확인 실패.
- 서버에서 전송 — 브라우저를 켜둘 필요 없음. DB 저장이 끝난 뒤 `notification_outbox`를 통해 보내고, 실패하면 재시도.
- 알림 실패가 결제·리포트 제공을 막지 않는다.
- 넣지 않는 것: 고객 이름, 생년월일, 검사 답변, 분석 내용.

```
미유 결제 완료
개인 통합 리포트 / 9,900원
주문번호: M2031
리포트 상태: 생성 완료
```

## 12. 관리자 (3단계)

- 관리자 권한은 DB의 역할 값으로 서버에서 확인한다.
- 화면: 주문 상태, 리포트 생성 실패, 재처리, 환불 요청·상태, 작업 기록.
- 실제 환불이나 중요한 운영 데이터 변경은 사용자(운영자) 승인 없이 실행하지 않는다.

## 13. 보안 · 개인정보

- 비밀키(Supabase secret key, 토스 secret key, 텔레그램 봇 토큰, AI API 키)는 서버 환경변수에만. 로컬은 `.env.local`(커밋 안 됨), 배포는 Vercel 프로젝트 설정의 Environment Variables.
- 로그에 생년월일·답변·리포트 본문을 남기지 않는다.
- 판매 전 준비(사용자 확인 필요): 개인정보 처리방침, 이용약관, 사업자·통신판매업 정보, 환불 정책, PG 가맹 심사.
