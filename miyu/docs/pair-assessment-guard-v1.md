# 리포트 궁합 쌍 × 기록 삭제 동시성 장치 — DB 변경 30번

운영자 지시(2026-10-20): "쌍 생성과 기록 삭제가 동시에 겹칠 때 DB 장치가 없음"을 재현해서 확인하고, 원자료를 빈 값으로 만든 분석을 새 `pairs`가 참조할 수 있으면 출시 전에 고친다.
결과: **실제로 일어났다(로컬 DB, 가상 계정으로 재현).** 28 · 29번 파일은 고치지 않고 새 파일 하나(30번)로 막았다. 외부 DB에는 적용하지 않았다.

## 1. 무엇이 문제였나 (코드 · DB 사실)

- `pairs`는 검사 결과(`assessments`)를 외래 키로 묶지 않는다(24번 주석: 회원 탈퇴가 주문 없는 검사 결과를 지울 때 이 표가 탈퇴를 막으면 안 되기 때문). 그래서 **쌍을 만들거나 수락하는 쪽은 검사 결과 행을 잠그지 않는다.**
- 29번 삭제 함수(`delete_assessment_record_v2`)는 검사 결과 행을 `for update`로 잠근 뒤 "쌍이 이 결과를 가리키면 분석 원자료를 남긴다"를 한 번 확인(`select exists … from pairs`)하고 원자료를 비운다. 이 확인은 **아직 커밋하지 않은 쌍을 볼 수 없다.**
- 두 가지 순서에서 "원자료가 빈 값인 분석을 새 쌍이 가리키는" 상태가 남았다(둘 다 재현):
  1. **쌍이 먼저, 아직 커밋 전** — 삭제가 확인에서 쌍을 못 보고 원자료를 비운 뒤 쌍이 커밋된다. (재현: 쌍을 넣는 트랜잭션을 2초 붙잡은 채 삭제 → 삭제가 기다리지 않고 닉네임 `삭제` · 생년월일 1900-01-01로 비움 → 쌍이 그 분석을 가리킴)
  2. **삭제가 먼저, 아직 커밋 전** — 삭제가 결과 행을 잠근 채 원자료를 비우는 동안 쌍 만들기는 기다리지 않고 들어온다. (재현: 삭제 트랜잭션을 2초 붙잡은 채 쌍 넣기 → 오류 없이 만들어짐)
- 겹치지 않아도 DB는 막지 못했다: 이미 삭제한 결과(28번 범위 `record_deleted_at` · 29번 범위 `record_purged_at`)를 가리키는 쌍을 직접 넣거나, `pair_join`으로 삭제한 결과를 상대 자리에 연결해도 DB가 거절하지 않았다(앱이 읽기 → 쓰기 사이에 확인할 뿐, 그 사이에 삭제가 끼어들 수 있다).
- 수정 전 상태로 시험 9개를 돌렸을 때 6개가 실패했다(위 재현 + 삭제한 결과를 가리키는 쌍 · 수락 거절 · 새 함수 없음). 로컬 DB에는 이 재현이 만든 "원자료가 빈 분석을 가리키는 쌍"이 5건 남았다(가상 계정 · 로컬 전용, 30번은 이 행을 고치지 않는다 — 사전 확인 SQL 번호 4가 이 수를 센다).

**실제 가능성**: 쌍 초대 생성 · 수락과 같은 결과의 기록 삭제가 같은 몇 밀리초 안에 겹쳐야 한다(사람 한 명이 두 화면에서, 혹은 상대의 수락과 내 삭제가 같은 순간). 확률은 낮지만 겹치면 데이터가 어긋나고 되돌릴 수 없어서 출시 전에 막았다.

## 2. 무엇을 바꿨나 (`supabase/migrations/20261109000000_pair_assessment_guard.sql`)

28번 · 29번의 방식 그대로다(삭제 함수의 `for update`와 같은 행을 `for share`로 읽는다).

1. **트리거 `pairs_block_deleted_record`** — 쌍을 넣을 때(두 자리 모두) 또는 `a_assessment_id` · `b_assessment_id`가 바뀔 때 그 검사 결과 행을 `for share`로 읽고, 삭제를 마쳤으면 `record_purged`, 삭제 표시만 있으면 `record_deleted`로 거절한다.
   - 삭제가 진행 중이면 끝날 때까지 **기다린 뒤** 결과를 보고 판단한다(순서 2 해결).
   - 쌍이 먼저면 삭제 함수의 `for update`가 그 쌍이 커밋될 때까지 기다리고, 그 뒤 확인(`select exists … from pairs`)이 커밋된 쌍을 본다(순서 1 해결 — 읽기 커밋 격리에서는 문장마다 새 기준으로 읽는다).
   - 결과 번호를 바꾸지 않는 갱신(연결 해제 · 동의 철회 · 탈퇴 반응)은 막지 않는다 — 한쪽이 기록을 삭제한 뒤에도 기존 쌍은 정리할 수 있다.
   - 없는 결과(탈퇴로 지워진 번호)를 가리키는 쌍은 예전처럼 허용한다(외래 키 없는 설계 그대로).
2. **`pair_join` 새 정의(`create or replace`)** — 24번 정의와 같고, 상대의 결과를 `for share`로 읽으며 삭제한 결과는 트리거 오류가 아니라 깨끗한 상태 값 `bad-assessment`로 돌려준다. 권한은 24번과 같다(서버만).
3. 선행조건(24번 pairs · 29번 record_purged_at)이 없으면 아무것도 바꾸기 전에 멈춘다. 데이터는 한 줄도 바꾸지 않는다.

**잠금 순서(교착 가능성)**: 새 잠금은 모두 공유 잠금(`for share`)이라 쌍끼리 서로 기다리지 않는다. 삭제 함수는 결과 행 하나만 잠그고 쌍 행은 읽기만 한다. `pair_join`은 쌍 행 → 결과 행 순서로 잠그고 이 순서를 거꾸로 잡는 곳은 없다(탈퇴 함수는 상대가 들어오기 전의 쌍 행을 건드리지 않는다). 이는 코드 읽기로 확인한 것이고 시험은 위 양쪽 순서만 실제로 돌렸다.

## 3. 앱 쪽 변경

- `lib/services/pair-service.ts` `createPairInvite`: 앱이 결과를 읽은 뒤 같은 순간 기록이 삭제되어 DB가 `record_deleted` · `record_purged`로 거절하면 오류 화면 대신 앱의 삭제 확인과 같은 답(`not-found`)으로 돌려준다. 다른 DB 오류는 그대로 던진다.
- 수락(`pair_join`)은 새 정의가 `bad-assessment`를 직접 돌려주므로 앱 변경이 없다(예전 앱 코드도 이 값을 이미 처리한다).
- **코드와 DB 배포 순서**: 어느 쪽이 먼저여도 안전하다. 30번이 없는 DB에서는 앱이 이전과 똑같이 동작하고(삭제 확인은 앱 몫), 30번이 먼저 들어가면 새 트리거가 거절한 오류를 앱이 위처럼 처리한다.

## 4. 시험 (로컬 Postgres 16, 가짜 결제 · 실제 AI 호출 없음)

`supabase/tests/pair-purge.db.test.ts`(10개, `npm run test:db`에 등록) — **실제 동시 트랜잭션 두 줄**(psql 트랜잭션을 `pg_sleep(2)`로 붙잡고 다른 쪽을 같은 순간 실행):

| # | 순서 | 확인한 것 | 수정 전 | 수정 후 |
| --- | --- | --- | --- | --- |
| 1 | 삭제가 먼저 + 쌍 만들기 | 쌍 만들기가 기다렸다가 `record_purged`로 거절, 쌍 0건 | 실패(쌍이 만들어짐) | 통과 |
| 2 | 쌍이 먼저(커밋 전) + 삭제 | 삭제가 기다렸다가 쌍을 보고 원자료 보존 | 실패(원자료가 비워짐) | 통과 |

| 4 | 삭제가 먼저 + 수락(`pair_join`) | 수락이 기다렸다가 `bad-assessment`, 초대는 그대로 열림 | 실패(연결됨) | 통과 |

| 6 | 순서 없음 | 28번 · 29번 범위로 삭제한 결과를 가리키는 쌍 · 수락 · 번호 변경 거절 | 실패 | 통과 |
| 7 | 보존 | 이미 연결된 쌍은 한쪽이 삭제한 뒤에도 연결 해제 · 철회 가능, 없는 결과를 가리키는 옛 쌍 허용 | 통과 | 통과 |

- 기존 28 · 29번 DB 시험의 "29번이 마지막 번호" 가정은 30번이 생겨 "29번까지만 적용한 DB에 29번을 얹는다"로 바꿨다(점검 조건은 그대로, 30번은 `pair-purge.db.test.ts`가 같은 방식으로 본다).

## 5. 적용 순서 (테스트 전용 프로젝트, root가 SQL Editor에서 — **개발 세션은 외부 DB에 접속하지 않았고 적용하지 않았다**)

1. 29번이 이미 적용돼 있어야 한다(24번도). 아니면 30번 파일이 멈춘다.
2. `supabase/pair-assessment-guard-30-precheck.sql` → 종합이 OK인지 확인하고 "참고" 줄(번호 5 · 6)의 숫자를 적어 둔다. **번호 4(이미 원자료가 빈 분석을 가리키는 쌍)가 0이 아니면** 30번 이전에 이미 그 상태가 된 행이 있다는 뜻이다 — 30번은 고치지 않는다. 결과를 알려 달라(복구 방법은 운영자 결정 항목).
3. `supabase/migrations/20261109000000_pair_assessment_guard.sql`을 한 번만 실행한다.
4. `supabase/pair-assessment-guard-30-postcheck.sql` → 종합이 `OK — 30번이 적용됐다`이고 번호 5 · 6 숫자가 적용 전과 같아야 한다.
5. 통합 파일 `supabase/apply-staging-all.sql`(빈 새 스테이징 프로젝트 전용)은 30번까지 들어 있다.

## 5-1. 29번 + 30번 통합 적용 파일 `supabase/apply-29-30.sql` (2026-10-20)

29번만 먼저 적용하면 위의 틈이 열린 채로 남으므로, 두 번호를 **하나의 트랜잭션**으로 적용하는 파일을 만들었다(`node scripts/render-apply-sql.ts --29-30`, 생성기 `lib/ops/apply-sql.ts`의 `buildScope2930ApplySql`). 원본 29 · 30번 파일은 한 글자도 고치지 않고 그대로 이어 붙이며(서버 테스트가 같은지 확인), 따로 적용하는 경로도 그대로 쓸 수 있다.

- **시작 조건(하나라도 어긋나면 아무것도 바꾸지 않고 멈춤)**: 28번(기록 삭제 열 · 함수 · 표) · 24번(리포트 궁합 표 · `pair_join`) · 필요한 표 · 역할이 있어야 하고, **29 · 30번이 만드는 것이 하나도 없어야** 한다(이미 적용한 DB · 29번만 적용된 DB에서 다시 실행하면 여기서 멈춘다).
- **끝 확인(하나라도 어긋나면 전체 취소)**: 적용 전 · 후의 구조를 임시로 저장해 비교한다 — 열 · 제약 · 인덱스 · 정책 · 표 권한 · 함수 권한과 정의 · 트리거 · 사용자 자료 표(21개 중 있는 것)의 행 수와 행 내용. **새로 생긴 것은 열 `assessments.record_purged_at` · 함수 3개(권한 · 정의) · 트리거 5개 · `pair_join`의 새 정의뿐**이어야 하고 그 밖의 변화가 하나라도 있으면(다른 열 추가 · 권한 변경 · 행 변경) 취소한다. 그 밖에 새 함수의 브라우저 역할 실행 불가 · public 권한 없음 · `pair_join` · 28번 삭제 함수 권한 불변 · 삭제 완료 표시가 모두 비어 있음 · 트리거 5개가 올바른 표에 켜져 있음 · `pair_join`이 새 정의임을 확인한다.
- **고객 기록 삭제 함수(`delete_assessment_record_v2`)는 호출하지 않는다** — 만들기만 하고 확인은 카탈로그(존재 · 권한 · 정의)만 읽는다(서버 테스트가 우리가 더한 부분에 호출이 없음을 확인). 락 대기 15초 · 문장 180초 제한(`set local`)으로 오래 기다리며 다른 요청을 막지 않는다.
- 끝(commit 뒤)에 읽기 전용 `check-migrations.sql`이 붙어 29 · 30번이 "적용됨"인지 한 표로 본다. 사용 순서 · 안내는 파일 머리말에 있다.
- **로컬 검증(`supabase/tests/apply-29-30.db.test.ts` 5개, 실제 Supabase와 같은 기본 권한의 임시 DB)**: ① 28번까지 전부 적용한 DB와 **혜택 19~22번이 없는 테스트 DB 모양** 둘 다에서 한 번에 적용한 구조 = 29 → 30번을 따로 순서대로 적용한 구조, 사용자 자료 행 수 불변, 임시 객체 안 남음, 새 장치(삭제 표시된 결과를 가리키는 쌍 거절)가 동작 ② 다시 실행하면 시작 조건에서 멈춤 · 29번만 적용된 DB도 멈춤 ③ 24번 · 28번 선행이 없으면 멈춤 ④ **끝 확인이 틀리게 만든 변형 파일 5종이 전부 전체 취소**됨(30번의 권한 정리 줄을 뺌 · 끼어든 열 추가 · 끼어든 행 삭제 · 끼어든 행 내용 수정 · `pair_join` 새 정의를 뺌) — 취소 뒤 열 · 함수 · 트리거 · 임시 객체 · 끼어든 변경이 하나도 남지 않고 사용자 행이 그대로임을 확인.
- **외부 DB에서는 실행하지 않았다.** root가 검토한 뒤 테스트 전용 프로젝트의 SQL Editor에서 한 번 적용한다. 기존 개별 사전 확인 `delete-scope-29-precheck.sql`은 29번 적용 전에 그대로 쓸 수 있고, 30번 사전 확인은 29번 적용 전에는 "이상(선행 29번 없음)"이 정상이다(통합 파일이 둘을 함께 적용한다). 기존 `delete-scope-29-postcheck.sql`의 6번은 `delete_assessment_record_v2(null, null)`을 부르는 읽기용 점검(아무것도 하지 않고 `not_found`)이라 이 통합 파일에는 붙이지 않았다.

## 6. 확인하지 못한 것 · 한계

- **외부 DB(Supabase)에서는 확인하지 않았다.** 동시성 시험은 로컬 Postgres 16 + 로컬 PostgREST 중계에서 psql 트랜잭션으로 한 것이고, 실제 Supabase 연결 풀 · 지연 아래의 겹침은 시험하지 못했다. 잠금 동작 자체는 Postgres 기능이라 같다고 기대하지만 외부에서 확인한 것은 아니다.
- 이미 만들어진 "빈 원자료를 가리키는 쌍"이 외부 DB에 있는지 모른다(사전 확인 번호 4로 root가 읽어야 한다). 로컬의 5건은 이 재현이 만든 가상 계정 행이다.
- 연결된 쌍의 한쪽이 기록을 삭제하면 그 쌍이 쓰는 원자료는 남는다(29번 정책 그대로 — 하지 않은 것: 연결 해제된 쌍의 원자료를 비우기).
- 회원 탈퇴와 쌍 수락이 같은 순간 겹치는 경우(탈퇴가 지운 결과 번호를 가리키는 쌍)는 이 장치 밖이다 — 없는 결과를 가리키는 쌍은 설계상 허용되고 서비스가 "쓸 수 없는 결과"로 읽는다.
- 되돌리기: 이 변경은 새 트리거와 함수 정의뿐이다. 되돌리는 마이그레이션은 만들지 않았다 — 필요하면 새 마이그레이션으로 트리거를 지우고 `pair_join`을 24번 정의로 되돌린다(삭제 자체의 동작은 28 · 29번이므로 바뀌지 않는다).
