# 질문 3개 묶음 — 실제 환경에서 확인하기 (운영자가 한 단계씩 · 지금은 첫 단계만)

- 작성 2026-10-15 · 대상: **질문 3개 묶음 2,500원(부가세 포함, 낱개 없음)**. 운영자 요청: "실제 Supabase와 토스 테스트 키로 확인하는 **첫 단계만** 안내".
- **가짜 환경에서는 이미 확인했다**(가짜 결제 · 가짜 AI · 임시 DB). 그것은 **실제 환경의 확인이 아니다.** 이 문서는 운영자님의 **실제 Supabase + 토스 테스트 키 + 카카오(또는 이메일) 로그인**에서 확인하는 순서다.
- **돈이 나가는 단계는 없다.** 토스 **테스트 키**(`test_…`)의 결제는 실제로 청구되지 않는다. **실제 결제(`PAYMENTS_LIVE_MODE=true` + live 키)는 하지 않는다** — 이 문서를 모두 통과하고 운영자가 따로 승인한 뒤에만 한다. (코드도 막는다: 이용 기준이 확정되기 전에는 실결제 모드에서 질문 결제가 시작되지 않는다 — 문의 채널은 카카오톡 채널 "미유톡"으로 정해졌다.)
- **키 · 비밀값은 대화에 붙여넣지 않는다.** 값은 모두 `.env.local`(메모장)에 직접 적는다. 이 문서는 "어디에 적는지"만 안내한다.
- 막히면 **그 단계에서 멈추고** 화면(또는 오류번호 `ERR-…`)을 알려 주세요. 계속 눌러 보지 마세요.
- **이 문서에는 첫 단계만 자세히 적었다.** 첫 단계의 결과(○ / ✕)를 알려 주시면 다음 단계를 한 단계씩 안내한다. 뒤 단계의 목록은 아래 "첫 단계 통과 뒤"에 이름만 적었다.

## 첫 단계: DB 16번 적용 확인 → 테스트 결제 1건 → 질문 3개가 한 번만 들어갔는지 확인

**목표**: 실제 Supabase에서 새 DB 변경(16번)이 적용돼 있고, 토스 **테스트 키**로 묶음 하나를 결제했을 때 질문 3개가 **정확히 한 번** 들어가며 묶음 장부 한 줄이 생기는 것만 확인한다. (환불 · 부분 취소 · 웹훅은 이 단계에서 하지 않는다.)

### 1-0. 시작 전 (이미 하셨으면 건너뛴다)

| # | 할 일 | 확인 |
| --- | --- | --- |
| 1-0-1 | 최신 코드로 옮기기 — [`update-guide.md`](./update-guide.md) 1번(ZIP → 옛 `.env.local` 복사 → `miyu` 폴더에서 `npm.cmd ci`) | `npm.cmd run dev`가 켜진다 |
| 1-0-2 | `.env.local`에 **토스 테스트 키** — `NEXT_PUBLIC_TOSS_CLIENT_KEY`(`test_gck_…`) · `TOSS_SECRET_KEY`(`test_gsk_…`). **`PAYMENTS_LIVE_MODE`는 적지 않거나 `false`** | `http://localhost:3000/setup`의 결제 줄이 **테스트 환경**으로 나온다 |
| 1-0-3 | **AI 연결**(채팅 질문에 답하려면 필요) — [`update-guide.md`](./update-guide.md) 8번의 3~4단계(승인 금액 · 호출 수 · 기간을 `.env.local`에 직접 적기). 이 단계 전체가 수십 원 안쪽이다(질문 1건 약 17원 어림) | `/setup`의 "자유 질문 AI"가 "실제 Claude 연결됨" |
| 1-0-4 | 새 계정 하나로 시험한다(카카오 또는 이메일). 기존 구매 기록이 섞이지 않게 | 시험 계정이 있다 |

### 1-1. DB 적용 상태 확인 (읽기만 한다)

> **SQL Editor에는 파일 이름이 아니라 파일 안의 글(내용)을 붙여넣는다.** 파일 이름(`supabase\check-migrations.sql`)을 그대로 쓰면 `syntax error at or near "supabase"` 오류가 난다(2026-10-16 운영자 실행에서 실제로 난 오류). 아래 명령이 파일 내용을 클립보드에 복사해 준다 — PowerShell을 **`miyu` 폴더**에서 열고 칠 것.

1. 확인용 조회를 클립보드에 복사한다(읽기만 하는 조회):

   ```powershell
   Get-Content supabase\check-migrations.sql -Raw -Encoding UTF8 | Set-Clipboard
   ```

   Supabase 대시보드 → **SQL Editor** → New query → **붙여넣기(`Ctrl + V`)** → **Run**. (붙여넣은 글이 `-- ...`로 시작하는 긴 SQL이면 맞다. 한 줄짜리 파일 경로가 보이면 잘못 붙인 것이다.)
2. 결과 표에서 **13 · 14 · 15 · 16번**의 상태를 본다.
   - 13 · 14 · 15 · 16이 모두 **적용됨**이면 1-3으로 간다.
   - **16번(또는 15번)이 "아직 안 함"이면 1-2를 한다.** 13번이 "아직 안 함"이면 [`update-guide.md`](./update-guide.md) 2번 안내대로 13 → 14 → 15번을 번호 순서로 먼저 적용한다(질문 결제는 13번이 없으면 닫혀 있다 — 돈만 빠지는 일을 막는 안전장치).

### 1-2. 16번(와 15번) 적용 — 번호 순서로, 한 번에 한 파일

> **16번이 하는 일**: 질문 묶음별 장부 표(`question_packs`) · 부분 환불 반영 함수 · 무료 질문 한도 예약 함수를 **더한다.** 기존 회원 · 주문 · 결제 · 질문 · 리포트 데이터를 지우거나 바꾸지 않는다. (13번의 장부 검사 조건 몇 개를 "넓혀서" 다시 만든다 — 내역 종류에 `refund_claw`를 허용하기 위해서이며 기존 줄은 그대로 유효하다.) **실행만으로 누구의 질문도 늘거나 줄지 않는다.**
>
> **지금 쓰는 DB에 시험이 아닌 실제 고객의 결제가 있다면** 적용 전에 백업 상태를 먼저 확인하세요(`runbook.md` 백업 항목). 시험 데이터뿐이면 바로 해도 된다.

1. 15번 파일 내용을 복사한다:

   ```powershell
   Get-Content supabase\migrations\20261025000000_admin_credit_question.sql -Raw -Encoding UTF8 | Set-Clipboard
   ```

2. SQL Editor → New query → 붙여넣기(`Ctrl + V`) → **Run**. 오류가 없어야 한다.
3. 16번도 같은 방식으로(복사 → 새 쿼리에 붙여넣기 → Run):

   ```powershell
   Get-Content supabase\migrations\20261026000000_question_packs.sql -Raw -Encoding UTF8 | Set-Clipboard
   ```

4. 1-1의 확인용 조회를 다시 Run → **15 · 16번이 "적용됨"**.
5. 오류가 나면 **멈추고** 오류 문장을 그대로 알려 주세요(비밀값은 없다). 다시 Run 하지 마세요.

### 1-3. 시험 계정으로 무료 질문 쓰기

1. 시험 계정으로 로그인 → 무료 분석을 끝낸다(연애 방이 무료로 열린다).
2. 연애 상담방에서 **무료 질문 2번**을 쓴다. 두 번째 답이 오면 "무료 질문을 모두 썼어요" 안내창이 뜬다 → [구매 버튼으로 가기].
3. 확인(○/✕): 입력칸 자리에 **[질문 3개 구매하기]**(작고 연한 "2,500원 (VAT 포함)") 버튼 하나만 있고 **입력창 · 보내기 화살표는 없다.** (무료 질문이 남아 있을 때는 입력창 위에 절반 폭의 작은 구매 버튼이 하나 있다.)

### 1-4. 테스트 결제 1건

1. **구매 버튼을 한 번만** 누른다(질문은 적지 않는다) → 결제 화면(질문 3개 · 2,500원 · 부가세 포함 · 1개씩 결제하는 방법은 없어요).
   - **먼저 결제수단을 눈으로 확인한다(카드만 열기 — 알림이 아니라 실제 위젯 설정 확인):** 결제 화면에 "지금은 카드 결제만 지원해요."가 보이고, 토스 결제위젯에는 **카드만** 보여야 한다. **계좌이체 · 가상계좌 · 휴대폰 · 간편결제(토스페이 · 카카오페이 등) 중 하나라도 보이면 여기서 멈추고** 결제하지 말고 [`setup-guide.md`](./setup-guide.md)의 "카드만 열기"로 위젯 설정을 고친 뒤(환경변수를 바꿨다면 다시 배포) 이 화면을 새로 열어 다시 확인한다. 화면을 캡처해 두면 좋다.
2. 토스 **테스트 결제창**에서 테스트 카드로 결제한다(토스 개발자센터의 테스트 카드 안내를 따른다 — 실제 청구 없음).
3. 결제가 끝나면 **채팅방으로 돌아와 "질문 3개를 구매했어요. 궁금한 것을 적어 보내 주세요."** 안내가 보이고 입력창이 열려 있다. 질문을 하나 적어 보내면 답이 온다.
4. 확인(○/✕):
   - 입력창 안내가 **"결제해 둔 질문 2개가 남아 있어요"**이다.
   - MY → **"결제해 둔 질문 2개"**, 결제내역에 "유료 질문 3개 · 2,500원 · 결제 완료 · 테스트 결제".
   - 결제내역의 결제수단이 **카드**이다(다른 수단이면 운영자 알림 `payment.non_card`가 오고 `/admin`에서 주문을 열면 결제수단이 보인다).

### 1-5. 장부 확인 (읽기만 한다 — SQL Editor)

1. 장부 확인 조회를 복사해(`Get-Content supabase\check-cash.sql -Raw -Encoding UTF8 | Set-Clipboard`) 새 쿼리에 붙여넣고 Run. **합계에 충전 1건(9) · 사용 1건(−3)** 이 있고, **이번 시험 계정에 대한 "2 이상 징후" 줄이 없어야 한다.** (이전 시험으로 남은 줄이 있다면 이번 시험 줄인지 주문번호로 구분해 알려 주세요.)
2. 새 쿼리로 아래를 Run(읽기만, 새로 만들거나 바꾸는 것이 없다):

```sql
select o.order_number as "주문번호", p.questions as "산 질문", p.used as "쓴 질문", p.refunded_questions as "환불한 질문", p.refunded_krw as "누적 환불(원)", p.price_krw as "결제액(원)"
from public.question_packs p
join public.orders o on o.id = p.order_id
order by p.purchased_at desc
limit 5;
```

3. 확인(○/✕): 가장 위 줄이 **산 질문 3 · 쓴 질문 1 · 환불한 질문 0 · 누적 환불 0 · 결제액 2500**이다. (이 줄이 있다는 것이 16번이 실제로 동작해 묶음 장부가 만들어졌다는 뜻이다.)

## 첫 단계 통과 뒤 — 이어서 안내할 단계 (이름만 · 자세한 순서는 그때 한 단계씩)

운영자 요청에 따라 아래가 **확인 계획에 모두 들어 있다.** 가짜 환경에서는 이미 시험했고(`question-pack-policy-proposal.md` 9장) **실제 환경에서는 아직 한 번도 확인하지 않았다.**

| 단계 | 확인할 것 | 왜 실제 환경에서 봐야 하나 |
| --- | --- | --- |
| 2 | 새로고침 · 다른 브라우저 재로그인 후에도 잔여 질문 유지 | 실제 로그인 · 쿠키 · 저장 |
| 3 | 답을 받지 못하면 질문이 차감되지 않음 (승인 가드로 돈 없이 확인) | 실제 AI 연결 |
| 4 | 구매 버튼 두 번 · 같은 승인 주소 다시 열기 · 두 창에서 동시에 질문 | 실제 DB의 동시 처리 |
| 5 | **결제 직후 창을 닫은 경우**: 결제창에서 인증만 마치고 닫은 뒤 MY의 주문 화면 [결제사에 다시 확인하고 맞추기]로 질문이 **정확히 한 번** 들어가는지 | 토스의 실제 "진행 중 → 승인" 상태 · 조회 응답 |

| 6a | **고객이 다시 접속하지 않아도 환불이 반영되는가**(질문 사용 전 확인): 토스에서 834원 또는 1,667원만 부분 취소한 뒤 **미유 화면 · MY를 열지 않고**, 결제해 둔 질문이 남은 계정으로 질문을 보낸다 → 그 질문을 쓰는 순간 결제사 기록을 다시 확인해 환불이 먼저 반영되고(환불받은 질문은 쓰이지 않는다) `/admin`의 해당 주문에 환불 반영이 보인다. 이어서 하루가 지난 뒤 `/admin`의 "정기 점검 마지막 실행"이 찍혀 있는지 확인(Vercel Hobby는 하루 한 번) | 토스가 실제로 돌려주는 부분 취소 기록 · 실제 정기 실행 |
| 7 | **웹훅 중복 · 지연 · 순서 뒤바뀜**(테스트 배포를 Vercel "All Deployments" 보호로 올렸다면 웹훅이 서버에 닿지 않아 이 단계는 보호 방법을 따로 정한 뒤에만 확인할 수 있다 — [`deploy-vercel-test.md`](./deploy-vercel-test.md)): 배포 뒤 토스 개발자센터에 `…/api/webhooks/toss`를 등록하면 취소 알림이 오는지, 같은 알림이 여러 번 오거나 늦거나 순서가 뒤바뀌어도 질문이 한 번만 회수되는지(로컬에서는 알림이 오지 않으므로 [결제사와 대조해 맞추기]로 대신 확인) | 토스가 부분 취소 때 어떤 웹훅을 보내는지는 문서에 없다 |
| 8 | **환불 중 질문 사용**: 환불을 반영하는 동안 질문을 쓰는 경우 잔액이 어긋나지 않는지 | 실제 DB · 실제 응답 지연 |
| 9 | 전액 취소 → "환불 완료" · 남은 질문 회수 → 환불 뒤 다시 구매 | |
| 9a | **계좌 송금 환불 연습**(결제사 취소가 안 되는 경우의 대체 절차): 테스트 데이터의 묶음 하나로 [`runbook.md`](./runbook.md)의 "계좌 송금 환불"을 따라 `manual-refund-check.sql` → (송금은 실제로 하지 않고 연습) → `manual-refund-apply.sql` → check 다시. 환불한 질문 수 · 남은 질문이 맞게 바뀌고 운영 기록에 남는지, 결제 재확인이 이상으로 보지 않는지 | 실제 Supabase의 SQL Editor에서 두 파일이 도는지(로컬 Postgres에서는 시험했다) |
| 10 | 위가 모두 통과한 뒤에만, 운영자가 별도 승인하면 live 키로 **본인 카드 2,500원 소액 결제 → 환불** 한 번 (**클로드는 live 설정을 켜지 않는다**) | 테스트 키는 카드사 · 정산 · 수수료 · 취소 가능 기간 · 영수증을 실제와 똑같이 보여 주지 않는다 |

**실결제를 열기 전 필수(첫 단계로는 확인되지 않음)**: 정책 확정(환불 · 유효기간 · 탈퇴 — 문의 채널은 카카오톡 채널 "미유톡"으로 정해졌다) + 약관의 "출시 전 확정" 문구 제거 + 법적 검토 — [`question-pack-policy-proposal.md`](./question-pack-policy-proposal.md).

## 시험이 끝났을 때

- `.env.local`에서 AI 승인 값(`AI_PROVIDER` · `AI_CHAT_PROVIDER` · `AI_APPROVED_*`)을 지운다([`update-guide.md`](./update-guide.md) 8번 8단계).
- 시험 계정에 남은 질문은 이후 단계의 취소 시험에서 정리하거나 질문에 모두 쓴다(탈퇴는 남은 질문이 있으면 막혀 있다 — 임시).
