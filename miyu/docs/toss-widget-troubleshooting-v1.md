# 토스 테스트 결제 화면이 열린 뒤 약 60초 만에 오류가 나는 문제 — 조사 · 보존 기록 · 진단 장치 (2026-10-19)

> 결론부터: **원인은 확정하지 못했다.** 키 문제라고 단정하지 않는다. 이번에 한 일은 (1) 지난 측정 보존 (2) 코드와 토스 SDK에서 확인할 수 있는 사실 정리 (3) 다음 테스트 결제에서 **어느 단계의 어떤 오류인지 남도록** 화면을 고치고 (4) 막히면 스스로 멈춰 다시 불러올 수 있게 한 것이다.
> 실제 토스 서버 · 키 · 결제와는 통신하지 않았다(가짜 SDK 모의 검사). 기존 사용자 주문은 취소하거나 지우지 않았다.

## 1. 지난 실측 (사용자 보고 — 이 세션이 관찰한 값이 아니다)

| 항목 | 내용 |
| --- | --- |
| 일시 · 환경 | 2026-10-19, miutest(테스트 사이트) |
| 주문 | 신규 pending 주문 `MEU-20261019-UR4R3747X2`, 9,900원 |
| 화면 | "테스트 결제" 표시와 9,900원은 떴다. 토스 **결제수단 · 약관 iframe이 로딩된 뒤** 약 60초 후 일반 로딩 오류 |
| 재현 | 같은 주문을 다시 조회해도 같은 증상 |
| 결제 상태 | 승인 0 · 환불 0 · AI 호출 0 (결제된 것이 없다) |
| 처리 | 기존 주문은 건드리지 않았다(취소 · 삭제 없음). 1시간이 지난 결제 대기 주문은 기존 규칙대로 정리된다 |

## 2. 확인한 사실 (코드 · SDK 파일에서)

**우리 화면(고치기 전)**
- 결제수단 칸과 약관 칸의 id가 고정(`toss-payment-methods` · `toss-agreement`)이었다. Next.js 16은 떠난 화면을 숨긴 채 문서에 남기므로(`CLAUDE.md` 코드 구조 아래 주의), 같은 화면이 두 번 열린 적이 있으면 `#id` 선택자가 숨겨진 옛 칸을 가리킬 수 있다.
- `catch { setStatus("error"); ... }`가 **오류 객체를 버렸다.** 그래서 어느 단계에서 어떤 코드로 났는지 어디에도 남지 않았다. 오류 문구는 우리가 쓴 일반 문구였다 — 사용자가 본 "일반 로딩 오류"가 이것이다.
- 막힌 뒤에는 다시 시도할 방법이 새로고침뿐이었다.

**우리 서버 설정**
- 결제 키는 서버가 모양을 검사한다: 테스트 모드는 `test_gck_`(클라이언트) · `test_gsk_`(시크릿)만 받는다(`server/env.ts`). API 개별 연동 키(`test_ck_`)로는 시작하지 않는다. **miutest에 실제로 들어 있는 값은 이 세션이 볼 수 없다.**
- 응답 헤더(`next.config.ts`)에 CSP · COOP/COEP가 없고 `Permissions-Policy`는 camera · microphone · geolocation만 막는다. `X-Frame-Options: DENY`는 우리 페이지를 남이 iframe에 넣는 것을 막는 것이라 토스 iframe을 우리 페이지에 넣는 것과 무관하다. → 우리 헤더가 토스 위젯을 막을 근거는 코드에서 찾지 못했다(실제 위젯으로 확인하지는 못했다).

**토스 SDK**
- npm 패키지 `@tosspayments/tosspayments-sdk` 2.8.1은 로더일 뿐이고 실제 SDK는 `https://js.tosspayments.com/v2/standard`를 불러온다(이 세션에서 받아 읽기만 했다 — HTTP 200 · 509,707바이트 · 실행하지 않았다).
- 호스팅 SDK에는 **화면(iframe)과 주고받는 요청의 기본 대기 시간 60,000ms**가 있고 시간이 지나면 오류 코드 `REQUEST_TIMEOUT`이 난다. 관찰한 "약 60초 뒤 오류"는 이 값과 맞는다 — 즉 **화면 쪽에서 SDK의 요청에 답이 오지 않았을 가능성**이 한 가지 설명이다. 왜 답이 안 왔는지는 알 수 없다.
- 토스가 공개 오류로 구분하는 코드(일부): `INVALID_CLIENT_KEY` · `NOT_SUPPORTED_API_INDIVIDUAL_KEY` · `NOT_SUPPORTED_WIDGET_KEY` · `INVALID_CUSTOMER_KEY` · `INVALID_VARIANT_KEY` · `PAYMENT_METHODS_WIDGET_ALREADY_RENDERED` · `AGREEMENT_WIDGET_ALREADY_RENDERED` · `INVALID_SELECTOR` · `NOT_SETUP_AMOUNT` · `NAMESPACE_CHANGE_REQUIRED` · `INSECURE_KEY_USAGE` · `PROVIDER_STATUS_UNHEALTHY` · `NETWORK_ERROR` · `REQUEST_TIMEOUT`. **그 밖의 오류는 SDK가 자기 쪽 로그에만 남기고 `UNKNOWN_ERROR`로 바꿔 돌려준다** — 우리 화면에서 보이는 것은 이 일반 코드뿐일 수 있다.

## 3. 가능한 원인 후보 (모두 미확인 — 새 보고로 가릴 수 있는 것과 없는 것)

| 후보 | 새 보고에서 보이는 모습 | 확인 방법 |
| --- | --- | --- |
| 토스 어드민 설정(결제 UI `variantKey`가 없거나 게시되지 않음 · 결제수단 목록 · 위젯 사용 상태) | `INVALID_VARIANT_KEY` 또는 `render` 단계 `REQUEST_TIMEOUT` / `CLIENT_TIMEOUT` | Vercel `TOSS_WIDGET_VARIANT_KEY`를 비우고(기본 `DEFAULT`) 다시 시험. 값이 있으면 토스 어드민의 그 UI 이름과 글자 하나까지 같은지 확인 |
| 키 종류 · 짝 | `INVALID_CLIENT_KEY` · `NOT_SUPPORTED_API_INDIVIDUAL_KEY` · `NOT_SUPPORTED_WIDGET_KEY` | 코드가 `test_gck_` 모양만 받으므로 모양 문제일 가능성은 낮다. 클라이언트 키와 시크릿 키가 **같은 상점**의 위젯 키인지 확인 |
| 브라우저 · 네트워크(앱 안 브라우저, 저장소 · 쿠키 차단, 광고 차단, 회사/학교망) | 보고의 `브라우저` · `저장소 blocked` · `쿠키 꺼짐` · `sdk` 단계 `SDK_LOAD_FAILED` | 같은 주문을 PC 크롬과 휴대폰 사파리 · 크롬에서 각각 열어 보고를 비교 |
| 숨겨진 옛 화면과 칸 id 겹침 | 보고의 `결제 칸 N개`가 2 이상 · `*_ALREADY_RENDERED` | **이번에 고쳤다**(화면마다 다른 id). 보고에 칸 수가 남는다 |
| 토스 쪽 일시 장애 · 점검 | `PROVIDER_STATUS_UNHEALTHY` 또는 시간이 지나면 저절로 해결 | 시간을 두고 다시 |
| 개발 모드에서 효과가 두 번 실행(로컬 개발 서버) | (운영 빌드에서는 해당 없음) | 한 틱 뒤에 시작하게 해 한 번만 그리도록 했다 |

## 4. 이번에 고친 것

- `lib/commerce/widget-session.ts`(채널 독립): 준비 과정을 **단계(sdk → init → amount → render)**로 나누고 단계마다 시간을 재며, 토스가 돌려준 `code`를 그대로 들고 있다. **30초 안에 준비되지 않으면 `CLIENT_TIMEOUT`으로 스스로 멈춘다**(SDK의 60초보다 먼저). 멈추거나 실패하면 이미 그려진 한쪽 화면(예: 약관만)을 치우고, 늦게 도착한 화면도 치운다.
- `components/checkout/toss-checkout.tsx`: 칸 id를 화면마다 다르게(`useId`), 화면이 사라지거나 다시 시도할 때 위젯을 치움, 실패하면 이유에 맞는 안내 + **[결제 화면 다시 불러오기]**. 안내는 원인을 단정하지 않고 "아직 결제되지 않았어요"를 먼저 알린다. 결제 금액 · 승인 로직은 건드리지 않았다.
- `app/checkout/[orderNumber]/widget-actions.ts`: 막혔을 때 **단계 · 오류 코드 · 걸린 시간 · 시도 횟수 · 환경 사실**을 운영 기록(`/admin` 알림 목록, 텔레그램이 연결돼 있으면 `[미유·테스트]` 알림)으로 남긴다. 로그인한 본인의 주문에만 받고, 값은 서버가 열거형 · 범위로 다시 확인한다. 같은 주문 · 단계 · 코드는 6시간에 한 번만 알린다. 한 번 열 때 보고는 최대 3건. 결제 상태는 바꾸지 않는다.
  - 담는 것: 주문번호 · 단계 · 코드 · 시간 · 시도 횟수 · 브라우저 종류(카카오톡 · 네이버 · 인스타 등 앱 안 브라우저 여부) · 보안 연결 · 저장소/쿠키 사용 가능 · 온라인 · 최상위 창 · 결제 칸 수 · 화면 표시 상태 · 오류 문구(160자, 키 · 연락처는 서버가 가림).
  - 담지 않는 것: 이름 · 생년월일 · 키 · 사용자 에이전트 원문 · 주소(URL) · 결제 키(paymentKey).
  - 구매자가 결제창을 닫거나 약관에 동의하지 않은 것(`USER_CANCEL` 등)은 막힘으로 기록하지 않는다.
- `/dev/toss-widget`(내 컴퓨터에서만) + `scripts/qa-toss-widget.ts`: 가짜 SDK로 정상 · 끝내 열리지 않음 · 코드 오류 · SDK 불러오기 실패 · 화면 두 개 · 결제창 닫기를 브라우저(크롬)에서 확인한다.

## 5. 확인한 것 · 못 한 것

확인함 (가짜 SDK · 로컬):
- 단위 시험 `lib/commerce/widget-session.test.ts` 7개: 단계별 오류 코드 보존 · 30초 시간 초과 · 늦게 도착한 화면 정리 · 취소 · 처리되지 않은 거절 없음 · 보고 값 재검증(모르는 값 버림 · 낯선 필드 버림 · 구매자 취소 제외).
- 정적 보호 `server/toss-widget-guard.test.ts` 5개: 고정 id 없음 · 본인 주문만 · 결제 상태 불변 · 보고 필드 고정.
- 브라우저 모의 `scripts/qa-toss-widget.ts` 7개 장면(크롬 · 390px): 정상 / 열리지 않음(시간 초과 → 보고 → 다시 불러오기 → 한 쌍만 그려짐) / 코드 오류 보존(`INVALID_VARIANT_KEY`) · 보고 3건 상한 / SDK 불러오기 실패 → 재시도 / 화면 두 개가 서로의 칸에 그리지 않음 / 결제창 닫기는 기록하지 않음 · 그 밖의 시작 오류는 `pay` 단계로 기록 / 좁은 화면 넘침 없음.

**확인하지 못한 것 (합격 처리하지 않는다)**
- **실제 토스 결제위젯이 왜 약 60초 뒤 오류를 냈는지** — 재현하지 못했다. 이 세션은 토스 테스트 키와 miutest 환경값이 없고, 외부 토스 테스트 실행은 사용자가 조율하기로 했다.
- 새 화면이 실제 토스 위젯에서 정상적으로 그려지는지 · 실제 오류 코드가 무엇으로 오는지(가짜 SDK는 우리 화면의 행동만 본다).
- 실제 휴대폰 · 카카오톡 앱 안 브라우저의 동작.
- 고친 id 방식이 토스 위젯의 선택자 처리와 문제없이 맞는지(`#toss-methods-…` 같은 일반 id 선택자이므로 문제 없을 것으로 보지만 실제 위젯으로는 확인하지 못했다).

## 6. 다음 테스트 결제 때 (사용자가 조율 — 토스 테스트 키 · 테스트 사이트만, 실제 금전 결제 아님)

1. 배포 반영 확인 후 같은 주문(또는 새 테스트 주문 1건)의 결제 화면을 **PC 크롬**과 **휴대폰(사파리 또는 크롬)**에서 각각 연다. 앱 안 브라우저(카카오톡)에서도 한 번 열어 본다.
2. 정상이면 결제수단 · 약관 화면이 뜨고 **결제하기** 버튼이 켜진다 → 테스트 카드로 성공 / 취소 / 실패를 시험한다.
3. 막히면 최대 30초 뒤 "결제 화면이 제때 열리지 않았어요…"와 **다시 불러오기** 버튼이 나온다. 그때 `/admin`의 알림 목록(종류 `checkout.widget`, 텔레그램 연결 시 알림)에서 **단계 · 코드 · 환경 줄**을 그대로 알려 준다.
4. 코드별 다음 행동: `INVALID_VARIANT_KEY` → `TOSS_WIDGET_VARIANT_KEY` 비우기 또는 어드민의 UI 이름과 대조 / `SDK_LOAD_FAILED` → 광고 차단 · 네트워크 · 다른 브라우저 / `저장소 blocked`나 앱 안 브라우저 → 일반 브라우저에서 열기 / `결제 칸 2개 이상` → 알려 주기(숨겨진 옛 화면) / `CLIENT_TIMEOUT`만 반복 → 토스 개발자센터 문의 시 이 줄 전체를 첨부.
5. 어떤 경우에도 **결제 상태의 기준은 결제사 기록**이다 — 이 화면의 오류는 결제가 되었다는 뜻도 안 되었다는 뜻도 아니다(아직 결제되지 않았다고 안내하는 것은 승인 요청 전 단계의 실패이기 때문이다. 결제창에서 승인 뒤 돌아오지 못한 경우는 기존 대조 절차가 맡는다).

## 7. 되돌리기

화면(`toss-checkout.tsx`)과 새 파일들만 바뀌었고 DB · 결제 로직 · 환경변수 변경은 없다. 이전 화면으로 돌리려면 이 커밋을 되돌리면 된다(고정 id와 오류 버리는 catch가 돌아오므로 권하지 않는다).
