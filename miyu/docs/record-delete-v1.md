## 1. 무엇이 지워지고 무엇이 남는가

| 지운다(복구할 수 없다) | 남긴다 |
| --- | --- |
| 이 검사 결과로 받은 개인 통합 리포트 · 고민 반영 리포트의 본문(만족도 의견 포함) | 계정 · 가입 동의 기록 |
| 맛보기 리포트의 글(줄은 남기고 글만 `{"deleted": true}`로 비운다) | 주문 · 결제 · 환불 기록(결제 증빙) |
| 고민 입력 기록 · 고민 기록 | 질문권(지갑 · 묶음 장부) · 채팅 질문 횟수 · 저장한 채팅 요약 |
| 채팅방의 "행동 목록"(리포트 글을 다시 그리는 데만 쓰던 것 — 대화 내용은 읽기용 기록으로 옮긴다) | 사주 궁합 · 리포트 궁합(별개 상품이라 건드리지 않는다) |
| | AI 사용 기록(토큰 수뿐) |
| | 대화를 이어 가는 데 쓰는 **분석 원자료**(입력한 정보 · 응답 · 계산 결과 — 결과 화면 · 리포트로는 다시 보이지 않는다) |
| | **읽기용 대화 기록**(새 표 `talk_transcripts`) |

"복구할 수 없다"는 **리포트 본문과 리포트 전용 데이터**에 대한 말이다. 분석 원자료는 채팅이 이어지도록 남으므로 "모든 정보가 삭제된다"고 쓰지 않는다(확인창 · 화면 문구도 같다).

**맛보기 무료 한 번이 다시 생기지 않는다**: `taste_reports`는 계정당 한 줄이라 줄을 남기고 글만 비운다. 삭제 뒤 새 분석을 해도 "이미 다른 결과로 받았어요"(`used-elsewhere`)다.

## 2. 대화는 어떻게 남나 (원문 없이도 읽힌다)

대화방은 "눌렀던 행동 목록"만 저장하고 풀이는 리포트에서 다시 그리는 구조라, 리포트 본문을 지우면 옛 대화를 다시 그릴 수 없다. 실제 조건에서는 저장된 채팅 요약이 0개였다. 그래서 **삭제 직전에 서버가 기존 렌더러(`replayRoom`)로 그 방에 이미 표시된 말만 글 줄로 옮겨** `talk_transcripts`에 남긴다.

- 리포트 전체 본문을 옮기는 것이 아니다(대화 중에 열어 본 부분만 · 열어 보지 않은 풀이는 없음). 새로 만든 글도 없다 — AI · 결제를 부르지 않는다(`server/talk-transcript.ts`, 정적 시험이 확인).
- 읽기용 줄: 내가 한 말 / 미유가 한 말 / 가운데 알림. 그림 · 표(특징 카드 · 시기 그림 · 관계 반응 단계 · 분석 카드)는 글로만 적는다. 줄 수 500 · 한 줄 4,000자 한도.
- 삭제한 기록의 채팅방에서 이 글이 위쪽에 읽기 전용("이전 대화예요…")으로 보이고, **이어 갈 수 있는 방**(나를 알아보기 · 오늘의 운세 · 고민 상담 · 연애 — 무료 리포트로 열리는 방)은 그 아래 "여기부터 새 대화"에서 새 대화가 계속된다.
- **이어 갈 수 없는 방**(올해의 흐름 · 결혼 · 진로 · 재무 — 풀이를 리포트 글에서 가져오던 방)은 읽기 전용 화면에 지난 대화 + 이유("리포트를 삭제한 기록이라 새 대화를 이어 갈 수 없어요")만 보이고 구매 안내는 하지 않는다.
- 동시 대화: 읽은 뒤 대화방이 바뀌었으면(DB가 `updated_at`을 대조) 아무것도 쓰지 않고 `stale`을 돌려주고, 앱이 다시 읽어 옮긴다(최대 3번). 옮기지 못하면 아무것도 지우지 않는다(`transcript-failed`). 삭제 전에 열어 둔 다른 탭의 저장은 "표지(epoch)"가 달라 거절된다.

## 3. 삭제 뒤 막히는 것

모든 길이 서버에서 먼저 막히고 DB가 마지막으로 한 번 더 막는다.

| 길 | 막는 곳 |
| --- | --- |
| 결과 화면 · `?r=` · `#r-purchase` | `getResultView`가 `deleted`를 돌려주고 페이지가 삭제 안내만 보인다 |
| 리포트 다시 만들기 · 결제된 주문의 재생성 | `queueReport`가 줄을 만들지 않음 + `reports` 입력 트리거 |
| 다시 구매 · 새 주문 | `startCheckout`(`record-deleted`) + `orders` 입력 트리거(질문 결제 주문은 허용) |
| 삭제 전에 만든 결제 대기 주문의 승인 | `confirmPayment`가 취소하고 결제사에 승인 요청을 보내지 않는다 |
| 맛보기 글 | 서비스(`deleted`) + `taste_reports` 입력 · **수정** 트리거(늦게 도착한 생성 응답 · 직접 갱신도 막음) |
| 고민 · 초대 · 혜택 견적 · 새 궁합 · 새 연결 | 각 서비스가 삭제한 기록을 찾지 못한 것으로 처리 |

## 4. 안전선

- 서버 액션: 로그인 회원 번호로만 일하고(화면이 보낸 회원 번호는 받지 않음) 소유자를 서비스와 DB 함수가 두 번 확인한다. Server Action의 출처 검사가 기본 CSRF 방어다. 다른 계정 · 비로그인이 같은 요청을 재전송해도 아무것도 지워지지 않음을 브라우저 E2E로 확인했다.
- 삭제 함수는 한 트랜잭션 · 검사 결과 행 `for update` 잠금 · 같은 요청 여러 번은 한 번만(`unchanged`). 진행 중인 생성 · 1시간 안의 결제 대기 · 리포트 줄 없는 결제 완료 궁합 · 맛보기 작성 중 · 답을 기다리는 질문 · 30초 안의 질문/질문권 사용이 있으면 `busy`.
- 권한: 삭제 함수는 `service_role`만. 새 트리거 함수 4개는 PUBLIC · `anon` · `authenticated` 실행 권한을 거둠. `talk_transcripts`는 PUBLIC · anon · authenticated · service_role의 기본 권한을 먼저 모두 거둔 뒤 회원 `select` / 서버 `select, insert`만 다시 준다(실제 Supabase는 새 표에 서버 역할 ALL을 자동으로 주므로). 기존 표 · 기본 권한 설정은 바꾸지 않는다 — 시험이 확인.
- 탈퇴하면 읽기용 대화 기록도 지워진다(프로필 탈퇴 표시 트리거 — 탈퇴 함수는 바꾸지 않음). 탈퇴 · 전체 purge · 유료 권한 · 장부는 건드리지 않는다.

## 5. 알려진 한계 (정직하게)

1. **분석 원자료는 남는다** — 채팅이 이어지도록. 완전한 개인정보 삭제는 기존 회원 탈퇴 절차다.
2. 리포트 풀이가 필요한 4개 방은 삭제 뒤 새 대화를 이어 갈 수 없다(읽기만). 이어 가고 싶으면 새 분석 후 새 리포트가 필요하다.
3. 삭제 전에 화면에만 있고 서버에 저장되지 않은 말(저장 직전의 대화)은 읽기용 기록에 없다. 동시에 막 저장되려던 낡은 탭의 저장이 삭제 직후 한 줄 끼어들 수 있는 아주 짧은 틈(수 ms)이 있다 — 읽어서 새는 본문은 없고 새 대화 줄 하나가 생기는 정도다.
4. 삭제 전에 만들어 둔 **초대 링크**는 남는다(할인 기록 보존). 삭제한 기록으로는 새 링크를 만들지 못한다.
5. 삭제 전에 만든 결제 대기 주문이 결제사에서 이미 승인된 경우(웹훅 경로)에는 운영자 환불 확인이 필요할 수 있다 — 승인 요청은 보내지 않지만 결제창에서 끝낸 건은 결제사 기록이 기준이다.
6. 숨기기(27번)의 열 · 함수는 외부 테스트 DB에 적용돼 있어 지우지 않고 쓰지 않는다. 롤백이 필요하면 코드를 되돌려도 28번의 열 · 표는 남아 있어도 해가 없다(기능만 꺼짐). 이미 삭제한 기록은 되살릴 수 없다.
7. 읽기용 대화 기록의 글은 삭제 시점의 화면 글이라, 이후 지시문 · 문구가 바뀌어도 옛 글 그대로다(의도한 동작).

## 6. 이번에 확인한 것과 확인하지 못한 것

- **확인(로컬 · 가상 데이터 · 비용 0)**: 위 시험 전부 + 로컬 앱/스택/Chromium E2E 76개(390 · 320px) + 재생성 · 재구매 차단을 실제 로컬 DB에서 확인. 외부 테스트 DB 적용은 root가 28번 파일 하나만 적용했고 삭제 RPC는 호출하지 않았다.
- **확인하지 못함 (환경 한계)**: 삭제 뒤 직접 적는 질문의 **AI 답**. 로컬 가짜 AI가 채팅 검사를 통과하는 답을 만들지 못해 삭제하지 않은 기록에서도 같은 실패가 나온다(이번 범위 밖). 서비스 경로는 단위 시험으로 보완.
- **확인하지 못함**: 실제 휴대폰 · miutest 배포본에서의 화면 — 배포 뒤 root가 확인창 열기/취소만 확인한다. 실제 사용자 기록 삭제는 어떤 세션에서도 하지 않는다.

## 7. 확인창이 작은 화면에서 잘리던 문제 (실기기 보고 2026-10-19)

## 8. 확인창이 어두운 배경만 남고 안 뜬다는 보고 (2026-10-19, 7장 수정 뒤 사용자 보고 — 이 장이 7장의 "본문 고정" 부분을 대체한다)

보고: 현재 miutest에서 "기록 삭제"를 누르면 배경만 어두워지고 확인창이 보이지 않아 삭제할 수 없었다. 7장의 모바일 높이 수정(`fda1355`)만으로는 닫히지 않았다.

**먼저 말해 둘 것: 이 환경(Chromium)에서는 "배경만 남는" 상태를 재현하지 못했다.** 7장의 하네스 132개 검사와 root의 miutest 확인은 모두 Chromium이었고 통과했다. 사용자의 기기(iPhone · 카카오톡 앱 안 브라우저로 추정, 정확한 기기는 모른다)는 WebKit이라 같은 코드가 다르게 동작했을 가능성이 크다. WebKit이 이 환경에 없어 원인을 **확정하지 못했고**, 아래는 "7장에서 새로 넣은 것 중 브라우저마다 다르게 그릴 수 있는 곳"을 조사해 위험을 없앤 것이다.

### 조사한 것(정적 확인 · Chromium 실측)

| 점검 항목 | 결과 |
| --- | --- |
| 확인창이 있는 조상의 stacking context · `transform` · `filter` · `opacity` · `overflow` · `content-visibility` · `contain` | MY 카드(`<li>`)에서 문서 맨 위까지 해당 속성이 없다(리스트 `overflow-hidden`은 다른 목록). 네이티브 `<dialog>`는 맨 앞 레이어(top layer)에 그려져 조상의 `z-index` · `overflow`의 영향을 받지 않는다. 사이트 머리글(`sticky z-30 backdrop-blur`)은 형제 요소다 |
| portal | 네이티브 `<dialog>`(top layer)라 portal이 필요 없다. 별도 overlay 요소도 없다 — "배경"은 `dialog::backdrop`이다 |
| **7장이 새로 넣은 두 가지**(7장 수정 전에는 확인창이 (잘렸지만) 보였다) | ① 열기 직전 **본문 `position: fixed; top: -스크롤px`**(스크롤 잠금) ② 확인창 안쪽을 **`flex-1`(= `flex: 1 1 0%`) 중첩 flex**로 나눈 구조. 둘 다 Chromium에서는 문제가 없지만, 브라우저에 따라 ①은 맨 앞 레이어의 위치(화면 밖으로 밀림), ②는 높이가 정해지지 않은 창에서 0% 기준 높이(창이 0 높이가 되어 `overflow: hidden`이 내용을 모두 가림)에서 어긋날 수 있다 — 어느 쪽이든 어두운 배경(`::backdrop`)은 그려지고 창만 안 보이는 모양이 된다. 사용자가 "하단으로 스크롤한 뒤 누를수록" 문제가 커졌는지(①은 스크롤 양만큼 어긋남)는 확인하지 못했다 |
| Chromium 실측 | 맨 아래 스크롤 · 짧은 화면 · 반복 열기/닫기 · 키보드 · 회전 · 높이 변화 모두 정상(아래). 즉 코드의 일반적인 논리 오류는 찾지 못했다 |

### 고친 것(화면 · CSS만 — 삭제 서버 로직 · SQL 28번 · 승인 · AI · 결제 설정 불변)

- **`components/my/body-scroll-lock.ts`**: 본문 `position: fixed` 방식을 없앴다. 문서 `html` · `body`의 `overflow: hidden`만 걸고(데스크톱은 스크롤바 폭만큼 오른쪽을 채움) **스크롤 위치는 건드리지 않는다**(그래서 닫을 때 되돌릴 위치도 없다). `overflow: hidden`을 무시하는 오래된 iOS를 위해 모달 안에서 스크롤할 수 있는 칸(`[data-scroll-ok]`)이 아닌 곳의 손가락 이동(`touchmove`, `passive: false`)은 막는다. 한계: iOS 15 이하에서 안내 칸 끝에서 더 밀면 뒤쪽 화면이 따라 움직일 수 있다(7장의 "뒤쪽 화면 불변"은 Chromium 기준으로만 확인).
- **`components/my/delete-record-button.tsx` · `app/globals.css`**: 확인창을 **위 고정(제목 · 삭제할 기록 · 경고) / 가운데 안내(`flex: auto`, `min-height: 0`, 안에서만 스크롤) / 아래 고정(취소 · 삭제하기)**의 직접 자식 세 개로 바꿨다. 서버 액션을 부르는 `<form>`은 아래 고정 줄만 감싼다(안내 전체를 감싼 중첩 flex를 없앰). `flex-1`(0% 기준)을 쓰지 않는다. 시험이 `flex-1`이 없음을 확인한다.
- **안전장치(어두운 배경만 남는 상태에서 막다른 길이 되지 않게)**: 연 직후 두 번 그린 뒤 `isVisiblyRendered`(`components/my/visible-check.ts`: 숨김 · 크기 · 제목이 화면 안인지 · 제목 자리를 누르면 이 창 안의 것이 눌리는지)로 확인하고, **보이지 않으면 확인창을 닫고(어두운 배경 제거) 같은 안내 · 같은 두 버튼 · 같은 서버 액션을 카드 안(일반 문서 흐름)에 펼친다.** `showModal()`이 오류를 내는 브라우저도 같다. 펼침에서도 취소 · Esc는 아무것도 지우지 않고, 삭제하기는 확인한 뒤에만 지운다. 판단이 틀려 멀쩡한 창을 "안 보인다"고 해도 같은 내용이 카드 안에 열릴 뿐 확인 절차는 똑같다. 닫을 때 눌렀던 "기록 삭제" 버튼으로 초점이 돌아온다.

### 확인한 것(비용 0 · 가상 카드 · 가짜 삭제 액션 · DB 없음 — 실제 사용자 기록은 건드리지 않았다)

실제 컴포넌트 파일을 그대로 복사해 가짜 삭제 액션(아무것도 지우지 않음)과 함께 띄우는 임시 하네스(저장소 밖)에서 Chromium 모바일 에뮬레이션(터치 · 휠 · 키보드):

1. **7장의 132개 검사를 새 구조로 다시** 통과(320x568 · 390x650 · 390x844 · 667x375 · 568x320 · 844x390 · 568x260: 열자마자 제목 · 삭제할 기록 · 두 버튼이 화면 안, 창 스크롤 없음, 초기 초점 제목, 휠은 가운데 안내만 이동, 배경 문지르기는 뒤쪽 위치 불변, Tab 이동 · 높이 변화 · 회전 뒤에도 화면 안, Esc · 취소 · 바깥 누르기 뒤 초점 복원, 삭제하기 두 번 눌러도 가짜 액션 1번). 바뀐 기대: 배경 잠금 = 문서 `overflow: hidden` · 스크롤 위치 그대로 · 본문 fixed 아님 · 닫으면 잠금 해제.
2. **"배경만 남는" 상태를 일부러 만들어** (확인창 높이 0 · 화면 밖으로 3000px · `visibility: hidden` · `opacity: 0` · `showModal` 오류) 4개 화면 크기에서 확인창이 닫히고 카드 안 펼침이 열려 제목이 화면 안으로 오는지, 취소 · Esc가 삭제 호출 0으로 닫고 초점을 돌려주는지, 삭제하기(가짜)가 한 번만 호출되고 끝나면 닫히며 잠금이 남지 않는지 — 20개 조합 모두 통과(합 126개 검사 중 실패 0).
3. **페이지 맨 아래 스크롤 · 짧은 화면(390x650 · 320x568)에서 12번 반복** 열기/닫기(Esc · 취소 · 바깥 번갈아) — 매번 화면 안, 펼침으로 바뀌지 않음, 잠금 해제, 초점 복원, 스크롤 위치 그대로. 키보드만으로 열기(Enter) → Tab은 창 안에서만 돎(안내 영역 → 취소 → 삭제하기) → 취소에서 Enter로 닫힘 · 삭제 호출 0.
4. 소스 시험(`server/record-delete-guard.test.ts` 10개): 지우는 곳이 확인창 안 `삭제하기`뿐 · form이 아래 줄만 감쌈 · `flex-1` 없음 · 본문 고정 없음 · 보이는지 확인 → 펼침 · 펼침도 같은 서버 액션 한 곳.

### 한계 · 아직 모르는 것 (합격으로 세지 않는다)

- **실제 iPhone · 카카오톡 앱 안 브라우저에서 확인창이 뜨는지는 확인하지 못했다.** 위 수정은 가장 의심스러운 두 곳을 없앤 것이고, 그래도 안 뜬다면 안전장치가 같은 내용을 카드 안에 펼친다 — 사용자는 어느 쪽이든 삭제 확인을 볼 수 있어야 하며, 그것을 실기기로 확인해야 한다.
- 안전장치가 "보이지 않는다"고 판단하는 기준은 위 네 가지다. 기기가 이 조건을 통과하지만 사람이 보기엔 안 보이는 경우(예: 색 대비 문제)는 잡지 못한다.
- 짧은 화면(높이 240px 미만) · iOS 15 이하의 뒤쪽 화면 따라 움직임은 7장의 한계 그대로이거나 위에 적은 대로다.
- 사용자가 눌러 본 기기 · 브라우저 · 화면 크기를 알려 주면(또는 `window.innerHeight` · 확인창 위치 스크린샷) 원인을 더 좁힐 수 있다.
