# 결제 출시 필수 QA 대조 — 순서별 증거와 구체적 누락 목록 (2026-10-19)

> 대상은 **테스트 전용 사이트(miutest) · 테스트 전용 DB · 토스 테스트 키**뿐이다. 실결제 · 운영 배포 · 새 AI 호출은 하지 않았고 이 문서의 어느 줄도 출시 GO가 아니다.
> 이 세션은 가짜 결제사(로컬)까지만 확인할 수 있다 — **실제 토스 테스트 모드 실행은 사용자가 구성과 변경분을 검토한 뒤 조율한다.**

## 0. 먼저: 출시를 막는 오류가 있는가

- **이번 대조에서 새로 확인된 "결제를 잘못 받거나 권한을 잘못 주는" 제품 오류는 없다.** 금액 · 소유자 · 중복 승인 · 웹훅 순서 · 환불 뒤 권한 · 타인 열람의 빈틈을 7개 시험으로 더 찔러 보았고 모두 막혀 있었다(`lib/services/payment-lifecycle.test.ts`).
- **고친 것 1건(작은 UX 결함)**: 결제사가 "아직 승인 전(IN_PROGRESS)" 같은 상태를 돌려주면 `confirmPayment`가 **문구가 빈 거절**을 돌려줬다 → 결제 확인 화면이 빈 안내가 될 수 있었다. 안내 문구를 채웠다(주문은 대기로 남고 재확인이 결제사 기록으로 맞춘다 — 결제 판단은 바뀌지 않았다).
- **출시 전 반드시 풀어야 하는 막힘 1건**: 테스트 결제 화면이 약 60초 뒤 오류로 끝나는 문제(MEU-20261019-UR4R3747X2)는 **원인이 확정되지 않았다.** 진단 장치를 넣었고(`docs/toss-widget-troubleshooting-v1.md`) 다음 실제 테스트 결제에서 단계 · 코드가 남는다. 이것이 풀리기 전에는 아래 1~4단계의 "실제 토스" 줄을 시작할 수 없다.

## 3. 실제 토스 테스트 실행 순서 (사용자가 조율 — 이 순서를 권한다)

1. 이 변경(진단 장치 포함)이 miutest에 반영됐는지 `/admin`의 배포 정보(브랜치 · 커밋)로 확인.
2. Vercel 환경변수 이름 · 모양만 확인(값은 대화에 붙이지 않는다): `NEXT_PUBLIC_TOSS_CLIENT_KEY`가 `test_gck_`로, `TOSS_SECRET_KEY`가 `test_gsk_`로 시작하는지, `PAYMENTS_LIVE_MODE`가 꺼져 있는지, `TOSS_WIDGET_VARIANT_KEY`는 비워 두거나 어드민의 UI 이름과 같은지.
3. 새 테스트 주문 1건(또는 기존 pending 주문)으로 결제 화면을 PC 크롬에서 연다 → 결제수단 · 약관이 뜨고 [결제하기]가 켜지는지. 막히면 30초 안에 나오는 안내와 `/admin` 알림(`checkout.widget`)의 줄을 그대로 공유.
4. 테스트 카드로 **성공 → 리포트 열림(또는 질문 3개 지급) → MY 결제내역 → 승인 1회 · 웹훅 수신(G2) 확인**.
5. **취소**: 결제창을 닫아 MY에서 주문이 취소로 남는지, 같은 주문으로 다시 결제할 수 있는지(새 대기 주문 규칙).
6. **실패**: 토스 테스트 모드의 실패 시나리오(거절 카드 등)에서 주문이 실패로 남고 권한이 생기지 않는지.
7. **환불**: 토스 어드민에서 취소 → 웹훅(또는 `/admin`의 [결제사와 대조해 맞추기]) → 주문 환불됨 · 리포트 / 질문 권한 사라짐 · 잔액 회수.
8. 휴대폰(사파리 · 크롬 · 카카오톡 인앱)에서 3~4를 반복(G11).
9. 각 단계의 결과(주문번호 · 단계 · 코드 · 시각)를 알려 주면 이 문서의 ⛔ 줄을 ✅로 바꾼다. **확인하지 못한 줄을 합격 처리하지 않는다.**

- 실제 토스 결제위젯 · 카드 인증 · 웹훅 수신 · 환불 실행 — 외부 토스 테스트 실행은 사용자 조율 대상이다.
- 실제 Supabase(테스트 DB)에서의 결제 · 질문 묶음 · 공동 열람.
- 실제 휴대폰 · 카카오톡 인앱에서의 결제 복귀.

- 실제 AI 리포트 생성 시간(호출하지 않았다).
