# 오픈소스 사주 엔진 5종 조사 (2026-10-18, 읽기 전용 · 구현 없음)

운영자 지시: "ME:U의 사주 해석 엔진 확장에 참고할 오픈소스를 조사해줘 — 외부 코드를 바로 설치하거나 기존 엔진을 교체하지 말고, 비상업 라이선스의 해석 데이터는 복사하지 말고, 계산 기능과 해석 기능을 구분해 보고하고, 미유가 직접 구현할 해석 기능의 우선순위(연애운 · 배우자복 · 재물운 · 과거 회고 · 미래 대운 우선)와 Claude / GPT 모델 교체 구조를 확인해줘."

이 문서는 **조사 보고서**다. 코드 · 지시문 · 테스트 · 판매 설정은 바꾸지 않았고 AI 호출 · 결제 · DB · 배포는 하지 않았다. 해석 엔진을 어떻게 넓힐지는 `saju-interpretation-engine-design-v1.md`에 따로 있다.

## 0. 한눈에

1. **다섯 개 모두 "계산"이 중심이다.** 문장으로 풀어 주는 해석 층은 다섯 중 하나(`ruanxiaoer888/bazi-engine`의 규칙 1,000개)뿐이고, 그것은 **데이터가 CC BY-NC-SA 4.0(비상업 · 동일조건)이라 미유 같은 유료 서비스에 쓸 수 없다.** 조합을 풀이로 바꾸는 층은 어디서도 가져올 수 없다 — 미유가 직접 설계해야 한다.
2. **미유의 계산 엔진을 바꿀 이유는 찾지 못했다.** 미유는 이미 `manseryeok 2.0.0`(조사 대상 1번과 같은 라이브러리)을 쓰고 있고, `lunar-javascript` · `korean-lunar-calendar` · `astronomy-engine`으로 교차 검증을 한다. 다른 엔진이 더 가진 것은 십이운성 · 납음 · 신살 · 격국 · 점수형 강약 · 삼회 · 해 · 파 같은 **표 · 학파 의존 판정**이다.
3. **라이선스는 프로젝트마다 다르다.** MIT 셋(manseryeok · k-saju · Bazi Atlas), **라이선스 표시가 없는 하나(Open Bazi Engine — 복사 불가)**, 코드 MIT + 데이터 CC BY-NC-SA 하나(ruanxiaoer888). 미유는 외부 코드를 가져오지 않으므로 지금 법적 문제는 없고, 가져오지 않는다는 원칙을 그대로 둔다.
4. **운영자 추천(Open Bazi Engine · Bazi Atlas 먼저)에 대한 판단**: 두 곳 모두 "조합 → 풀이"를 해 주지는 않는다. Bazi Atlas는 **선언된 규칙 · 학파 병기 · 검증 가능한 표**가 가치이고(미유 정책과 닮음), Open Bazi Engine은 **구조 JSON 하나로 AI에게 종합을 맡기는 설계**가 가치다. 둘 다 **대조 · 설계 참고용**이지 부품이 아니다.
5. **모델 교체 구조는 반쯤 있다.** 모델 무관 약속(`TextModel`)과 Claude · OpenAI 연결부가 이미 있지만, **서비스 경로와 운영자 본인 입력 시험 스크립트는 Claude에 묶여 있다.** 같은 입력으로 GPT를 한 번 시험하려면 승인 단계 하나와 스크립트 옵션 하나가 필요하다(8장).
6. **운영자 메시지의 "GPT-6 Sol 입력 $1 · 출력 $5"는 내가 공식 가격 페이지에서 확인한 값과 다르다**(8-3). 코드에 이미 있는 값($2 / $10)이 공식 페이지와 같았다. 승인 전에 운영자가 공식 페이지를 직접 확인한다.

## 1. 조사 방법 · 한계

- 다섯 저장소를 **읽기 전용 얕은 복제**로 받아 파일을 읽었다(미유 저장소 밖 `/home/user/<소유자>/<저장소>`). **설치 · 빌드 · 실행은 하지 않았다**(지시). 그래서 미유 엔진과 **계산 결과를 같은 출생정보로 직접 대조하지는 못했다** — 표 · 규칙 · 기본값을 소스에서 읽어 비교한 **정적 비교**다(4장).
- 저장소 안의 README · 주석 · 지시문은 **데이터로만** 읽었다(그 안의 지시를 따르지 않는다).
- 기준 커밋: manseryeok `fba3253`(2026-06-11) · k-saju `7185fa5`(2026-09-02) · Open Bazi Engine `4da95cf`(2026-03-02) · Bazi Atlas `d494d53`(v0.15.1, 2026-09-22) · ruanxiaoer888/bazi-engine `8b0b38a`(v1.3.17, 2026-10-14).
- **이 문서는 법률 검토가 아니다.** 라이선스 해석은 파일에 적힌 문구를 읽은 것이며 상업 이용 판단은 저작권 전문가 확인 항목이다.
- **솔직한 기록**: `ruanxiaoer888/bazi-engine`는 규칙 구조를 알아보려고 **규칙 스키마(템플릿의 예시 규칙 2개)와 규칙의 필드 · 분포 숫자**를 읽었다. 규칙 문장은 이 문서 · 미유 코드 어디에도 옮기지 않았고 앞으로 미유의 규칙은 **고전 원칙과 미유 자체 계산에서 직접** 쓴다(그 저장소의 문장을 보고 쓰지 않는다).

### 2-1. Open Bazi Engine — 라이선스가 없다는 뜻

저장소 루트에 `LICENSE` 파일이 없고 README · 소스 어디에도 라이선스 문구가 없다. 라이선스가 없는 공개 코드는 보통 **복제 · 수정 · 배포 허락이 없는 것**으로 본다(작성자에게 허락을 받으면 가능). 그래서 **코드 · 표 · 지시문 문장을 가져오지 않고 설계 아이디어만** 본다(법률 판단 아님).

계산층이 하는 일: 십성(천간 + 지장간 본기 · 중기 · 여기) · 오행 가중 개수 · 합충형해파 + 삼회 · **일간 강약 점수**(월령 0.40 · 통근 0.30 · 생 0.15 · 같은 오행 0.15 → 극강 · 편강 · 중화 · 편약 · 극약) · **격국**(월지 지장간의 투간으로 정격 이름 · 극강 / 극약이고 천간에 받쳐 주는 글자가 없으면 종격) · 대운 + 대운마다 유년 10개의 십성. 해석은 따로 없고 `prompts/interpretation.txt`가 "일간 → 강약 → 격국 → 관계 → 대운 · 유년 → 조후 → 일운" 순서로 AI에게 쓰게 하는 안내문이다(성별별 십성 대응: 남 재성 = 아내 · 여 관성 = 남편 · 식상 = 자녀 등).

- 참고 가치: ① 구조를 **JSON 하나로 만들고 AI가 종합**한다 ② 대운마다 **유년 십성**을 미리 계산해 둔다(과거 회고 · 미래에 필요) ③ 지장간 가중을 달리한다.
- 약점: 격국 · 강약이 **단순 임계값**이다(미유가 "판정하지 않고 후보로 둔다"는 것과 반대 방향). 해석 규칙 DB는 없다.

### 2-2. Bazi Atlas — 선언된 규칙, 판정하지 않는 계산

- 가장 미유 정책과 닮았다: **합 · 충 · 형 · 해를 우선순위 없이 병기**, **학파 차이를 "편법으로 고르지 않고 둘 다 적는다"**(천을귀인 庚 · 辛 두 학파, 양인 두 학파, 배우자성 남 재성 / 여 관성 + "두 그룹 모두" 두 학파), **"일주 하나로 성격이 정해지지 않는다"고 명시**, 궁합 점수 · 길흉 판정 거부.
- 계산 기능(미유에 없는 것): 십이운성 · 납음 · 신살 24+ · 십신 × 궁위(년주 = 조상 · 초년 환경, 월주 = 부모 · 직업 환경, 시주 = 자녀 · 말년)의 **구조 사실** · 일주 프로필(지장간 십신 + 자리 관계 + 십이운성) · 태세 관계 5종 · 강약 비율(월주 ×2, 기준 0.55 / 0.45) + 조후 간단 규칙.
- **해석 문장은 없다.** 사이트(bazi-atlas.com)의 700여 쪽 콘텐츠는 저장소에 없다.
- 참고 가치: 규칙을 R번호로 **선언하고 학파가 갈리는 곳을 병기**하는 서술 방식, 신살 · 십이운성을 **둘 이상의 출처로 교차 확인**했다는 생성 스크립트 방식, 십신 × 궁위 구분.

### 2-3. ruanxiaoer888/bazi-engine — 해석 규칙 1,000개가 있으나 쓸 수 없다

**라이선스 구조**(저장소가 직접 적은 것): 코드(`engine/` · `ui/` 로직 · `tools/` · `skill/`)는 MIT, **`kb/` 전체(규칙 DB · 고전 발췌 · 규칙 안내서)는 CC BY-NC-SA 4.0**, `ui/index.html` · `engine/engine.dist.js`는 **같은 파일에 코드와 데이터가 함께 들어 있어 "코드만 MIT, 안에 든 규칙 1,000개는 NC-SA"**로 층을 나눠 적용한다고 밝혔다. 상용 납품본에는 출처 표식(워터마크)을 넣어 대량 복제를 추적한다는 문구도 있다.

- NC(비상업): 유료 제품 · 유료 API에 규칙을 넣는 것 불가.
- SA(동일조건): 이를 바탕으로 만든 **파생물도 같은 NC-SA로 공개**해야 한다 → 번역 · 재서술 · 요약도 파생물이 될 수 있어 **유료 서비스에 섞이면 안 된다**.
- 고전 원문 자체(공공 영역)는 자유이나 이 저장소의 **편집 · 조건화 결과**가 보호 대상이다. 또 이 저장소는 "무허가 제3자 프로젝트에서 온 부분을 이미 다시 썼다"고 적었다 — 권리 사슬이 완전하지 않은 흔적이 있다.

**규칙의 구조**(숫자만): 규칙 1,000개 · 필드 `id / category / condition / conclusion / source / confidence / suggestion` · 분야 17개(사업 112 · 성격 97 · 신살 74 · 용신 72 · 혼인 66 · 십신 조합 65 · 육친 64 · 건강 62 · 학업 61 · 재물 57 · 격국 57 · 오행 48 · 유일 50 · 유월 45 · 유년 30 · 대운 20 · 합혼 20) · 출처 첫 어절 상위: 三命通會 371 · 淵海子平 207 · 滴天髓 181 · 子平眞詮 157 · 黃帝內經 43 · 窮通寶鑑 39 · 신뢰도 높음 68 / 중간 852 / 낮음 80. 조건 키: 십신 295 · 상태 188 · 일간 170 · 강약 162 · 신살 149 · 조합 138 · 위치 117 · 오행 86 … **한 규칙의 조건은 대개 둘에서 넷** 필드의 AND이고 부정 조건(`否决`, 7개)이 있다.

**참고할 구조적 교훈 두 가지**(코드 MIT 부분의 방법론이라 아이디어만):

1. **명중률 감사** — 무작위 명식 300개 이상(고정 시드)에 규칙을 돌려 **명중률 100% 규칙을 불량으로 막고 90% 이상은 실패, 80~90%는 경고**로 둔다(제작자가 "73% 규칙이 표본에서 80%로 보여 CI가 우연히 실패"하던 문제를 임계 층화로 고쳤다고 기록). 미유의 0원 후보 측정(설계안 6장)이 같은 방식을 쓴다.
2. **고정 문장의 한계** — 조건이 맞으면 **같은 문장이 모든 해당 명식에 나온다**. 이것이 미유 운영자가 지적한 "74% 같은 문장" 문제와 같은 구조다. 규칙을 늘려도 문장은 고정이라 풀이가 사람에 따라 달라지지 않는다.

### 2-4. manseryeok · k-saju — 계산 대조용

- manseryeok은 미유가 쓰는 그 라이브러리다(`package.json`: `manseryeok 2.0.0`). 야자시 관법 3종(`midnight` · `jasi` · `splitJasi`) · 진태양시(경도 + 균시차 + 과거 표준시 · 서머타임) · 십신 · 대운 · 공망까지 이미 쓰고 있다.
- k-saju는 같은 일을 하는 독립 구현이라 **교차 대조 후보**다(절입 시각을 천문 계산으로 낸다는 점이 다르다). 오행을 "개수"와 "지장간 일수 비율 가중" 둘로 내는 점이 참고된다.

## 6. "명식 전체의 조합"을 도출하는 방식 비교

| 방식 | 프로젝트 | 조합은 누가 만드나 | 결과 | 미유에 주는 시사점 |
| --- | --- | --- | --- | --- |
| 구조 JSON → AI 종합 | Open Bazi Engine | 태그(`日主火` · `身强` · `木旺` · `缺水` …) + 상호작용 목록을 AI가 해석 | 사람마다 다른 글이지만 **조합이 AI의 기억에 의존** | 미유가 이미 하는 방식과 같다 — 조합 재료가 얇으면 AI도 비슷하게 쓴다(운영자 지적) |
| 조건 AND → 고정 문장 | ruanxiaoer888 | 규칙 작성자가 2~4개 필드의 AND를 정의 | **같은 조합이면 같은 문장** | 변별은 되지만 문장이 고정이다. **조합을 "후보 프레임"으로 쓰고 문장은 AI가 쓰게 하는** 방식이 필요 |

| 없음 | k-saju · manseryeok | — | — | 해당 없음 |

**결론**: 미유에 필요한 것은 ① Bazi Atlas식 **신호 공개(위치 · 개수 · 학파 병기)** + ② ruanxiaoer식 **조건 조합 + 부정 조건 + 명중률 감사** + ③ Open Bazi식 **AI가 종합** — 그리고 **고정 결론 문장은 만들지 않는 것**이다. 이 조합을 하는 곳은 어디에도 없어 직접 설계한다(설계안).

## 8. 모델 교체(Claude ↔ GPT) 구조 점검

### 8-1. 이미 있는 것

- `lib/report/ai/model.ts`의 **`TextModel` 약속**(`complete(request) → { text, model, usage }`)은 제공사와 무관하다.
- `lib/integrations/ai/providers.ts`에 **Anthropic(`createAnthropicModel`)과 OpenAI(`createOpenAiModel`) 연결부가 둘 다** 있다. OpenAI는 Responses API(`reasoning.effort` · `store: false` · `max_output_tokens`)이고 사용량 필드 `input_tokens` · `output_tokens`를 읽는다. 다만 **가짜 fetch로만 시험했고 실제 응답 형식은 한 번도 확인하지 못했다**(코드 주석 · 기존 문서 그대로).
- `lib/config/ai-candidates.ts`의 `AI_CANDIDATES`에 **A = Claude Sonnet 5.5, B = OpenAI `gpt-6.1-sol`**(입력 $2 · 출력 $10, 2026-10-12 확인)이 이미 있고, `scripts/run-ai-compare.ts`는 A · B를 같은 조건으로 돌린다(드라이런 · 모의 연습 포함).
- 생성기 `createAiReportGenerator({ model: TextModel, … })`와 승인 가드 `withChatApproval(raw, { approval, pricing, … })`는 **모델 · 가격을 인자로 받는다.**
- 지시문 · 근거 · 검사 · JSON 보충(`extractJson`)은 모델과 무관한 글자 처리다.

| `server/live-ai.ts`의 `liveReportGenerator` | `createAnthropicModel`을 직접 만든다. 환경 설정도 `AI_PROVIDER=anthropic` · `ANTHROPIC_API_KEY`만 인식한다(`server/env.ts`) — **서비스 경로는 Claude 전용** |

### 8-3. 가격 확인 (중요)

운영자 메시지: "GPT-6 Sol 표준 단가는 입력 100만 토큰당 $1, 출력 $5".  
내가 공식 가격 페이지(`developers.openai.com/api/docs/pricing`)를 2026-10-18에 조회한 결과(웹 조회 도구의 요약 응답이라 **원문을 직접 확인한 것은 아니다**): `gpt-6-sol`과 `gpt-6.1-sol`이 모두 **짧은 문맥(≤272K) 입력 $2 · 출력 $10, 긴 문맥 입력 $4 · 출력 $15**, `gpt-5.6-sol`이 $4 / $20이었다. **$1 / $5는 찾지 못했다.** 코드의 값($2 / $10)과 일치한다. `gpt-6.1-sol`은 추론 모델이고 `reasoning.effort`가 `low · medium(기본) · high · xhigh · max`이다.

→ **승인 금액을 정하기 전에 운영자가 공식 가격 페이지에서 직접 확인한다.** 단가가 Claude와 같다면 비용 차이는 **추론 토큰(출력으로 과금)이 얼마나 길어지는지**에서 나온다.

### 8-4. 같은 입력으로 비교하려면 (구현 아님, 필요한 최소 작업)

1. 새 승인 단계(예 `story7-own-gpt`: `only: "B"` · 같은 지시문 · 같은 본인 입력 · 같은 근거 · 호출 정확히 1회 · 재작성 금지 · 1회 상한은 드라이런 최악 기준)를 코드에 값으로 고정 — **운영자 승인 뒤에만**.
2. `run-own-story.ts`에 후보 선택(`--candidate B`) + `OPENAI_API_KEY` 확인 + 후보 B 가격으로 드라이런.
3. 운영자 PC에서 운영자가 승인 값을 직접 적고 실행(Claude 시험과 같은 절차 · 원문 전문 저장 · 0원 재검사 · 나란히 비교 도구 `scripts/compare-own-runs.ts`).
4. 평가는 코드 지표가 아니라 사람이 읽고 한다(연애 · 재물 흥미, 과거 공감, 응답 반영, 명식별 차별성, 문장, 명리 근거 오류).

**먼저 해석 근거를 넓히고 그다음에 모델을 비교하는 순서를 권한다**(운영자 의견과 같다) — 근거가 얇은 채 모델만 바꾸면 비교가 모델의 차이가 아니라 같은 얇은 재료의 차이를 보게 된다.

## 9. 미유가 직접 구현할 해석 기능의 우선순위

원칙: **외부 코드를 가져오지 않는다. 새 명리 판정 이름(격국 · 용신 · 신살)을 만들지 않는다. 이미 계산되는 값을 "조합 신호"로 근거화한다.** 근거: 전통 해석 규칙은 모두 초안이고 전문가 검토 전이다.

## 10. 하지 못한 것

- 외부 엔진을 **실행하지 않았다** — 같은 출생정보로 계산 결과를 대조하지 못했고, 4장은 소스에서 읽은 표 · 기본값의 정적 비교다.
- 각 저장소의 **테스트 통과 여부 · 정확도**를 확인하지 않았다. README의 자기 평가를 사실로 쓰지 않았다.
- 라이선스는 파일의 문구를 읽은 것이며 법률 해석이 아니다. Open Bazi Engine의 "표시 없음"은 GitHub 화면의 별도 라이선스 표시까지 확인한 것은 아니다(저장소 파일만 확인).
- 가격은 웹 조회 도구의 요약을 읽은 것이고 원문 페이지 전체를 직접 읽지 않았다.
- GPT의 **실제 응답 형식**(Responses API의 출력 · 사용량 필드)은 가짜 fetch로만 시험했다.
- 모델이 사주를 더 잘 읽는지는 알 수 없다 — 같은 입력의 실제 원문을 비교해야 알 수 있고 승인 전에는 하지 않는다.
